# 皮革背包 OBJ 模型实验（已应用到正式代码）

你放进这个目录的文件：

| 文件 | 内容 |
|---|---|
| `皮革背包.glb` | AI 生成的皮革背包完整模型（真实雕刻网格，带 PBR 贴图），本轮实验的原始素材 |
| `皮革背包.jpg` / `铁背包.jpg` / `金背包.jpg` / `钻石背包.jpg` / `下界合金背包.jpg` | 五档的效果参考图，目前只有皮革档生成了对应的 `.glb` 完整模型，其余四档暂时只是风格/配色参考，还没建模 |
| `obj_export/` | 我处理后、实际应用到游戏里的产物（见下）|

## 分析结论：能不能直接用

**不能直接套用 Minecraft 原版物品模型 JSON**（就是 `leather_floating_backpack.json` 之前用的那种
`"elements"` 格式）——那个格式只支持轴对齐长方体。用 Blender MCP 读了 `皮革背包.glb` 的真实结构：

- 15,535 顶点 / 16,178 面，是一个真正意义上的雕刻网格（看得出每条边都加了倒角），不是立方体拼接。
- 材质是标准 glTF PBR 三件套：Base Color（漫反射）+ Normal（法线）+ ORM（金属度/粗糙度打包）各一张
  2048×2048。Minecraft 物品渲染是不带实时 PBR 的简单纹理贴图，Normal/ORM 这两张贴图游戏里完全用不上，
  只有 Base Color 这张能实际派上用场。
- 没有背带（肩带）几何体，只有主体+翻盖+前袋+两个侧袋+铆钉装饰——你确认了这是有意的设计方向（偏"工具
  腰包/斜挎包"风格），不用补背带。

## 用的方案：NeoForge 内置的 OBJ 模型加载器

这是 NeoForge 自带的能力（不是第三方 mod，`net.neoforged.neoforge.client.model.obj.ObjLoader`，loader id
是 `neoforge:obj`），读了它的源码确认了几个关键点：

1. `.mtl` 材质文件里的 `map_Kd` 可以写成 `#贴图变量名` 的写法（和我们现有模型里 `"texture": "#backpack"`
   是同一套机制），实际贴图由物品模型 JSON 自己的 `"textures"` 字典决定——所以可以完全照搬现有的贴图资源
   管理方式，不需要给 OBJ 模型单独发明一套贴图系统。
2. OBJ 模型的顶点坐标是**直接当成方块空间坐标使用**的（1 个 OBJ 单位 = 1 个 Minecraft 方块），跟原来
   `"elements"` 格式的 0-16 网格（0-16 对应 0-1 方块）不是一回事。
3. `ItemRenderer.render()`（读的是 `neoforge-21.1.251-sources.jar` 里的源码）不管模型是 `"elements"`
   格式还是 OBJ 格式，都会无条件执行 `poseStack.translate(-0.5, -0.5, -0.5)`——这意味着 OBJ 模型的坐标
   也得按"0 到 1，不是 -0.5 到 0.5"的约定来写，和原来的 `"elements"` 格式一致，这样这次自动居中才能把模型
   摆到正确位置。
4. `display`（`gui`/`thirdperson_*`/`firstperson_*`/`fixed` 等视角变换）这块完全通用，和模型是哪种格式
   无关——`ItemTransform.apply()` 对旋转数值的处理是 `new Quaternionf().rotationXYZ(...)`，这是一个纯粹
   作用在"摄像机 vs 物体"关系上的固定变换，跟挂在物体上的具体几何形状完全没关系。这点很关键：第二轮我们
   把立方体模型的 `gui`/`thirdperson_*`/`firstperson_*`/`fixed` 旋转都加了 180°，是因为立方体模型的"正
   面"（扣具那一侧）朝着 north；而这次读取这个 GLB 导出的 OBJ 坐标发现它的"正面"（扣具/前袋那一侧）朝
   着 **south**（和立方体模型方向相反）。所以这次没有套用立方体模型改过的旋转值，而是直接照搬了**最原
   始、第一次重新建模之前的** `floating_backpack.json` 那套旋转数值——因为那套原始数值本来就是"south 朝
   镜头"的效果，正好和这个新网格的正面朝向对上。

## `obj_export/` 里的产物 & 处理流程

1. **减面**：原始 16,178 三角面对一个要频繁渲染的物品（图标、手持、GUI 悬停、其他玩家背上同时看到好几个）
   来说偏重，用 Blender 的 Decimate（Dissolve 模式，20° 共面合并阈值）把面数砍到 7,277（降了 55%），渲染
   图对比过，这个幅度下视觉细节几乎没有损失（见下面"减面前后对比"）。
2. **贴图分辨率：1024×1024，不是最早用的 512**（这是第二轮修正，见下面"贴图模糊，为什么、怎么修"）。
3. **坐标偏移 +0.5**：导出时用 Blender 默认的 `Forward: -Z, Up: Y` 轴向转换成 Minecraft 的 Y-up 坐标系，
   导出后整体顶点坐标又加了 (0.5, 0.5, 0.5)，把原来以原点为中心的 -0.5~0.5 范围挪到 0~1（配合上面第 3 点
   的自动居中逻辑）。
4. **`.mtl` 改成用贴图变量**：`map_Kd` 从 Blender 导出的字面文件名改成了 `map_Kd #base`，对应物品模型 JSON
   `"textures"` 里的 `"base"` 这一项。

产物：`leather_backpack.obj`（7,277 三角面）、`leather_backpack.mtl`、`leather_backpack_diffuse.png`
（1024×1024，Base Color）、`leather_backpack_normal_n.png`（1024×1024，LabPBR 法线贴图，见下面单独一节）。

## 贴图模糊，为什么、怎么修

你反馈拿在手上/背到身上贴图糊，怀疑是分辨率太低，建议改成 64×64 或 32×32。排查之后，实际情况和"分辨率
不够"不是一回事：

- 把原始 2048×2048 贴图直接截一块放大看，**皮革本体的方格纹理在 2048 原始分辨率下本来就是清晰的硬边**，
  不模糊；但**金色五金件（扣具、铆钉）的边缘在 2048 原始分辨率下就已经是柔和/带羽化的**——这是 AI 生成
  这个模型时，贴图是从 3D 渲染烘焙出来的（边缘自带抗锯齿/倒角高光），不是逐像素手绘的硬边像素画，这部分
  模糊是贴图本身自带的，换多大分辨率都去不掉。
- 但是：我第一版把贴图从 2048 直接缩到 512，用的是 Lanczos（适合缩小照片类图像的平滑算法），**把本来清
  晰的方格纹理也一起缩模糊了**——这部分模糊是我自己缩图时引入的，是真正可以修的。
- 实测对比了 64/128/256/512/1024 几档（都缩小后再用最近邻放大到同样大小看，模拟游戏里实际显示效果）：
  64/128/256 这几档因为细节密度太高，缩小后方格纹理几乎完全糊成一团噪点，**不是"变成像素风"，是直接丢失
  信息**，不如大分辨率；1024 这一档方格纹理基本保持了 2048 原图的清晰度，金色五金件的柔和边缘和原图一致
  （本来就是软边，不是这次缩图造成的）。所以最终选了 **1024×1024**，不是 512，也没有用你建议的 64/32——
  这个贴图是"烘焙渲染图"而不是"手绘像素画"，不符合"我的世界用小分辨率像素贴图"这个一般印象，缩到 32/64
  只会把细节丢没，不会变成清晰的像素风。

## 更正：真正导致"黄色污渍"的是 UV 的 V 方向没翻转（`flip_v`）

上一节我把"糊"主要归因到缩图算法和分辨率，那个判断只对了一部分（Lanczos 确实会把方格纹理缩糊，1024 也
确实比 512 清晰），但**背上看到一片片黄色污渍、和原始模型完全不像，真正的主因是另一个 bug**，我当时漏
掉了：

- 读 `ObjModel.java` 第 376 行：`texture.getV(flipV ? 1 - texCoord.y : texCoord.y)`，`flip_v` 默认是
  `false`，也就是直接把 OBJ 里的 V 当成"从上往下"来用。
- 但标准 OBJ（包括 Blender 导出的）V=0 是图片**底部**，Minecraft 的 V=0 是图片**顶部**，两者差一个上下
  翻转。不开 `flip_v`，所有面都在贴图里上下颠倒着取色——本该取皮革的面取到了金色五金件区域，本该取扣具
  的面取到了皮革区域，混在一起就是一片片黄色污渍。
- 修复：物品模型 JSON 里加 `"flip_v": true`。这也解释了为什么贴图换成更高分辨率之后你仍然看到污渍。

这是读源码确认的原因，没法用游戏截图自己验证修复后的效果，需要你再看一眼。

## 加回了法线贴图（没加高光/粗糙度贴图）

你说得对，现在装光影包（Iris/Oculus，NeoForge 上的移植版叫 NeOculus）的玩家很多，法线贴图能在有光影时
提供更好的凹凸光照效果，光影不存在时这张贴图完全不会被用到、不影响没装光影的玩家——这是纯增量、零风险
的事，加回来了。查了光影社区的权威规范 [ShaderLabs Wiki LabPBR Materials](https://shaderlabs.org/wiki/LabPBR_Materials)
确认了具体格式（命名约定是贴图同目录下 `<贴图名>_n.png`，Iris/Oculus 这类光影加载器会自动识别，不需要
我们这边写任何代码或 JSON 配置）：

- R 通道 = X 方向（不变）；G 通道 = Y 方向，但**需要翻转**——glTF/Blender 的法线贴图是 OpenGL 惯例（Y 朝
  上），LabPBR 规范要求 DirectX 惯例（Y 朝下），不翻转会导致凹凸方向反了。
- B 通道 = 环境光遮蔽（AO），不是原来法线贴图自带的 Z 分量（LabPBR 会用 R/G 重新算出 Z）。
- A 通道 = 高度图（视差贴图用），没有数据时填 255（=无视差效果，安全默认值）。

已生成 `leather_floating_backpack_n.png`（1024×1024，和正贴图同目录同名+`_n`后缀）并应用到正式代码。

**没有加高光/粗糙度贴图（`_s`）**：这个也查了规范，格式本身不难（R=平滑度、G=金属度编码、B=孔隙度、A=
自发光），但用 Blender 读了这个 GLB 自带的粗糙度/金属度数据实测发现：**金色扣具和皮革主体在这两个通道
里的数值几乎没有区分度**（粗糙度几乎全是 250-255 这一个窄范围，金属度全是 80-98 这一个窄范围，用阈值去
分都分不出"哪里是金属哪里是皮革"）——换句话说，这个模型生成时这两个通道大概率只是占位的默认值，不是真
的按材质分别画出来的。如果拿这种没有区分度的数据硬套 LabPBR 格式，做出来的高光贴图要么全图一个效果（光
影下完全看不出金属质感），要么我自己臆测一个"哪里是金"的遮罩来凑——这种没有可靠数据支撑的猜测，做错了
比不做还难看，所以这次先不做，法线贴图是有真实凹凸数据支撑的，高光贴图目前没有。

  `"loader": "neoforge:obj"` 格式，不再是 `"elements"` 长方体格式；`display` 沿用了上面说的"原始未修改"
  那套旋转数值，位移/缩放数值也暂时沿用原始值（没有重新摸索，详见下面"还没验证的部分"）。

  `leather_floating_backpack_n.png`（1024×1024 法线贴图，见上面单独一节）。
- `BackpackBackLayer.java`（背到身上的渲染，上一轮已经改成直接渲染物品真实烘焙模型）不需要任何结构性改
  动——它本来就是不关心模型具体格式的通用代码。只是因为这个模型没有背带，没有"东西固定住"的视觉支撑，
  按你的要求把贴近身体的位移从 `-0.32` 调近到了 `-0.40`，让背包尽量贴紧人物、减少空隙。

  应的 `.glb` 完整模型。
