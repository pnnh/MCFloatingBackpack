# 皮革背包 OBJ 模型实验（已应用到正式代码）

你放进这个目录的文件：

| 文件 | 内容 |
|---|---|
| `皮革背包.glb` | AI 生成的皮革背包完整模型（真实雕刻网格，带 PBR 贴图），本轮实验的原始素材 |
| `皮革背包.jpg` / `铁背包.jpg` / `金背包.jpg` / `钻石背包.jpg` / `下界合金背包.jpg` | 五档的效果参考图，目前只有皮革档生成了对应的 `.glb` 完整模型，其余四档暂时只是风格/配色参考，还没建模 |
| `obj_export/` | 我处理后、实际应用到游戏里的产物（见下）|

## 分析结论：能不能直接用

**不能直接套用 Minecraft 原版物品模型 JSON**（就是 `leather_floating_backpack.json` 之前用的那种
`"elements"` 格式）——那个格式只支持轴对齐长方体。用 Blender MCP 读了 `皮革背包.glb` 的真实结构：

- 15,535 顶点 / 16,178 面，是一个真正意义上的雕刻网格（看得出每条边都加了倒角），不是立方体拼接。
- 材质是标准 glTF PBR 三件套：Base Color（漫反射）+ Normal（法线）+ ORM（金属度/粗糙度打包）各一张
  2048×2048。Minecraft 物品渲染是不带实时 PBR 的简单纹理贴图，Normal/ORM 这两张贴图游戏里完全用不上，
  只有 Base Color 这张能实际派上用场。
- 没有背带（肩带）几何体，只有主体+翻盖+前袋+两个侧袋+铆钉装饰——你确认了这是有意的设计方向（偏"工具
  腰包/斜挎包"风格），不用补背带。

## 用的方案：NeoForge 内置的 OBJ 模型加载器

这是 NeoForge 自带的能力（不是第三方 mod，`net.neoforged.neoforge.client.model.obj.ObjLoader`，loader id
是 `neoforge:obj`），读了它的源码确认了几个关键点：

1. `.mtl` 材质文件里的 `map_Kd` 可以写成 `#贴图变量名` 的写法（和我们现有模型里 `"texture": "#backpack"`
   是同一套机制），实际贴图由物品模型 JSON 自己的 `"textures"` 字典决定——所以可以完全照搬现有的贴图资源
   管理方式，不需要给 OBJ 模型单独发明一套贴图系统。
2. OBJ 模型的顶点坐标是**直接当成方块空间坐标使用**的（1 个 OBJ 单位 = 1 个 Minecraft 方块），跟原来
   `"elements"` 格式的 0-16 网格（0-16 对应 0-1 方块）不是一回事。
3. `ItemRenderer.render()`（读的是 `neoforge-21.1.251-sources.jar` 里的源码）不管模型是 `"elements"`
   格式还是 OBJ 格式，都会无条件执行 `poseStack.translate(-0.5, -0.5, -0.5)`——这意味着 OBJ 模型的坐标
   也得按"0 到 1，不是 -0.5 到 0.5"的约定来写，和原来的 `"elements"` 格式一致，这样这次自动居中才能把模型
   摆到正确位置。
4. `display`（`gui`/`thirdperson_*`/`firstperson_*`/`fixed` 等视角变换）这块完全通用，和模型是哪种格式
   无关——`ItemTransform.apply()` 对旋转数值的处理是 `new Quaternionf().rotationXYZ(...)`，这是一个纯粹
   作用在"摄像机 vs 物体"关系上的固定变换，跟挂在物体上的具体几何形状完全没关系。这点很关键：第二轮我们
   把立方体模型的 `gui`/`thirdperson_*`/`firstperson_*`/`fixed` 旋转都加了 180°，是因为立方体模型的"正
   面"（扣具那一侧）朝着 north；而这次读取这个 GLB 导出的 OBJ 坐标发现它的"正面"（扣具/前袋那一侧）朝
   着 **south**（和立方体模型方向相反）。所以这次没有套用立方体模型改过的旋转值，而是直接照搬了**最原
   始、第一次重新建模之前的** `floating_backpack.json` 那套旋转数值——因为那套原始数值本来就是"south 朝
   镜头"的效果，正好和这个新网格的正面朝向对上。

## `obj_export/` 里的产物 & 处理流程

1. **不减面，用原始 16,178 三角面的完整网格**（最早我做过 Dissolve 减面到 7,277，后来发现会撕出裂缝，
   已撤销，见下面"透光裂缝"一节）。
2. **贴图分辨率：1024×1024，不是最早用的 512**（这是第二轮修正，见下面"贴图模糊，为什么、怎么修"）。**【2026-11-04 更新】后来发现 1024 会把共用图集撑到 4096×4096，010 正在把它改回 512（盒式缩放 + 轻锐化）并把 `_n` 排除出图集，见 `specs/010-backpack-texture-budget/research.md`；"512 糊"的结论也需要修订：当时的反馈还叠加了 `flip_v` bug。**
3. **坐标偏移 +0.5**：导出时用 Blender 默认的 `Forward: -Z, Up: Y` 轴向转换成 Minecraft 的 Y-up 坐标系，
   导出后整体顶点坐标又加了 (0.5, 0.5, 0.5)，把原来以原点为中心的 -0.5~0.5 范围挪到 0~1（配合上面第 3 点
   的自动居中逻辑）。
4. **`.mtl` 改成用贴图变量**：`map_Kd` 从 Blender 导出的字面文件名改成了 `map_Kd #base`，对应物品模型 JSON
   `"textures"` 里的 `"base"` 这一项。

产物：`leather_backpack.obj`（16,178 三角面）、`leather_backpack.mtl`、`leather_backpack_diffuse.png`
（1024×1024，Base Color）、`leather_backpack_normal_n.png`（1024×1024，LabPBR 法线贴图，见下面单独一节）。

## 贴图模糊，为什么、怎么修

你反馈拿在手上/背到身上贴图糊，怀疑是分辨率太低，建议改成 64×64 或 32×32。排查之后，实际情况和"分辨率
不够"不是一回事：

- 把原始 2048×2048 贴图直接截一块放大看，**皮革本体的方格纹理在 2048 原始分辨率下本来就是清晰的硬边**，
  不模糊；但**金色五金件（扣具、铆钉）的边缘在 2048 原始分辨率下就已经是柔和/带羽化的**——这是 AI 生成
  这个模型时，贴图是从 3D 渲染烘焙出来的（边缘自带抗锯齿/倒角高光），不是逐像素手绘的硬边像素画，这部分
  模糊是贴图本身自带的，换多大分辨率都去不掉。
- 但是：我第一版把贴图从 2048 直接缩到 512，用的是 Lanczos（适合缩小照片类图像的平滑算法），**把本来清
  晰的方格纹理也一起缩模糊了**——这部分模糊是我自己缩图时引入的，是真正可以修的。
- 实测对比了 64/128/256/512/1024 几档（都缩小后再用最近邻放大到同样大小看，模拟游戏里实际显示效果）：
  64/128/256 这几档因为细节密度太高，缩小后方格纹理几乎完全糊成一团噪点，**不是"变成像素风"，是直接丢失
  信息**，不如大分辨率；1024 这一档方格纹理基本保持了 2048 原图的清晰度，金色五金件的柔和边缘和原图一致
  （本来就是软边，不是这次缩图造成的）。所以当时选了 **1024×1024**（**已被 010 取代，见文末"第九轮"**），不是 512，也没有用你建议的 64/32——
  这个贴图是"烘焙渲染图"而不是"手绘像素画"，不符合"我的世界用小分辨率像素贴图"这个一般印象，缩到 32/64
  只会把细节丢没，不会变成清晰的像素风。

## 更正：真正导致"黄色污渍"的是 UV 的 V 方向没翻转（`flip_v`）

上一节我把"糊"主要归因到缩图算法和分辨率，那个判断只对了一部分（Lanczos 确实会把方格纹理缩糊，1024 也
确实比 512 清晰），但**背上看到一片片黄色污渍、和原始模型完全不像，真正的主因是另一个 bug**，我当时漏
掉了：

- 读 `ObjModel.java` 第 376 行：`texture.getV(flipV ? 1 - texCoord.y : texCoord.y)`，`flip_v` 默认是
  `false`，也就是直接把 OBJ 里的 V 当成"从上往下"来用。
- 但标准 OBJ（包括 Blender 导出的）V=0 是图片**底部**，Minecraft 的 V=0 是图片**顶部**，两者差一个上下
  翻转。不开 `flip_v`，所有面都在贴图里上下颠倒着取色——本该取皮革的面取到了金色五金件区域，本该取扣具
  的面取到了皮革区域，混在一起就是一片片黄色污渍。
- 修复：物品模型 JSON 里加 `"flip_v": true`。这也解释了为什么贴图换成更高分辨率之后你仍然看到污渍。

这是读源码确认的原因，没法用游戏截图自己验证修复后的效果，需要你再看一眼。

## 透光裂缝：减面把网格撕开了，已改用原始完整网格

现象：第三人称背后仰视拉近，背包内部有很多横竖的细条纹，能透过去看到天空/人物皮肤。

原因（用脚本逐条边统计确认，不是猜的）：
- Minecraft 渲染物品时会做背面剔除，面朝向摄像机的反面不画；Blender 预览不剔除，所以我之前用 Blender 渲
  染图检查"减面没有损失"时看不出问题——那个检查方法本身漏掉了这类缺陷。
- 按顶点位置统计每条边被几个面共用：原始网格只有 16 条开放边（基本封闭）；我之前的 Dissolve 减面（20°）
  之后变成 **1,506 条开放边**——也就是几百处裂缝。这个 AI 网格由很多互相穿插的部件（倒角、口袋、五金件）
  叠成，边被 3~6 个面共用的非流形边有 900 多条，减面算法对这种网格会撕开洞。
- 试了其他减面方案都一样：Dissolve 5° 仍有 699 条开放边；Collapse（保留 UV 边界）0.6 比例 4,648 条、
  0.4 比例 6,022 条——都比原始网格差很多。

修复：撤销减面，改用原始完整网格（16,178 三角面，裂缝回到原始的 16 条，已基本封闭）。代价是面数比减
面版本多一倍多；单个物品 1.6 万三角面对现代电脑不算重，但比原版物品大得多，如果后面性能有问题再考虑别
的办法（比如手工重拓扑，而不是自动减面）。

## 加回了法线贴图（没加高光/粗糙度贴图）

你说得对，现在装光影包（Iris/Oculus，NeoForge 上的移植版叫 NeOculus）的玩家很多，法线贴图能在有光影时
提供更好的凹凸光照效果，光影不存在时这张贴图完全不会被用到、不影响没装光影的玩家——这是纯增量、零风险
的事，加回来了。查了光影社区的权威规范 [ShaderLabs Wiki LabPBR Materials](https://shaderlabs.org/wiki/LabPBR_Materials)
确认了具体格式（命名约定是贴图同目录下 `<贴图名>_n.png`，Iris/Oculus 这类光影加载器会自动识别，不需要
我们这边写任何代码或 JSON 配置）：

- R 通道 = X 方向（不变）；G 通道 = Y 方向，但**需要翻转**——glTF/Blender 的法线贴图是 OpenGL 惯例（Y 朝
  上），LabPBR 规范要求 DirectX 惯例（Y 朝下），不翻转会导致凹凸方向反了。
- B 通道 = 环境光遮蔽（AO），不是原来法线贴图自带的 Z 分量（LabPBR 会用 R/G 重新算出 Z）。
- A 通道 = 高度图（视差贴图用），没有数据时填 255（=无视差效果，安全默认值）。

已生成 `leather_floating_backpack_n.png`（1024×1024，和正贴图同目录同名+`_n`后缀）并应用到正式代码。

**没有加高光/粗糙度贴图（`_s`）**：这个也查了规范，格式本身不难（R=平滑度、G=金属度编码、B=孔隙度、A=
自发光），但用 Blender 读了这个 GLB 自带的粗糙度/金属度数据实测发现：**金色扣具和皮革主体在这两个通道
里的数值几乎没有区分度**（粗糙度几乎全是 250-255 这一个窄范围，金属度全是 80-98 这一个窄范围，用阈值去
分都分不出"哪里是金属哪里是皮革"）——换句话说，这个模型生成时这两个通道大概率只是占位的默认值，不是真
的按材质分别画出来的。如果拿这种没有区分度的数据硬套 LabPBR 格式，做出来的高光贴图要么全图一个效果（光
影下完全看不出金属质感），要么我自己臆测一个"哪里是金"的遮罩来凑——这种没有可靠数据支撑的猜测，做错了
比不做还难看，所以这次先不做，法线贴图是有真实凹凸数据支撑的，高光贴图目前没有。

## 第四轮：背上大小、颜色偏暗分析

**背上偏小 → 已调大约 1.24 倍**（`BackpackBackLayer` 的缩放 0.55 → 0.68，手持用的是模型 JSON 自己的 `display`，
没有动，大小不变）。放大之后背包近身面的位置会跟着变，所以 z 按公式重新算了（`-(0.12 + 0.262×S)`，S 为净缩放
0.748，得 -0.316），Y 从 -0.45 微调到 -0.42，避免变高后掉到腰以下。这些数值是算出来的，没有实测。

**颜色偏暗不是错觉**（没有修改，按你的要求只分析）：
- 用脚本按网格实际用到的 UV 区域（按面积加权，排除贴图里没用到的空白区域）采样，贴图平均亮度约 33；参考
  jpg 里背包部分平均亮度约 61（中位数 49），贴图大约只有参考图的 0.55~0.65 倍亮度。
- 原因：GLB 的 Base Color 本来就偏暗（PBR 反照率，没有高光和环境光），jpg 是带灯光和高光渲染出来的效果图，
  所以看起来更亮。和有没有光影包无关，你装了光影包可能会因为光影的处理方式有一点不同，但贴图本身就比参
  考图暗。
- 另外发现一个附带问题（**没有修改**）：`.mtl` 里的 `Ka 1 1 1` 会让 NeoForge OBJ 加载器默认走 `emissive_ambient`，
  也就是整个模型按最大亮度渲染、不受白天黑夜/阴影影响、也不做方向明暗（`ObjModel` 340~343 行）。白天看没
  问题，但夜里或山洞里背包会像自己发光一样。如果要修，建议把 `emissive_ambient` 关掉（让它受环境光影响），
  同时整体提亮贴图（约 1.5~1.9 倍）来补偿，避免白天反而更暗。你决定要不要做。

## 第五轮：已修复颜色偏暗和模型始终全亮

- `leather_floating_backpack.json` 加了 `"emissive_ambient": false`：模型不再按最大亮度渲染，开始受白天黑夜、
  洞穴和阴影影响（夜里不会再像自己发光）。
- 贴图整体提亮：对 Base Color 做 gamma 0.62 的曲线（`255*(x/255)^0.62`），不是线性乘法——线性放大会让金色
  高光被截断成纯色，gamma 曲线能把偏暗的皮革拉亮、同时保持最亮处不超出。按网格实际用到的 UV 区域面积加权，
  平均亮度从 32.7 提到约 62，和参考 jpg 背包部分的平均亮度（约 61）接近。曲线选择过程：gamma 0.8/0.75/0.7/
  0.65 分别约 45/49/53/58；因为关闭全亮之后游戏光照在白天大约会再乘上 0.8~1.0 的系数，所以取了偏亮一点的 0.62。
- 未提亮的原始贴图保留为 `obj_export/leather_backpack_diffuse_original.png`，想回退或换别的曲线可以从它重新算。
- 法线贴图 `_n` 没有动（亮度调整只针对 Base Color）。
- 没法自己截图验证，需要你在游戏里实测：白天看是否接近参考图，夜里/洞穴里是否按环境光变暗；如果白天仍偏暗或偏亮，
  调 gamma 值即可（越小越亮）。

## 第六轮：铁、金背包也换成了雕刻网格模型

流程和皮革完全一样（完整原始网格不减面 → `.obj` 坐标 +0.5 → `.mtl` 用 `#base` 变量 → 贴图 1024×1024 → 法线
贴图按 LabPBR 转换 → 模型 JSON 带 `flip_v: true`、`emissive_ambient: false`），`display` 沿用皮革那套。先用
Blender 渲了正面确认：两个模型的"正面"（口袋/扣具那一侧）也在 -Y 方向，和皮革一致，所以旋转数值不用改。

**两个模型和皮革不一样的地方**：
- 面数：铁 20,240、金 19,401（皮革 16,178）；高度/厚度比皮革大（皮革高 0.81 厚 0.54；铁 0.88/0.63；金 0.97/0.72，宽度
  都是 1.0），档位越高包越大，我没有把它们缩放成同样大小。手持、图标会比皮革略大一点，背上也略高。
- 为了让背上贴身位置对三档都有效，导出时把每个模型沿 z 平移，使它们**背面（贴着人的那一面）都落在同一位置**
  （z=0.238，和皮革一致），这样 `BackpackBackLayer` 里 z=-0.316 的贴合距离对铁、金同样成立，不用给每档单独算。
  代价是更厚的模型整体中心稍微偏离方块中心（铁约 0.04、金约 0.09 个方块），对手持/图标的影响很小。
- **开放边（裂缝）比皮革多**：按之前同样的方法统计，皮革 16 条，铁 122 条，金 325 条。这是原始 GLB 本身的问题（没做
  减面），不是我们引入的，可能在个别角度看到细小透光，金更明显；如果你实测发现，再看是用补面还是别的办法处理。
- 亮度：之前只有皮革贴图偏暗，铁的贴图亮度约为参考图的 0.76 倍，只做了轻微提亮（gamma 0.89）；金的贴图本来就和
  参考图一样亮甚至更亮，**没有调整**（不是照搬皮革的 0.62）。这个对比是拿参考图中间区域和贴图按面积加权的平均亮度
  粗略比的，误差比较大，别当精确值。关闭全亮之后实际效果还要看游戏光照，需要你实测。
- 每个模型的未提亮原图都保留为 `obj_export/<tier>_backpack_diffuse_original.png`。

**Git LFS**：`design/**/*.obj` 已经走 LFS（单个文件近 2MB 的顶点数据，没法 review）；`src/main/resources` 里随 mod 打包
的 `.obj` 仍是普通文件（否则没装 git-lfs 的构建环境会把 LFS 指针文本打进 jar，模型就坏了）。注意"obj 是二进制"这个说法
不准确——它是文本格式，只是又大又没法人工看，所以才值得走 LFS。`.glb` 才是真二进制，目前没有走 LFS（没要求），建议也加。

**目前状态**：皮革、铁、金三档是雕刻网格模型；钻石、下界合金还是立方体程序模型（只有参考图）。

## 第七轮：钻石、下界合金背包也换成了雕刻网格模型（五档全部完成）

流程同铁、金（完整原始网格、`.obj` 坐标 +0.5、背面统一对齐到 z=0.238、`.mtl` 用 `#base`、`flip_v`、关闭全亮、贴图 1024、法线
贴图 LabPBR 转换），**有一处和之前不同：这两个 GLB 的朝向转了 90°。**

- 铁、金、皮革的"正面"在 Blender 的 -Y 方向；钻石、下界合金的包宽 1.0 在 Y 轴上（X 轴只有 0.65~0.70），渲染确认从 -Y
  看到的是侧面口袋，正面其实朝 +X。所以导出前先把网格绕垂直轴旋转了 -90°（+X → -Y），让正面朝向和前三档一致，
  `display` 里的旋转数值才能继续通用。
- 第一次尝试旋转时没生效：glTF 导入的物体默认是四元数旋转，直接改 `rotation_euler` 不起作用，包围盒没变。改成直接在
  世界坐标下对网格数据做变换，包围盒（x ±0.50、y 深度 0.70/0.65）和渲染图都确认转对了。
- **下界合金的"正面"不确定**：这个模型几乎左右镜像对称（正反两面都有翻盖+扣具+口袋，各高度的 X 范围几乎一样），没法从几何形状
  判断哪边是正面；钻石能判断（口袋和翻盖扣具在 +X 一侧，背面是平的）。下界合金我按和钻石同样的 +X 当正面，如果你实测发现
  显示的是"另一面"（比如口袋/扣具位置和参考图对不上），告诉我，把旋转角度换成 +90° 即可。
- 钻石的翻盖是向后包过去的（背面最外缘是翻盖，不是主体），对齐"背面"时按最外缘算，所以主体背面离人体背部会多出约 0.05 个
  方块（不到 1 像素）的缝；下界合金没有这个问题。
- 面数：钻石 20,227、下界合金 20,265；原始开放边（可能的透光裂缝）钻石 169 条、下界合金 114 条（皮革 16、铁 122、金 325），
  同样没处理。
- 亮度：钻石贴图本来就和参考图一样亮，没调整；下界合金本身是黑色系，只做了很轻的提亮（gamma 0.91）。同样是粗略估算。

**目前状态：五档全部是雕刻网格模型。** 旧的立方体程序模型（`design/backpack-redesign/`）和 `floating_backpack.json` 共享父模型
已经没有任何一档在用，保留作为设计历史。

## 第八轮：下界合金背包底部"补上"（口袋底部是空的）

你反馈下界合金背包从下往上看底部是空的、像会漏。排查（都是脚本测量，不是目测）：

- 先用 Blender 从下往上给整个模型发射射线，看第一个打到的面是正面还是背面：五档里"首个命中是背面（会透光）"的射线
  只有零星几条（下界合金 24/约 1 万），所以不是真的"洞"。
- 再看首个命中面的**高度**：下界合金底部是一圈贴地的边框（宽约 0.058），框里面最先打到的是离底部 0.22~0.26 高度的
  "天花板"——也就是下口袋是一个**没有底板的盒子**，只剩一圈框，从下面往上看是个凹进去的空腔。对比皮革/铁/金/钻石，
  底部都是平的（首个命中高度≈0），只有下界合金有这个问题。这就是你看到的"空"。（它不透光，但视觉上像漏了。）
- 补法：AI 网格的开放边散落在整个高度上，不是一条干净的洞边，不适合自动填洞，所以改为在开口下面加一块**盖板**：
  一个向下的平面（四边各比开口大约 0.03，埋进边框里不会露缝），高度比边框底面高 0.03（凹进约 0.4 像素，看不出来），
  UV 取贴图里和口袋正面一样的"金色斑点"区域，这样底面和口袋外观连贯。Blender 脚本保存在
  `design/demo/tools/netherite_bottom_cap.py`（含贴图导出和补盖，之后要重新导出可以直接用）。
- 一个小坑：脚本里我最初用盖板法线 z 判断是否翻转，但新建面的法线没算过恒为 0，判断无效；所以导出后直接读 `.obj` 里
  三角形的绕序确认是朝下的（法线 y=-0.27）。
- 验证：对最终 `.obj` 在开口范围里发射 1,681 条射线，**全部**打在盖板上，没有一条打到旧空腔或背面；带背面剔除的
  渲染图里，口袋底部是一整块金色斑点的平板。面数 20,265 → 20,267。

## 第九轮：贴图预算（010）——图集从 4096×4096 降到 2048×1024

**问题**：009 之后实测日志显示共用方块图集 `blocks.png-atlas` 涨到了 4096×4096，估算显存从约 5.6MB 涨到约 89MB，影响所有玩家的所有方块贴图。

**原因（实测）**：图集会扫描 `textures/item/` 下的**全部** PNG，所以 5 张法线贴图 `_n.png` 也被拼了进去，一共 **10 张** 1024² 贴图才撑出 4096×4096（之前文档里"法线不进图集"是错的）。详细矩阵见 `specs/010-backpack-texture-budget/research.md`。

**怎么改的**：
1. 新增 `src/main/resources/assets/minecraft/atlases/blocks.json`，用图集的 `filter` 源把 `mcfloatingbackpack:item/*_n` 从共用图集里剔除（光影包按"精灵名 + `_n`"自己读取，预期不受影响，**需要光影包实测确认**）。
2. 基础色与法线贴图都从 GLB 的 2048 原图重新处理成 **512×512**：基础色 `BOX` 缩放 → 轻锐化 → 各档原有 gamma；法线 `BOX` 缩放 → 重新归一化 → LabPBR 转换。
3. 结果（实测）：图集 **2048×1024**，估算显存约 11.2MB；亮度（按网格 UV 面积加权）与旧 1024 版偏差 ≤ ±2.9%。

**处理流程（可重复）**：
```bash
# 1. 从 GLB 取 2048 原图（Blender 无头，输出到 design/demo/work/，已 gitignore）
/Applications/Blender.app/Contents/MacOS/Blender --background --factory-startup --python design/demo/tools/extract_textures.py
# 2. 生成 512 贴图并覆盖到 src/main/resources（不加 --install 则只生成不覆盖；尺寸可改成 640）
python3 design/demo/tools/build_textures.py 512 --install
# 3. 度量图集尺寸，超过 2048 非零退出（会起一次客户端，约 30~60 秒）
design/demo/tools/check_atlas_budget.sh
# 4. 比较亮度偏差，超过 ±10% 非零退出
python3 design/demo/tools/check_brightness.py
```

**维护规则**：新增或替换背包贴图之前和之后，都要跑一遍第 3 步。`_n` 的文件名必须是 `<基础色名>_n.png`，否则既不会被图集过滤规则匹配，光影包也找不到。

**之前结论的修订**：
- 上面"贴图分辨率：1024×1024 是最终选择"已被取代：1024 会让图集回到 4096×2048 以上，超出 010 确认的 2048×2048 上限。
- "512 看起来糊"的结论需要修订：当时的反馈同时叠加了 `flip_v` 的 UV bug，不能证明 512 本身不行；离线对比里 512 的"盒式缩放 + 轻锐化"边缘保留度接近现状 1024。**但 512 在 UV 正确的情况下还没有在游戏里看过，清晰度必须在游戏里确认**（010 的 T011/T012）。
- 旧的 1024 版贴图留在 `design/demo/obj_export/<tier>_backpack_diffuse.png`，作为亮度对比的基准；新版同时存了 `*_512.png` 留档。

**一个踩过的坑**：度量脚本用 `timeout` 结束 `./gradlew runClient` 时，只会杀掉 gradle 外壳，**Minecraft 客户端的 JVM 会留着**。脚本现在会按客户端特有的启动参数 `fml.modFolders=mcfloatingbackpack` 清理它。以后在命令行里检查残留进程，也用这个参数 `pgrep -f 'fml.modFolders=mcfloatingbackpack'`，不要用 `pgrep -f "A\|B"`（`pgrep` 是扩展正则，`\|` 是字面竖线，检查会无效）。

## 第十轮：开发期光影包，以及铁背包手持时的竖缝

### 开发期怎么开光影包


- 版本选择的依据：Modrinth 上 Iris `1.8.12+1.21.1-neoforge`（正式版）声明的必需依赖就是 Sodium `mc1.21.1-0.6.13-neoforge`。

- **还没做的**：我无法从命令行看到游戏画面，所以"背包表面有没有法线凹凸"这件事**没有验证**，要你进游戏看（光影包里 PBR 设置要开 Normal/“PBR” 相关选项，Complementary 默认会读 LabPBR 法线）。
- 工作区里的 `run/` 被 gitignore，光影包 zip 和 `iris.properties` 不会进仓库；换机器重跑第一步即可。
- Mac 注意：Mac 的 OpenGL 上限是 4.1，部分光影包的高级特效会被降级或关闭，这不影响判断法线是否生效。

### 铁背包手持时的竖缝

**现象**：第一人称手持铁背包时，背包上有一条竖线能看到背后的水面。

**结论：是模型本身的问题，且修起来不麻烦，已修。**

- **原因**：AI 生成的铁背包网格在 x≈0.24–0.28、y≈0.46–0.69、z≈0.31–0.42 处，两块曲面之间留了一条约 0.02–0.04 宽、0.2 高的缝。Minecraft 会剔除背面，所以从模型正面（−z 侧）看过去缝里没有任何可见面，直接看到背后的场景。这就是 009 记录的"铁背包有 122 条开放边"里的一段。
- **怎么确认的（不是猜）**：用离线栅格化脚本，对铁背包网格**只画正面朝向的三角形**（和游戏一致），从 24 个偏航角 × 5 个俯仰角共 120 个方向看，找图形内部没有被覆盖的"洞"。修之前，正面一侧偏航 180°–225°（含斜向）、俯仰 −30°～30° 的每个方向都有一条 2–4 像素宽、20–35 像素高（0.13–0.2 个方块高）的竖缝，位置和上面的开放边簇吻合；修之后 120 个方向都没有竖缝。
- **为什么不做"按开放边界三角化"**：这个网格有 544 条被 3 个以上面共用的边（非流形），开放边界在缝上断成好几段，不成一个闭环，拓扑方法不可靠。改成按几何补：在缝里（比前面那层更靠里）放一片薄板，正反两面各一层，所有顶点共用一个 UV 点（取离板中心最近的网格顶点），所以是纯色，不会因跨 UV 岛而出现彩色拉伸。
- **第一次补得不够宽**：最初的板只覆盖 x∈[0.236, 0.284]，修完后偏航 225° 的斜向视角仍有缝（射线从缝的侧面穿过板所在深度，x 偏到 0.30 左右）。射线检查显示它只命中最远处的背面三角形，说明直接穿透整个模型。把板加宽到 x∈[0.226, 0.340] 后，120 个方向全部没有竖缝。
- **会不会补出新问题**：板放在 z=0.345，位于前层（z≈0.309）与后层（z≈0.34–0.42）之间，从正面看被前层挡住、只在缝里露出。验证了 120 个方向，修前修后的**外轮廓像素差为 0**，说明板没有凸出模型。
- **改动**：`models/item/iron_backpack.obj` 末尾新增薄板（见下面"第二轮"，现共 5 块）；设计目录 `design/demo/obj_export/iron_backpack.obj` 同步；补丁脚本是 `design/demo/tools/patch_iron_slit.py`（幂等，已打过补丁会跳过；要重打先从 git 取回未打补丁的 OBJ）。
- **没有改的**：铁背包其余的开放边、其他四档的开放边（金 325、钻石 169、下界合金 114、皮革 16）。它们要么在背面/内侧看不到，要么还没有人在游戏里发现可见的缝；如果之后哪一档也出现类似竖缝，用同样办法（栅格化找洞 → 在缝里放一片薄板）处理。
- **第一轮的结果**：用户在游戏里确认，上方那条竖线补好了，但**下方还漏一点点，能看到背后的草地**。

### 第二轮（补错了地方）与第三轮（按真实手持画面补）

**第二轮的错误**：我推断手持时相机看到模型 −x 一侧，就去补 ±x 两侧小口袋上的缝和两条水平细缝，并用"正对着看"的栅格化确认洞数下降。用户进游戏后反馈**画面完全没变化**。原因：手持有 25° 滚转和透视，真正穿透的光线不是正对着看的方向；而且那几块板补的不是用户看到的那条缝。"各个方向的洞数变少了"和"用户在游戏里看到的缝补好了"不是同一件事。

**第三轮的做法——先重建出和截图一样的画面再动手**：
- 新写了 `design/demo/tools/firstperson_holes.py`，按 `ItemInHandRenderer` 的链条重建第一人称画面：相机在原点朝 −z、70° 垂直 FOV；右手 `translate(0.56, −0.52, −0.72)`；再接显示变换 `firstperson_righthand`（平移 ×0.0625 → `rotationXYZ` → 缩放）；只画正面三角形。
- **先验证重建是否可信**：对修补前的铁背包重建，右下角出现一条斜缝，起点、走向、落到屏幕下沿的位置都和用户截图一致（把截图缩到 864 宽后，缝的起点在 (788,442)，重建里在 (800,440)，终点都落在屏幕下沿 x≈755–765，相差十来个像素，走向一致）。修补前该工具在标准视角下数出 620 个洞像素。
- **真正的缝**：从洞里发一条射线看它穿过哪里——它穿过的是**第一轮那条竖缝**（x 0.24–0.35、y 0.44–0.62、z 0.30–0.43），不是侧面口袋。第一轮的 z=0.345 板 y 下限是 0.462，而斜着看的光线从板的**下缘以下**漏过去，所以用户看到的是"板下面还漏一点草地"。
- **补法**：工具对每个洞在其后面（比洞边缘最深的蒙皮再靠里 0.004）生成一块贴合视线方向的斜板，并把标准视角加上 ±6°/±10° 的 6 组晃动都纳入（手握时有轻微晃动）。迭代到所有视角洞数为 0，一共 5 块斜板，写进补丁脚本的 `HAND_VIEW_PLATES`。
