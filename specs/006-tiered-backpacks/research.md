# Research: 分级浮动背包

## 1. 五个物品，而不是一个物品加等级组件

- **Decision**: 五个物品 ID：`leather_floating_backpack`（已有）、`iron_floating_backpack`、`gold_floating_backpack`、`diamond_floating_backpack`、`netherite_floating_backpack`。共用 `FloatingBackpackItem`，用 `BackpackTier` 区分容量与贴图。
- **Rationale**: 配方、创造栏、JEI、模型 JSON 都按物品 ID 工作。规格要求五件可区分的物品。
- **Alternatives considered**: 单一 ID + tier 组件。升级配方和模型覆盖更绕，创造栏也不好各给一个图标。

## 2. 容量存在物品上，列表按等级补齐

- **Decision**: `BackpackInventory` 不再使用固定 `SIZE = 36`。`MAX_SIZE = 108`。每个实例的格子数等于其 `BackpackTier`。读组件时不足补空、超出截断。
- **Rationale**: 现有 `BackpackContents` 已是可变列表。升级只要把 36 格拷到 54 格物品上并补空即可，不必换组件类型。
- **Alternatives considered**: 五种组件。重复编解码，没有收益。

## 3. 锻造台升级，附加槽只消耗 1 个物品

- **Decision**: 自定义 `SmithingRecipe`（模板槽必须为空）。基底是恰好低一级背包，附加物是 **1 个**物品，结果是高一级背包。`assemble` 把基底的组件拷到结果上，再按新容量补空格。消耗按原版锻造台规则：基底与附加各减 1。
- **材料**（相对规格里的「4 锭 / 2 钻石」作了收束，因为锻造台一次只扣附加槽 1 个，不为扣 4 个去改锻造台界面）：

  | 升级 | 附加物 |
  | --- | --- |
  | 皮革 → 铁 | 铁块 ×1 |
  | 铁 → 金 | 金块 ×1 |
  | 金 → 钻石 | 钻石 ×1 |
  | 钻石 → 下界合金 | 下界合金锭 ×1 |

- **Rationale**: 规格要求锻造台而不是工作台。原版锻造结果槽取出时每个输入槽只减 1。用块代替多锭，仍是生存可做的成本，且不需要 mixin。
- **Alternatives considered**: 工作台摆 4 锭 + 背包，能精确对齐「4 锭」但不是锻造台。锻造模板物品每级消耗一张，规格没要求模板。mixin 锻造台以扣多个物品，过重。

## 4. 面板行数与滚动

- **Decision**: 列固定 9。行数 = 容量 / 9（4、6、8、10、12）。面板高于当前 GUI 可用高度时，格子区可用滚轮滚动，拖动条仍移动整个面板。滚动偏移只在客户端。
- **Rationale**: 12×18 像素再加标题，在 GUI 比例 4 的 1080p 上会超出屏幕。规格要求每一格仍能点到。
- **Alternatives considered**: 分页按钮。多一次操作，和「一块面板」不一致。整体缩小槽位。命中变小，不好点。

## 5. 外观：共用低多边形模型 + 五张 32×32 贴图

> **【009 修订】本节是 006 当时的决定，现已被取代。** 现状：五个等级是**五个各自独立**的雕刻网格模型（`neoforge:obj` 加载器，每档一份 OBJ/MTL），**没有肩带**，贴图是每档一张 **1024×1024**（外加法线贴图），背部直接渲染物品自己的烘焙模型（不再画"同一轮廓"）。下面原文保留以便追溯当时为什么选立方体元素；当时"不加载 OBJ，不进高模"的判断，被后来拿到的 AI 网格素材推翻了。取代的理由与证据见 [009 research.md](../009-sculpted-mesh-backpack-models/research.md)。

- **Decision**: 一个物品模型 JSON（包身、翻盖、两条肩带、扣具，若干方块元素）。五个等级各一张 **32×32** 物品贴图和一张背部用同图（或同图拷贝到 `textures/entity`）。物品栏、手持走该 JSON 模型；背部图层按等级贴图画同一轮廓，删除现在的单位立方体。
- **配色**: 皮革棕、铁灰、金边、钻石青、下界合金近黑带紫边。结构相同，便于认出是同一系列。
- **生产**: 生图出正面旅行背包概念 → 收成 32×32 透明像素图。需要时用 Blender 只定长宽比例，再把方块元素写进 JSON。不加载 OBJ，不进高模。
- **Rationale**: 原版物品模型只吃 JSON 元素。高模 Blender 导出不能直接当 MC 物品。32×32 满足规格下限，又仍是像素 UI。
- **Alternatives considered**: 继续 `item/generated` 平面图标。手持是一张纸片，不满足「手持能看出背包」。每级一套完全不同的主题模型。工期大，也不符合「同一结构的材质变体」。

## 6. 装备后不要画成皮革胸甲

- **Decision**: `FloatingBackpackItem` 不再继承 `ArmorItem`。用原版可装备组件占用胸甲槽，不提供人形护甲贴图。潜行使用仍装备到胸甲；非潜行使用仍打开面板。背部只由 `BackpackBackLayer` 绘制。
- **Rationale**: 继承皮革胸甲会在身上画出皮甲；若改成铁/金/钻石材料，会画出对应胸甲，盖住背包。五个等级不应变成五套盔甲。
- **Alternatives considered**: 透明护甲贴图仍走 `ArmorItem`。护甲模型的袖子和分层仍可能闪一下，而且材料与等级语义冲突。

## 7. 网络

- **Decision**: 协议版本改为 `"3"`。全量同步与会话包的格子列表上限 108，实际长度等于该背包容量。点击槽位必须 `< 该物品容量`，否则拒绝。客户端视图大小跟随最近一次全量同步，不再写死 36。
- **Rationale**: 固定 36 的列表编解码无法表示 108 格。模组尚未对外发布，可以改版本。
- **Alternatives considered**: 始终发送 108 格。浪费带宽，也会把低级背包显示成空行。
