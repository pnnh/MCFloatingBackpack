# Feature Specification: 统一的"背着的背包"查找

**Feature Branch**: `032-worn-backpack`

**Created**: 2026-11-09

**Status**: Draft

**Input**: 用户描述："允许浮动背包放到 Curios（Adorned）和 Accessories（Blodhgarm）的后背槽位，放置后和放在玩家胸甲上效果一样，都认为是背在了身上。……按 B 打开和模型渲染都走同一套查找顺序，不用拦截第二只或第三只。"本 feature 是其中的第一步：把"背着的背包"从"胸甲槽"一处写死，改成一个有顺序的来源列表，**自己不引入任何第三方模组，玩家看到的行为与现在完全一致**，为 033（Curios）、034（Accessories）打地基。

## 背景与已确认的决策

现在"背在身上"只有一个来源：玩家的胸甲槽。

- **背上的模型**：`BackpackBackLayer` 只画胸甲槽里的那一只。
- **按 B 打开哪一只**：`BackpackRef.resolve` 按"主手 → 副手 → 胸甲 → 物品栏 0～35"找第一只；面板的所有服务端操作都先 `resolve`，自动拾取也走它（"按 B 会打开的那只"）。
- **引用怎样传输**：`BackpackRef` 是（来源序号，格子下标）。它在会话、打开请求、整份同步、点击、垃圾桶发送等包里传输，服务端收到后总是用 `resolve` 重新解析，不信任客户端的引用。

已确认的决策（来自用户，见 `docs/plan/worn-backpack-compat.md`，不重新讨论）：

1. **一套全局一致的查找顺序**：玩家胸甲 → Curios 后背槽 → Accessories 后背槽。按 B 打开与背上的模型渲染都走这一套。
2. **不拦截**第二只、第三只，**不数数、不去重**：同时放几只都允许，只取顺序里的第一只；背上最多画一只，不会出现多个模型重叠。
3. 按 B 的整体顺序变成：**主手 → 副手 → 背着的（上面顺序里的第一只）→ 物品栏 0～35**。手里拿着的背包仍然优先于背着的（现状如此）。排在后面的背包是槽里的普通物品：不画，按 B 也不会打开它（拿掉前面的才轮到它）。
4. 尊重第三方槽位的"隐藏渲染"开关：第一只所在的槽被玩家设为不渲染，就不画，但仍算"背着的"，按 B 照常打开；装饰栈不看，只看真实栈。（这两条在 033/034 实现，**本 feature 要为它们留出口子**。）
5. `modLevels`（020）对这两个模组的含义：GENERIC / OFF 时我们为它们写的代码不运行，所以它们槽位里的背包不算"背着的"。

由我按已有惯例设计的部分（可在 plan 阶段微调）：

- **来源**：一个来源回答四个问题——这个玩家（服务端或客户端）身上，这个来源里有没有背包、是哪一只；能不能读写它的栈；它所在的槽是否被设为不渲染；怎样用（来源序号，格子下标）指回它。本 feature 只有**一个来源：玩家胸甲槽**。
- **来源列表有固定顺序**，加新来源不会改变已有来源的序号；033、034 把各自的来源作为兼容类加进来，排在胸甲后面。
- **来源是否生效在查询时判断**（受 `modLevels` 控制），不是在注册时判断，这样配置改了立刻生效。
- 来源与列表**不依赖 Minecraft 类**的那部分（顺序、第一只的选取、隐藏渲染的处理）写成可以单元测试的纯逻辑，用假来源测试。

## Out of Scope（本阶段不做）

- Curios、Accessories 的任何代码、数据、标签、依赖、语言键、开发期模组（033、034）。
- 渲染抑制（压住第三方模组自己的渲染器）、读取第三方槽的隐藏渲染开关（033、034）；本 feature 只在来源的接口里留出"该槽是否隐藏渲染"这个问题，胸甲槽的答案恒为"不隐藏"。
- 网络协议改动（协议版本仍是 16）、新贴图、新配方、新设置项、新语言键。
- 去重与计数；拦截第二只、第三只；改 Shift+右键换到胸甲槽的行为（`FloatingBackpackItem` 不动）。

## 已查证的事实（读本仓库源码；规格要尊重，不要重新猜）

- `BackpackRef.Source` 现在是 `MAIN_HAND`、`OFF_HAND`、`CHEST`、`INVENTORY`；`resolve` 的顺序、`getStack`/`setStack`/`stillValid`/`loadInventory`/`saveInventory` 都按它分支。
- 引用以（来源序号 `ordinal()`，格子下标）在这些地方传输：`BackpackSessionPayload`、`BackpackOpenRequestPayload`、`BackpackFullSyncPayload`、`BackpackClickPayload`（客户端声称的引用，服务端只在与 `resolve` 的结果来源与下标一致时才采用）。`BackpackQuickTransferPayload` 对来源做 `switch`（映射到 `QuickTransferRequest.Holder`）；`FloatingPanelEvents` 用 `ordinal() + ":" + 下标` 当引用的键。（`BackpackTrashSendPayload` 里的 `Source` 是**另一个**枚举——垃圾桶发送的取物来源，与 `BackpackRef.Source` 无关。）
- 服务端调用 `BackpackRef.resolve` 的有 11 个包处理，客户端 3 处（`FloatingPanelEvents`、`FloatingPanelInput`）；自动拾取也走它。
- `BackpackBackLayer` 在客户端对**任意玩家实体**读 `getItemBySlot(CHEST)`（包括别的玩家）。
- 现有测试里只有 `BackpackRefTest` 直接测 `BackpackRef`。
- `BackpackRef.saveInventory` 里有一段 026 遗留的注释（"count the revision up and keep the registry's shadow copy current"），登记表已经不存在了，注释已过时。

## 尚未验证（plan 阶段先查证；验证前不得声称已满足）

- 来源列表放在哪、怎样让**客户端和服务端各自算出同一个结果**（两端都不能依赖对方）。
- `Source` 枚举与来源列表的关系：序号怎样与槽位一起编码，才能在 033/034 里指向"Curios 的 back 槽第 N 格"而不改协议；服务端对客户端引用的重新解析与校验在新结构下怎样保持"不信任客户端"。
- 渲染层在客户端对别的玩家取"第一只"的开销：每帧每个玩家调用一次，第三方来源接入后要保持便宜。
- `BackpackQuickTransferPayload.holderOf`（以及它映射到的 `QuickTransferRequest.Holder`）、`FloatingPanelEvents` 的引用键，在来源可扩展之后是否要改。
- `BackpackRefTest` 里哪些断言依赖顺序；改动后它们的含义要保持。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 行为完全不变 (Priority: P1)

**Independent Test**: 在 031 之后的版本与本 feature 完成后的版本上，对同一组操作比较结果：背包在胸甲槽、主手、副手、物品栏各种组合下，按 B 打开哪一只、背上画哪一只、自动拾取针对哪一只，全部相同。

**Acceptance Scenarios**:

1. **Given** 背包只在胸甲槽，**When** 按 B，**Then** 打开它；背上画它。
2. **Given** 背包在主手，同时胸甲槽里也有一只，**When** 按 B，**Then** 打开主手的那只（手里的优先）；背上画胸甲槽的那只。
3. **Given** 背包只在副手，**Then** 按 B 打开它；背上没有背包模型。
4. **Given** 背包在物品栏里（不在手上、不在胸甲槽），**Then** 按 B 打开物品栏里下标最小的那只；背上没有背包模型。
5. **Given** 物品栏里有两只、胸甲槽有一只，**Then** 按 B 打开胸甲槽的那只（背着的优先于物品栏）。
6. **Given** 打开面板后把胸甲槽里的背包摘下，**Then** 服务端不再认那个引用，面板按现状关闭或改指向新 `resolve` 的结果。
7. **Given** 自动拾取，**Then** 针对的是按 B 会打开的那只，与现状一致。
8. **Given** 别的玩家穿着背包，**Then** 在我的客户端上背着的模型照常显示，与现状一致。

---

### User Story 2 - 顺序规则被测试钉住 (Priority: P1)

**Independent Test**: 用假来源做单元测试：给定若干来源各自"有/无背包"，断言按 B 的结果顺序是"主手 → 副手 → 来源 1 → 来源 2 → … → 物品栏"，渲染取的是来源列表里的第一只。

**Acceptance Scenarios**:

1. **Given** 三个假来源 A、B、C 都有背包，**Then** "背着的第一只"是 A。
2. **Given** A 没有、B 和 C 有，**Then** 是 B。
3. **Given** 都没有，**Then** 没有背着的；按 B 回到物品栏顺序。
4. **Given** 来源 A 被判定为"不生效"（模拟 `modLevels` 为 GENERIC / OFF），**Then** 它被跳过，不出现在结果里。
5. **Given** 第一只所在的槽被设为"隐藏渲染"，**Then** 它仍然是"背着的第一只"（按 B 打开它），但渲染取不到可画的背包——**不会**改画后面的那只。
6. **Given** 手里有背包，**Then** 手里的永远优先于任何来源。
7. **Given** 同一个顺序，**Then** 无论在"服务端视角"还是"客户端视角"调用，结果相同。

---

### User Story 3 - 为 033/034 留好口子 (Priority: P2)

**Independent Test**: 读代码与测试：加一个新来源只需要实现来源接口并把它放进列表末尾；已有的序号、已有的网络包、已有的调用点都不用改。

**Acceptance Scenarios**:

1. **Given** 一个新的假来源加在列表末尾，**Then** 已有来源的序号不变，已有测试不变。
2. **Given** 引用指向新来源的某一格，**Then** 它能被编码进现有的（来源序号，格子下标）并被服务端重新解析，协议版本不变（仅用假来源在单元测试里验证编码与解析）。
3. **Given** 客户端声称的引用在服务端已经不是"背着的第一只"，**Then** 服务端按 `resolve` 的结果处理（与现状一致）。

---

### Edge Cases

- 玩家同时没有任何背包：`resolve` 返回空，与现状一致。
- 来源列表里某个来源在查询时抛异常或第三方模组被移除：该来源被当作"没有背包"，不影响其它来源（033/034 的兼容类要遵守；本 feature 的列表结构要允许这样处理）。
- 渲染层对每个玩家每帧取一次"第一只"；没有任何第三方来源时，开销与现在读一次胸甲槽相当。
- 死亡或观战玩家：现状如何就如何（不改）。
- 来源序号越界的引用（旧客户端、伪造）：按现状被拒绝或忽略。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: "背着的背包"由一个**有固定顺序的来源列表**决定；本 feature 的列表里**只有玩家胸甲槽一个来源**。
- **FR-002**: 提供一个统一的查询：给定一名玩家（服务端或客户端的实体），返回"背着的第一只"（来源、格子、栈、是否隐藏渲染），按列表顺序、跳过不生效的来源。
- **FR-003**: 背上的模型渲染使用 FR-002 的结果：只画"背着的第一只"，且该槽被设为隐藏渲染时不画（不改画后面的）；没有背着的就不画。与现状的差别仅在于取背包的方式。
- **FR-004**: `BackpackRef.resolve` 的顺序为：主手 → 副手 → FR-002 的结果 → 物品栏 0～35；手里的背包优先于背着的。
- **FR-005**: `BackpackRef` 的读写（取栈、写回、是否仍有效、加载与保存内容）对"某个来源里的某个格子"成立；来源序号是现有枚举值**加在末尾**扩展，已有序号不变；引用仍以（来源序号，格子下标）传输。
- **FR-006**: 服务端对客户端引用的处理不变：始终用 `resolve` 重新解析，只在客户端声称的引用与解析结果一致时才采用声称的那个。
- **FR-007**: 来源是否生效在**查询时**判断（以后由 `modLevels` 控制），不在注册时判断。
- **FR-008**: 来源接口留有"该槽是否被设为不渲染"的问题，胸甲槽恒为"否"；本 feature 不读任何第三方槽的开关。
- **FR-009**: 加入一个新来源只需实现来源接口并放进列表末尾：已有来源序号不变，已有网络包与调用点不用改；用假来源的单元测试证明这一点。
- **FR-010**: 来源列表的顺序、"第一只"的选取、跳过不生效来源、隐藏渲染的处理、手里优先，都是**不依赖 Minecraft 类的纯逻辑**，有单元测试。
- **FR-011**: 不新增网络包、不改网络协议（版本仍是 16）、不新增语言键、贴图、配方、设置项。
- **FR-012**: 修正 `BackpackRef.saveInventory` 里已经过时的、提到登记表的注释。
- **FR-013**: 玩家可见的行为与 031 完成后**完全一致**（见 User Story 1）。

### Key Entities

- **背着的来源（Worn Source）**：一个能回答"这名玩家身上这里有没有背包"的东西；有固定的顺序与序号。
- **背着的背包（Worn Backpack）**：来源 + 格子 + 栈 + 是否隐藏渲染。
- **背包引用（BackpackRef）**：指向手里、背着的某个来源的某个格子、或物品栏某一格的一只背包。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 031 之后与本 feature 之后，同一组操作（User Story 1 的 8 个场景）的结果 **100% 相同**。
- **SC-002**: 顺序规则（来源顺序、第一只、跳过不生效来源、隐藏渲染、手里优先）全部由单元测试覆盖，自动化测试全部通过。
- **SC-003**: 增加一个新来源不需要改任何已有网络包、已有调用点或已有测试（用假来源验证）。
- **SC-004**: 协议版本仍是 16；没有新增语言键、贴图、配方、设置项；图集仍是 2048×1024。
- **SC-005**: 渲染层每个玩家每帧只做一次"背着的第一只"查询，没有第三方来源时开销与现在读一次胸甲槽相当。

## Assumptions

- 033、034 会把 Curios 与 Accessories 的后背槽作为新来源加在胸甲之后；本 feature 不预设它们的内部细节，只保证接口足够。
- 来源接口需要能在客户端对任意玩家实体使用（渲染层读别的玩家）。
- `modLevels` 在查询时读取（现状的配置读取是热加载，020）。
- 现有只在服务端或只在客户端调用 `resolve` 的地方，行为不变。
