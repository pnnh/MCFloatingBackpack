# Feature Specification: 背包整理

**Feature Branch**: `047-backpack-sort`

**Created**: 2026-11-12

**Status**: Draft

**Input**: 用户（2026-11-12）：在背包标题栏放一个整理图标，点击把背包里的物品重新排序，相同物品自动堆叠；如果有分类扩展行，则优先堆叠到分类扩展行。

## Clarifications

### Session 2026-11-12

- Q: 主区域的物品按什么顺序排？ → A: **注册名顺序**（用户确认）：按 `命名空间:路径` 排，`minecraft` 排最前，其余模组按命名空间字母序，同一模组按物品 id 字母序；同一种物品再按数据组件的稳定写法排。只靠服务端就能算、与玩家语言无关、结果可预测。
- Q: 分类扩展行怎么处理？ → A: 沿用 035/038 已有的"放入背包"规则：**能放进某个可见分类行的物品优先进那一行**（多个同类行就一行一行填），放不下的再进主格子（背包档位自己的格子），**通用扩展行（038）只在最后兜底**（主格子满了才用）。
- Q: 整理范围？ → A: 只整理**主区域**（档位格子加可见的扩展行）。左、右、下三个工具区、被隐藏的行、光标上的物品、背包标签、垃圾桶都**不动**。

## 背景

背包有 36 到 108 格，加上扩展行最多 9 的倍数更多。东西一多就乱，同一种物品散在好几格没堆满。有了搜索（042～044）之后能找到东西，但没法一键整理。本 feature 在标题栏加一个整理图标：一次点击，服务端把主区域重新堆叠、排序、按分类行规则归位，并把结果同步给客户端。

## Out of Scope（本阶段不做）

- 其它排序依据（按类别分组、按数量、按创造模式标签页顺序）；玩家可选的排序方式与设置项；整理快捷键；自动整理（取放时自动排序）。
- 整理工具区、被隐藏的行、背包标签、垃圾桶；整理玩家物品栏或别的容器。
- 撤销按钮（有 030 的快照可以恢复；本 feature 只保证"不丢物品"，见 FR-005）。
- 搜索结果里的整理（搜索框打开时整理图标不显示，见 FR-008）。

## 已查证的事实（读本仓库源码；规格要尊重）

- 服务端是物品的唯一权威（宪法 II）：面板上所有改变背包内容的操作都发请求给服务端执行（如 `BackpackQuickTransferPayload`），服务端先解析并校验背包（`BackpackRef.resolve`、`stillValid`、`BackpackGate.acquireForPanel`），再改、再存、再把整个背包同步给客户端（`BackpackNetwork.sendFullSync`）；客户端不做乐观更新。
- 035 已经规定了"一个物品放进主区域去哪"：`ExtensionRules.targetSegments` 给出三段按顺序尝试的格子——先是它能放进的可见分类行的格子，再是档位自己的格子，最后是通用扩展行的格子；`QuickTransferLogic.StackOps` 是不依赖 Minecraft 类型的堆叠接口（`isEmpty/count/maxStack/sameKind/withCount`），`ItemStackTransferOps` 是它的生产实现（`sameKind` 即 `ItemStack.isSameItemSameComponents`）。
- 一个格子能不能放某物品由 `ExtensionRules.canPlace` 决定：档位格子什么都收，分类行格子只收匹配该类的（标签、食物或药水组件、背包标签），通用行什么都收；隐藏行的物品不在主区域里。
- 标题栏（042）从右往左是：关闭键（最小尺寸去掉）、快照键、放大镜；搜索框打开时整段变成搜索框，编号与这些按钮都不显示。`TitleBarLayout` 是纯算术，`hitsSnapshotButton` 等在 `FloatingPanelState`。
- 面板、网络协议号现在是 17（`versioned("17")`）；新增一个客户端发给服务端的请求要升协议号。
- 光标上拿着东西时，批量操作（快速转移）在服务端直接拒绝；本 feature 同样。

## 尚未验证（plan 阶段先查证；验证前不得声称已满足）

- 整理的纯逻辑放在不依赖 Minecraft 类型的泛型类里（沿用 `StackOps`），生产里用 `ItemStack`；"数据组件的稳定写法"用什么作排序键、是否真的稳定（同一物品每次顺序一致）。
- 数量超过堆叠上限的物品（别的模组或旧数据里可能有）怎么处理而不丢；背包格子的 `getSlotLimit` 与 `getMaxStackSize` 的关系。
- 标题栏再加一个按钮后，各宽度下（尤其 3 列、无关闭键）各元素的让位顺序与 `TitleBarLayoutTest` 的更新。
- 协议号升级的影响面：所有断言协议号为 17 的既有测试要同步改为新值（它们是"没有改协议"的历史断言，不是需求）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 一键整理：堆叠并排序 (Priority: P1)

玩家点标题栏的整理图标，背包主区域里：同一种物品（同物品同数据组件）合并堆叠到堆叠上限、凑不满的余量排在最后一堆；所有物品按注册名顺序从第一格起紧挨着排，空格都在末尾。

**Why this priority**: 这是整个 feature 的核心。

**Independent Test**: 背包里放散落的 3 堆圆石（10、20、40）、2 堆橡木原木、几个镐、一些面包，空格夹在中间：点整理，圆石变成 64+6，原木合并，所有物品从第一格起连续、按 `minecraft:` 的物品 id 字母序排，空格在末尾；再点一次结果不变（幂等）。

**Acceptance Scenarios**:

1. **Given** 主区域里同一种物品散在多格，**When** 点整理，**Then** 合并成尽量少的堆，每堆到堆叠上限，余量一堆在最后；物品总数不变。
2. **Given** 不同数据组件的同种物品（如不同附魔的书、不同药水），**Then** 不合并（`isSameItemSameComponents` 不同），各自成堆。
3. **Given** 没有分类扩展行，**Then** 全部物品按注册名顺序排在档位格子里，第一格起连续，空格在末尾。
4. **Given** 已经整理好的背包，**When** 再点整理，**Then** 内容与位置完全不变。
5. **Given** 不能堆叠的物品（上限 1，如工具、盔甲），**Then** 每件一格，按注册名排；同一物品的多件再按数据组件的稳定顺序排。

---

### User Story 2 - 优先进分类扩展行 (Priority: P1)

背包有分类扩展行（例如食物行、工具行）时，整理把能放进行里的物品放进行里：食物先填满食物行（行内同样堆叠、按注册名排），放不下的食物再去主格子；通用扩展行（038）最后兜底。

**Why this priority**: 用户明确要求；也是扩展行存在的意义。

**Independent Test**: 背包有一个食物行（9 格）和一个工具行，主区域散着面包、苹果、镐、圆石：点整理后食物行里是排好序的面包和苹果、工具行里是镐、圆石在主格子；主格子里再没有能进行的东西（除非行满）。

**Acceptance Scenarios**:

1. **Given** 有一个食物行且食物不超过 9 堆，**When** 整理，**Then** 所有食物堆在食物行里，按注册名排、从行首起连续，主格子里没有食物。
2. **Given** 食物多于一行能放的堆数，**Then** 食物行放满，其余食物按注册名顺序放进主格子（和其它物品一起按序排）。
3. **Given** 两个食物行，**Then** 先填第一个，满了再填第二个。
4. **Given** 有通用扩展行，**Then** 它只在主格子放满之后才被用（兜底），不会先被占满。
5. **Given** 物品能放进多个类别的行（如又是食物又被背包标签标成工具），**Then** 按行的先后顺序，放进第一个有空位的、匹配的行（与 035 的放入规则一致）。
6. **Given** 行里原有的物品现在已不匹配该行（比如拿走了决定类别的背包标签），**Then** 它被当作普通物品，放进主格子（不留在不匹配的行里）。

---

### User Story 3 - 标题栏的整理图标 (Priority: P1)

标题栏上有一个整理图标（放大镜左边），悬停提示"整理背包"；点击就整理。搜索框打开时它和放大镜、快照键一样不显示；面板最窄时仍可用。

**Why this priority**: 没有入口就没有功能。

**Independent Test**: 9 列、6 列、3 列（最小，无关闭键）下标题栏截图：整理图标都在，不挡编号、放大镜、快照键、关闭键；点击有效；悬停有提示；开搜索框时消失。

**Acceptance Scenarios**:

1. **Given** 面板打开，**Then** 标题栏右侧从右往左依次是：关闭键（最小尺寸无）、快照键、放大镜、**整理图标**；编号在它们左边。
2. **Given** 标题栏太窄放不下全部，**Then** 先让位的是快照键，再是编号的空间；放大镜与整理图标一直在。
3. **Given** 悬停整理图标，**Then** 弹出 tooltip"整理背包"（中英文）。
4. **Given** 光标上拿着物品，**When** 点整理，**Then** 不发请求、没有变化。
5. **Given** 搜索框打开，**Then** 整理图标不显示（整个标题栏右段是搜索框）。

---

### User Story 4 - 不丢东西、不动不该动的 (Priority: P1)

整理前后物品总数逐种不变；工具区、隐藏行、光标、标签、垃圾桶不变；任何异常（找不到合法位置、数据不一致）时整理整体放弃，背包保持原样，并有日志。

**Why this priority**: 宪法 II 的核心：服务端改背包必须守恒。

**Independent Test**: 单元测试里随机生成背包内容与行配置，整理后断言：每种物品总数不变、没有格子超过堆叠上限、行格子里只有匹配的物品、行与档位格子的位置规则成立；构造"放不下"的情形，断言返回"不整理"且内容不变。

**Acceptance Scenarios**:

1. **Given** 任意背包内容，**When** 整理，**Then** 每种物品（同物品同组件）的总数与整理前相等，没有物品凭空出现或消失。
2. **Given** 工具区有物品、隐藏行有物品、背包有标签、垃圾桶里有物品，**When** 整理，**Then** 它们完全不变。
3. **Given** 整理需要的位置不够（极端：行里有不匹配的旧物品而档位格子已满），**Then** 整个整理被放弃，背包内容不变，不报错、不崩溃，服务端记一条日志。
4. **Given** 背包不再是玩家的有效背包（被丢掉、被别人拿走、会话过期），**Then** 请求被拒绝并走原有的"会话失效"路径，不改任何东西。
5. **Given** 整理刚完成，**Then** 客户端收到完整同步，面板显示新的内容；选区被清空。

---

### Edge Cases

- **满背包**：每格都是不同物品时整理只是重新排序，位置变化但没有丢失。
- **超过堆叠上限的旧堆**：按物品的上限重新拆分，总数不变。
- **同种物品跨行与档位格子**：能进行的先进行，行满后的余量进档位格子，之后档位格子里再出现同种堆也只在这一次整理里合并完成。
- **空背包**：整理不做任何事（也不发无意义的存档）。
- **多人**：只改请求者自己的、当前打开的那只背包；服务端以自己解析的背包为准，不信任客户端。
- **连点**：每次点击一个请求，服务端串行处理；结果幂等，连点多次与点一次相同。
- **面板挂在原版界面、创造物品栏界面、箱子界面上**：整理图标同样可用；打开着的容器不受影响。
- **扩展行在整理过程中变化**：服务端以请求到达时的行配置为准，客户端随后收到完整同步。

## Requirements *(mandatory)*

### Functional Requirements

**入口**

- **FR-001**: 标题栏 MUST 有一个整理图标，放在放大镜左边（从右往左：关闭键、快照键、放大镜、整理图标）；用代码画（`fill`），不新增贴图；悬停 MUST 有 tooltip（中英文语言键）；点击 MUST 向服务端发一个整理请求。
- **FR-002**: 标题栏让位顺序 MUST 是：快照键先让位、编号的空间其次；放大镜与整理图标 MUST 始终显示（包括 3 列无关闭键的最小尺寸），且各元素不重叠、不越界。
- **FR-003**: 光标上拿着物品时点整理 MUST NOT 发请求；服务端收到请求时若光标（原版携带栈或面板自己的光标栈）非空 MUST 拒绝。

**整理规则（服务端）**

- **FR-004**: 服务端 MUST 只整理主区域（档位格子加可见行的格子）：
  1. 把所有非空堆按"同物品同数据组件"（`isSameItemSameComponents`）合并，每种合并后拆成尽量少的堆：满堆（物品的堆叠上限）在前，余量堆在最后；
  2. 把所有堆按注册名顺序排序：`minecraft` 命名空间最前，其余命名空间字母序，同命名空间按路径字母序；同一种物品（同一注册名）再按数据组件的稳定写法排序，同组件的堆里满堆在前、余量堆在后；
  3. 清空主区域，再按顺序逐堆放入：**先**放进它能放进的可见分类行的格子（一行一行填，每行从行首起第一个空格），**再**放进档位格子（从第一格起第一个空格），**最后**放进通用扩展行的格子；每堆整堆放在一个格子里，不再拆分；
  4. 空格留在各段的末尾。
- **FR-005**: 整理 MUST 守恒：每种物品（同物品同组件）整理后的总数与整理前相等；任何格子 MUST NOT 超过该物品的堆叠上限，行格子 MUST 只含匹配该行的物品。整理放不下某一堆（没有合法位置）时 MUST **整体放弃**：主区域内容保持原样，记一条服务端日志；MUST NOT 部分整理。
- **FR-006**: 整理 MUST NOT 改变：三个工具区、被隐藏的行、光标上的物品、背包标签、垃圾桶内容与拾取黑名单、背包的档位与行配置。
- **FR-007**: 整理 MUST 幂等：对已整理好的背包再整理，内容与位置不变。

**客户端行为**

- **FR-008**: 搜索框打开时整理图标 MUST NOT 显示（与放大镜、快照键一致：整个右段是搜索框）；整理完成后客户端 MUST 清空选区；MUST NOT 做乐观更新（以服务端的完整同步为准）。

**协议与范围**

- **FR-009**: 服务端 MUST 与其它改背包的请求走同一套校验：解析玩家的有效背包、`stillValid`、`BackpackGate.acquireForPanel`；改完 MUST 存回并发完整同步；失败 MUST 走原有的"会话失效"路径。
- **FR-010**: MUST 新增一个客户端到服务端的请求包（无参数）并把协议号从 17 升到 18；MUST NOT 新增服务端到客户端的包；MUST NOT 新增配置项或依赖；011～046 的行为与测试不变（断言协议号的历史测试同步改为 18）。
- **FR-011**: 整理的纯逻辑 MUST 写成不依赖 Minecraft 类型的泛型类并有单元测试：合并与拆分、排序键、分类行优先与兜底、守恒、放不下时整体放弃、幂等、行里不匹配的旧物品、多行同类、通用行兜底；渲染与接线用源码文本检查覆盖。
- **FR-012**: 文档 MUST 更新：`README.md`/`README_CN.md`、`docs/plan` 的相关说明（分类扩展文档里"搜索与整理单独做"的整理部分改为已做）、本 feature 的 `DELIVERY.md`（中文）。

### Key Entities *(include if feature involves data)*

- **整理请求**：客户端到服务端、无参数；服务端以自己解析的背包为准。
- **种类（kind）**：同物品同数据组件的堆视为同一种；总数按种类累计。
- **排序键**：`(命名空间是否 minecraft, 命名空间, 路径, 数据组件写法)`；同键的堆里满堆在前。
- **放置段**：沿用 035 的三段：匹配的可见分类行 → 档位格子 → 通用扩展行。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 随机生成的 1000 组背包内容与行配置（含无行、单行、同类多行、通用行、满背包、极大堆叠数）上，整理后**物品总数逐种不变、无格子超上限、行内只有匹配物品**的断言 **1000 次全部成立**，且再整理一次结果不变（幂等）。
- **SC-002**: US1 与 US2 的独立测试场景（散堆圆石、食物行与工具行）在游戏里的结果与规格逐条一致（容器截图 + `/data get` 核对格子内容）。
- **SC-003**: 工具区、隐藏行、光标、标签、垃圾桶在整理前后**逐项不变**（单元测试 + 游戏里 `/data` 对照）。
- **SC-004**: 标题栏在 3 列（无关闭键）、4 列、6 列、9 列下**整理图标都显示、元素互不重叠**（`TitleBarLayoutTest` 的算术断言 + 容器截图）。
- **SC-005**: 一次整理从点击到面板更新完成，在 108 格背包上**无可见停顿**（容器里不可信，记"未度量"或粗测）；服务端处理一次整理的耗时（单元测试粗略计时，108 格 + 行）在开发机上**小于 5 毫秒量级**。
- **SC-006**: 协议号升到 18，新增的只有一个客户端到服务端的包；`./gradlew compileJava test` 通过；`DependencyRulesTest` 照常通过；011～046 的测试除协议号断言外不改而通过。

## Assumptions

- "注册名顺序"里"数据组件的稳定写法"取该堆组件补丁的稳定字符串形式；只要求同一台机器同一版本里每次一致，不要求跨版本不变。
- 整理发生时玩家不在乎主区域各格原来的位置（用户的原话是"重新排序"）。
- 玩家的物品栏、箱子等其它容器不是整理对象；整理图标只在背包面板上。
- 整理需要的"能不能放进某行"完全沿用 035 的 `CategoryMatcher` 与 `ItemCategoryMatcher`（标签、食物与药水组件、背包标签），不另写规则。
- 行里原有的、现在已不匹配该行的物品当作普通物品放进档位格子；若档位格子也放不下，整个整理放弃（极端情形，见 FR-005）。
