# Feature Specification: 服务端库存与面板内取放

**Feature Branch**: `002-server-inventory`

**Created**: 2026-10-23

**Status**: Draft

**Input**: User description: "依据 docs/MCFloatingBackpack.md 的 M2：为浮动背包增加服务端权威库存、网络同步，以及面板格子内的取放操作。不包含与原版物品栏/箱子界面之间的互拖（留给 M3）。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 背包格子有真实物品并跨会话保留 (Priority: P1)

玩家打开浮动面板后，能看到背包里真实的物品图标与数量（不再是永远空的装饰槽）。退出世界再进入、或重新上线后，背包内容与离开前一致。内容由服务端保存，不能只存在于本机画面。

**Why this priority**: 没有权威库存与同步，后续一切点击都是假交互。

**Independent Test**: 用开发用填充手段放入若干物品后，重进世界，面板中物品与数量不变；在专用服务器上只装本模组时，换客户端重进仍保留（若本阶段以单人为主，至少验证单人存档保留）。

**Acceptance Scenarios**:

1. **Given** 浮动背包中已有物品，**When** 玩家保存并退出世界后再次进入，**Then** 打开面板看到的物品与数量与退出前一致。
2. **Given** 新玩家首次进入世界，**When** 打开浮动面板，**Then** 看到固定数量的空槽（与面板布局一致），无报错、无幽灵物品。
3. **Given** 仅服务端与客户端安装本模组，**When** 玩家在服务器游玩并存放物品后重进，**Then** 背包内容仍然保留。

---

### User Story 2 - 面板内点击取放 (Priority: P2)

浮动面板可见时，玩家可以在面板格子上点击，把物品拿起、放下或交换，行为接近原版槽位的左键取放（含堆叠合并的基本规则）。操作结果以服务端为准，客户端显示随后与之对齐。

**Why this priority**: 「面板内取放」是 M2 相对 M1 的核心可玩增量。

**Independent Test**: 打开面板，将物品放入一格、再点出、再与另一格交换；刷新或重开面板后结果仍正确。

**Acceptance Scenarios**:

1. **Given** 面板打开且某格有物品、光标未持物，**When** 玩家左键该格，**Then** 该格变空，光标持有该物品（或等价的「已拿起」状态）。
2. **Given** 光标持有物品且点到空格，**When** 玩家左键，**Then** 物品放入该格，光标清空。
3. **Given** 光标持有物品且点到已有同类可堆叠物品的格子，**When** 玩家左键，**Then** 按堆叠上限合并，剩余留在光标上。
4. **Given** 光标持有物品且点到不同物品的格子，**When** 玩家左键，**Then** 两格内容交换。
5. **Given** 网络延迟或校验失败，**When** 服务端拒绝某次操作，**Then** 客户端最终显示与服务端库存一致，不出现永久「假物品」。

---

### User Story 3 - 无容器界面时也能往背包存取 (Priority: P3)

在没有打开原版物品栏/箱子的情况下，玩家仍能把身上的物品存进浮动背包，或从浮动背包取回身上，以便在 M3 之前即可实际使用背包（不必依赖「两个 GUI 互拖」）。

**Why this priority**: 否则 M2 只能靠调试指令填物，难以真人验收。

**Independent Test**: 不按 E，只开浮动面板，完成「主手物品存入空槽」与「从槽取回主手/背包空位」各至少一次。

**Acceptance Scenarios**:

1. **Given** 未打开任何容器界面，主手持有物品，面板有空槽，**When** 玩家按约定方式存入（例如对空槽使用指定操作），**Then** 主手物品进入该槽，主手变空（或按规则减少数量）。
2. **Given** 未打开容器界面，面板某格有物品且主手为空，**When** 玩家取出该格，**Then** 物品回到主手（或玩家背包空位，规则在假设中固定一种）。
3. **Given** 已打开原版物品栏，**When** 玩家仅使用浮动面板格子，**Then** 本阶段不要求与物品栏光标物品互通；面板可继续用本模组自己的拿起状态，或暂时仅允许查看——具体在假设中选定并写清。

---

### Edge Cases

- 玩家死亡时：背包内容默认保留（类似末影箱），不掉落；若日后要掉落需另开规格。
- 槽位已满或堆叠已满时，存入失败且不吞物品。
- 模组未装在服务端时：客户端不得伪造可联机生效的物品移动（单人集成服务端除外）。
- 面板隐藏时，不允许对槽位点按生效。
- 超大 NBT / 模组物品：按原版可复制 ItemStack 规则存取；无法序列化的情况不得崩溃，可拒绝并提示。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 为每位玩家维护一份服务端权威的浮动背包库存，槽位数与面板可见格子一致。
- **FR-002**: 背包内容 MUST 随玩家数据持久化，并在重进世界后恢复。
- **FR-003**: 客户端面板 MUST 显示服务端同步后的物品图标与堆叠数，MUST NOT 仅用本地假数据冒充最终结果。
- **FR-004**: 玩家 MUST 能在面板格子上通过点击完成拿起、放下、交换与基本堆叠合并。
- **FR-005**: 所有改变库存的操作 MUST 经服务端校验后再生效。
- **FR-006**: 在未打开原版容器界面时，玩家 MUST 仍能在浮动背包与自身物品之间完成至少一种存入与取出路径。
- **FR-007**: 本功能 MUST NOT 实现与已打开的原版物品栏/箱子界面之间的光标互拖（属 M3）。
- **FR-008**: 打开浮动面板 MUST NOT 改为使用 `Screen` 替换当前界面；继续沿用 M1 叠加层。
- **FR-009**: 面板隐藏时，槽位点击 MUST 不生效。

### Key Entities

- **浮动背包库存**: 绑定玩家的固定槽位集合，含每槽物品与数量。
- **面板光标物品**: 玩家从面板拿起、尚未放下的物品（可与原版容器光标分离，直到 M3 再合并策略）。
- **同步快照**: 服务端发给客户端的库存（及可选光标）视图，用于渲染。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在一次单人会话中，玩家能在 2 分钟内完成「存入至少 1 组物品 → 隐藏再打开面板仍在 → 取出」。
- **SC-002**: 退出并重进同一存档后，抽查背包中至少 3 个不同槽位的物品与数量 100% 一致。
- **SC-003**: 连续进行 20 次面板内点击取放后，客户端显示与重开面板后的内容一致，无槽位错乱或复制刷物。
- **SC-004**: 不打开原版物品栏即可完成至少一次存入与一次取出（SC-001 的路径不依赖按 E）。
- **SC-005**: 验收不依赖精妙背包、旅行者背包等第三方模组。

## Assumptions

- 槽位数初版固定为 27（与 M1 面板 9×3 一致），本阶段不提供升级/多页。
- 死亡不掉落浮动背包内容。
- 与已打开容器 GUI 的光标互通留到 M3；M2 使用本模组自己的面板光标状态，或在打开容器时将面板槽位视为只读——实现计划中选定一种，默认为「仍可用模组光标，不读取原版菜单 carried」。
- 无容器界面时的存取默认路径：与主手（selected hotbar）交换/存取，规则写在计划与 quickstart 中。
- M1 的开关、拖动、位置持久化、叠加层渲染继续有效，本规格不重做。
- 不包含 JEI/EMI 专项、不包含第三方背包兼容。
