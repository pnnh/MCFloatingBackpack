# Feature Specification: 第三方模组兼容开关与客户端配置，并把依赖规则变成自动检查

**Feature Branch**: `020-compat-switches`

**Created**: 2026-11-05

**Status**: Draft

**Input**: User description: "第三方模组兼容开关与客户端配置系统，并把\"依赖规则\"变成自动检查。玩家在配置里用\"模组 id = 档位\"（FULL 正常兼容 / GENERIC 关闭专用适配 / OFF 完全关闭）控制浮动背包对某个第三方模组的主动兼容，以解决同时安装多种模组时的冲突；原版容器的支持不可关闭；服务端预留一个现阶段恒为真的门禁；依赖规则（宪法 2.1.0 原则 VII）用自动化测试守住。"

## 背景与已确认的决策

浮动背包的底线是：**只依赖 Minecraft 1.21.1 与 NeoForge 21.1.251，对其它模组的任何主动兼容都是可选的**。到 019 为止这一点是靠约定保持的（`neoforge.mods.toml` 里第三方模组都是 optional，构建里它们只在开发期运行时、JEI 的 API 只在编译期）。但实现过程中发现，面板和其它模组（背包类模组、JEI 等）之间有一些不可避免的互相干扰；而一个个测试每个模组再针对性处理是做不完的。所以需要：

- 把"最低依赖"写成宪法（2.1.0 原则 VII，已提交）并用**自动检查**守住，避免以后不小心破坏；
- 给玩家一个**逃生口**：遇到冲突时可以在配置里降低或关闭对某个模组的主动兼容。

已确认的决策（用户已裁决，不重新讨论）：

1. **三个档位**，配置项是"模组 id = 档位"的键值对：
   - **FULL**（默认）：**专用适配**——开启我们为该模组写的专有代码，代表我们对它做了主动兼容，也可以看作功能增强；受限于测试覆盖面仍可能有问题。
   - **GENERIC**：**没有专用适配**——关闭我们为该模组写的任何专有代码（没写过专有代码的模组，GENERIC 与 FULL 一样）。它**不决定**面板能不能显示在该模组的界面上、能不能与它的菜单 Ctrl+点击互相转移物品：这取决于该模组自己的实现——实现得越接近原版游戏里容器与面板的行为，我们理论上能给它的兼容性就越好；即使关闭了所有专有代码，Ctrl+点击面板格子仍然可能互相转移，也可能不行，只是我们**不根据是不是 GENERIC 来判断**是否支持 Ctrl+点击转移。部分功能可用，也可能有兼容问题，由用户自己选择是否接受。
   - **OFF**：完全关闭——不在该模组的界面之上显示面板。**OFF 只对"拥有容器界面的模组"有意义**：对只拥有非容器界面的模组（如 JourneyMap 的全屏地图、EMI 自己的配方页，019 已经让面板在这类界面上自动隐藏）或只叠加在别人界面上的模组（如 JEI、EMI 的侧栏），OFF 等同于 GENERIC，没有额外效果。
2. **名单之外的第三方模组默认互动**（保持现状，即 FULL）；用户发现冲突后自己到配置里改。
3. **原版容器的支持不可关闭**：玩家物品栏、箱子、熔炉、工作台等原版菜单永远按 FULL 处理，不进配置。
4. **本阶段只做客户端配置**，改了**不需要重启**游戏。服务端不做配置、不做名单，但在服务端**预留一个门禁**：一个现阶段**恒返回"允许"**的纯逻辑判断，接在服务端真正碰到别的模组菜单的入口，带单元测试；以后有服务端名单需求时只改这一个判断。不改网络协议。
5. 配置界面用 NeoForge 自带的配置界面，在游戏"模组"列表里可以打开。
6. 019 的按键"让出再重放"是**与模组无关的通用机制**（已按各按键映射在无界面时是否活跃来判断），**不属于**对某个模组的主动互动，**不在本 feature 的配置范围内，也不提供开关**。

已查证的事实（读本仓库源码与构建文件；规格要尊重，不要重新猜）：

- 必需依赖：`neoforge.mods.toml` 里只有 `neoforge` 与 `minecraft` 是 required；精妙背包核心、精妙背包、旅行者背包、JEI 都是 optional。构建里第三方模组只在开发期运行时（`-PcompatRuntime`、`-PshaderRuntime`、`-PnoJei` 控制），JEI 的 API 只在编译期。项目没有 mixin。
- **唯一的"模组专用适配"**是 `compat/jei` 下的 JEI 插件（008）：让 JEI 把浮动面板所在区域当作被占用、避让开，避免 JEI 内容被面板遮盖。它是项目里**唯一引用第三方类型的代码**。
- **对精妙背包、旅行者背包没有任何专用代码**。面板挂在它们的界面上、Ctrl 转移、光标合并，走的都是对任意容器界面和菜单槽位通用的逻辑，对任何模组的容器同样生效。`ContainerScreenCompat` 里的类名匹配与 `CompatTarget` 除了它自己的单测外没有人使用。**因此现阶段对容器类模组，FULL 与 GENERIC 的实际行为相同，只有 JEI 这类有专用适配的模组两档才有区别。**
- 019 的宿主界面把当前界面分成：无界面、宿主、容器界面（面板挂上去）、其它界面（面板隐藏，但"可见"状态保留，界面关闭后面板回来）。**把某个模组的界面按"其它界面"处理，就是 OFF 档想要的效果，直接复用这套语义。**
- 服务端碰到"别的模组的菜单"的入口：向打开着的容器投递物品、从打开着的容器取出物品、把面板光标合并进菜单携带物（以及 Ctrl 转移与光标手势里涉及菜单携带物的部分）。
- 测试类路径里只有 JUnit（没有 Minecraft 等库），所以判断逻辑要放在不依赖 Minecraft 的纯类里才能单测。
- 判断一个界面/菜单属于哪个模组的设想：用菜单类型的**注册命名空间**；玩家自己的物品栏菜单没有菜单类型，按原版处理；无法判断归属时按"未列出"（FULL）处理。**这一点尚未在游戏里验证，需要登记**。

## Out of Scope（本阶段不做）

- 服务端配置、服务端名单（只预留恒真的门禁）。
- 为精妙背包、旅行者背包等写**专用适配**（本阶段它们 FULL 与 GENERIC 无区别）。
- 为 EMI、JourneyMap 等写专用适配：没有适配就没有可以切换的档位。JourneyMap 的全屏地图本来就是非容器界面，面板自动隐藏；EMI 叠在容器界面上的侧栏与搜索框目前不做适配，玩家遇到遮盖时靠拖动面板或暂时关闭面板解决（将来如要适配，做法同 JEI，是另一个 feature）。
- **mixin 是否禁止**（宪法未定，不在本阶段）。
- 清理 `ContainerScreenCompat` 里没人用的 `CompatTarget`/`identify`：登记为整理项，**不顺手做**。
- 按键"让出再重放"的开关；任何新玩法。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 遇到冲突时，把某个模组设为 OFF，面板不再出现在它的界面上 (Priority: P1)

玩家同时装了浮动背包和另一个背包类模组，发现面板挂在对方界面上会出问题。玩家在配置里写 `sophisticatedbackpacks = OFF`，之后打开对方的界面时面板不再出现、不拦截任何操作；关闭对方界面后面板自动回来。原版的箱子、熔炉、工作台、物品栏完全不受影响。

**Why this priority**: 这是整个 feature 存在的理由——给玩家一个解决冲突的逃生口，而不用等开发者逐个适配。

**Independent Test**: 用 `runClientCompat`（精妙背包、旅行者背包、JEI）：先不配置，确认面板能挂在精妙背包界面上；写 `sophisticatedbackpacks = OFF` 后再开它的界面，确认面板不出现；再开原版箱子，确认面板照常。

**Acceptance Scenarios**:

1. **Given** 配置里没有任何条目，**When** 面板可见时打开精妙背包界面，**Then** 面板挂在它上面，Ctrl 转移等一切照常（与改动前一致）。
2. **Given** 配置里 `sophisticatedbackpacks = OFF`，面板可见，**When** 玩家打开精妙背包界面，**Then** 面板**隐藏**、不被绘制、不拦截点击/滚轮/键盘，Ctrl+点击不触发面板转移，也不向服务端发送合并光标请求；面板的"可见"状态保留。
3. **Given** 上一条的状态，**When** 玩家关闭精妙背包界面，**Then** 面板自动回来，位置、尺寸、选区不变。
4. **Given** 同样的配置，**When** 玩家打开原版箱子、熔炉、工作台、物品栏，**Then** 面板照常挂上去，行为与没有配置时完全一致。
5. **Given** 同样的配置，**When** 玩家在精妙背包界面上按面板热键，**Then** 面板**不打开**，并在屏幕上方给出一条简短提示（说明这个界面所属的模组被配置为关闭了面板）；在原版界面上按热键则正常打开。
6. **Given** 配置里只写了 `sophisticatedbackpacks = OFF`，**When** 玩家打开旅行者背包界面，**Then** 它不受影响（没列出就是 FULL）。
7. **Given** 配置里写 `travelersbackpack = OFF`，**When** 玩家在其界面上进行过一半的拖动、Ctrl 转移或缩放时界面切换过来，**Then** 进行中的手势被安全取消，物品总数守恒。

### User Story 2 - 对有专用适配的模组，三档的实际表现不同（以 JEI 为例） (Priority: P1)

浮动背包目前只对 JEI 有专用适配：面板被拖到 JEI 的区域上方时，JEI 会避让，不被面板遮盖。玩家可以选择：FULL（默认，JEI 避让）；GENERIC（不做避让，JEI 内容可能被面板遮盖，用户可以把面板拖走，属于降级体验，不影响核心功能）。

**Why this priority**: 它证明三档不是摆设：专用适配可以被单独关掉，面板自己的功能不受影响；也是将来其它专用适配的样板。

**Independent Test**: 装了 JEI 时，拖动面板到 JEI 区域上方：FULL 时 JEI 内容避让；改成 GENERIC 后不再避让，且不需要重启游戏；面板本身一切功能照常。

**Acceptance Scenarios**:

1. **Given** 配置里没有 `jei` 条目（或 `jei = FULL`），**When** 把面板拖到 JEI 的物品列表区域上方，**Then** JEI 避让面板所在区域，不被遮盖（与 008 一致）。
2. **Given** `jei = GENERIC`，**When** 同样拖动，**Then** JEI 不再避让，面板可能遮盖它；面板的所有功能（点击、拖动、Ctrl 转移、选区、标签等）不受影响。
3. **Given** 面板已经开着、JEI 已经避让，**When** 玩家在配置界面里把 `jei` 改成 `GENERIC` 并保存，**Then** 不需要重启游戏，JEI 在下一次刷新布局时不再避让。
4. **Given** `jei = OFF`，**When** 打开任何界面，**Then** 与 `GENERIC` 相同（JEI 只装饰别的界面，没有自己可"打开面板"的界面，见 Assumptions）。

### User Story 3 - 在游戏里或配置文件里改设置，坏配置不会让游戏崩溃 (Priority: P1)

玩家可以在游戏的"模组"列表里打开浮动背包的配置界面，看到每一档的说明并编辑"模组 id = 档位"；也可以直接改配置文件。写错、写乱、手工改坏时，游戏不崩溃，回退到默认（全部 FULL）。

**Why this priority**: 配置必须好用，且不能因为一行写错就让游戏起不来。

**Independent Test**: 在模组列表里打开配置界面，添加、修改、删除条目；再把配置文件改成各种非法内容，启动游戏。

**Acceptance Scenarios**:

1. **Given** 默认配置，**When** 打开配置界面，**Then** 条目列表为空，界面上有对三档的说明（中文与英文各一份）。
2. **Given** 在配置界面里添加 `sophisticatedbackpacks = OFF` 并保存，**When** 回到游戏，**Then** 不需要重启，立即生效。
3. **Given** 档位写成 `off`、`Off`、`OFF`，**When** 读取配置，**Then** 都按 OFF 处理（不区分大小写）。
4. **Given** 档位写成不存在的值（如 `HALF`），**When** 读取配置，**Then** 该条按 FULL 处理并在日志里记一条警告，其它条目不受影响。
5. **Given** 模组 id 含大写、空格或其它非法字符，**When** 读取配置，**Then** 该条被忽略并记日志。
6. **Given** 同一个模组 id 出现多次，**When** 读取配置，**Then** 取最后一条并记日志。
7. **Given** 配置里写了 `minecraft = OFF`，**When** 读取配置，**Then** 被忽略并记日志（原版不可配置），原版界面照常。
8. **Given** 配置文件整体被改坏（不是合法的配置格式），**When** 启动游戏，**Then** 游戏正常进入，配置回退默认。
9. **Given** 配置里列了一个根本没安装的模组 id，**When** 游戏运行，**Then** 没有任何效果也不报错。

### User Story 4 - 依赖规则由自动检查守住 (Priority: P2)

宪法 2.1.0 原则 VII 的几条规则，变成会失败的自动化测试：以后有人不小心把第三方模组改成必需依赖、在 `compat/<模组 id>/` 之外引用了第三方类型、或把第三方模组放进了发布产物的依赖里，构建的测试阶段就会报错。

**Why this priority**: 没有自动检查，"最低依赖"迟早会被不小心破坏。

**Independent Test**: 当前代码库通过检查；对三类违规各构造一个反例，检查器必须判为失败。

**Acceptance Scenarios**:

1. **Given** 当前代码库，**When** 运行测试，**Then** 依赖规则的检查全部通过。
2. **Given** `neoforge.mods.toml` 里除 `neoforge`、`minecraft` 之外出现了一个不是 optional 的依赖（反例），**When** 检查，**Then** 判为失败，并指出是哪个依赖。
3. **Given** `compat/<模组 id>/` 之外的源文件引用了不在白名单里的第三方包（反例），**When** 检查，**Then** 判为失败，并指出文件与引用。
4. **Given** 构建文件里第三方模组坐标出现在 `compileOnly`、`localRuntime` 之外的位置（反例），**When** 检查，**Then** 判为失败。
5. **Given** 一个合法的 `compat/jei/` 下的文件引用了 JEI 的包，**When** 检查，**Then** 判为通过。

---

### User Story 5 - 服务端预留门禁，现阶段不改变任何行为 (Priority: P3)

服务端在碰到别的模组的菜单之前，都先问一个统一的判断"允许对这个菜单做这件事吗"；现阶段这个判断**恒为允许**，所以所有现有的转入、取出、合并行为与改动前一模一样。以后需要服务端名单时只改这一个判断。

**Why this priority**: 它不带来玩家可见的变化，只是把将来的入口定好；符合宪法"影响物品移动的判断须在服务端做"。

**Independent Test**: 单元测试断言门禁对任何输入都返回"允许"；服务端三个入口都经过它；011/012/013 的相关手测结果不变。

**Acceptance Scenarios**:

1. **Given** 任意菜单与任意操作（转入、取出、合并），**When** 询问门禁，**Then** 都返回"允许"。
2. **Given** 现有的 Ctrl 转移到打开的容器、从容器取出、打开界面时的光标合并，**When** 重跑它们的验证项，**Then** 结果与改动前一致。

### 修订（2026-11-05，第一轮客户端验证之后）

- **GENERIC 的含义（用户补充说明）**：只关闭我们为该模组写的专有代码，不影响面板能否显示、能否与它的菜单交换物品（这取决于该模组自己的实现）；对没有专有代码的模组与 FULL 一样。曾误解为"不交换物品"并改过一版，已撤销。
- **提示改到聊天区**：OFF 的界面上按热键的提示、以及所有配置问题的提示，都输出到玩家自己的聊天区（原先热键提示在 action bar，一闪而过看不清）。
- **配置错误提示**：新增 FR-019。
- **配置"被重置"的原因**：见 Edge Cases 里"游戏运行时用编辑器改配置文件"。

### Edge Cases

- **模组 id 写错或没安装**：等于没有效果，不报错。
- **游戏运行时用编辑器改配置文件**：编辑器的自动保存可能存下写了一半的内容（比如少了一个引号），NeoForge 的文件监视器会立即重新读取，读不出来就把这份文件备份为 `mcfloatingbackpack-client-N.toml.bak` 并写回默认配置（`modLevels` 变回空数组）——这是 NeoForge 自己的恢复行为，不是本模组清空了设置；玩家改的内容在 `.bak` 里。本 feature 做的是在聊天区提示这件事（FR-019），建议在游戏关闭时改文件，或用游戏里的配置界面。
- **拥有非容器界面的模组**（如 JourneyMap 的全屏地图）：面板可见时打开它，面板按 019 的"其它界面"语义隐藏，关闭后恢复，不需要也不受任何配置影响；它们的小地图这类画在游戏画面上的 HUD 与面板的重叠不在本 feature 范围内，登记为未验证。
- **只叠加在别人界面上的模组**（如 EMI 的侧栏）：没有专用适配时没有可切换的档位；面板遮盖它时由玩家拖开面板；本 feature 不为此提供配置。
- **配置里列了 `minecraft`**：忽略并记日志；其它模组在原版菜单类型上打开的界面，归属为原版，**不受配置影响**。
- **面板正开着时把某个模组改成 OFF**：如果此刻正显示的就是该模组的界面，面板立即按 OFF 处理（隐藏），进行中的手势被安全取消。
- **玩家自己的物品栏界面、创造物品栏**：沿用现状，不受配置影响。
- **界面归属无法判断**（没有菜单类型、或不是容器界面）：按未列出处理，即 FULL（若它本来就不是容器界面，面板本来就不挂上去）。
- **多人服务器**：客户端配置只影响客户端自己的行为；服务端不受影响，服务端的门禁恒为允许。客户端配置**不是安全边界**。
- **OFF 的模组界面上的 Ctrl 转移**：不触发面板转移（面板已隐藏）；该模组自己的界面行为不受影响。
- **配置文件被改坏**：回退默认，游戏不崩溃。
- **同一模组重复列出**：取最后一条。
- **玩家在被 OFF 的界面上按 019 的"让出"类按键（如 E、聊天）**：与现状一致，这些按键由原版或其它模组处理，面板不在场。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供**客户端**配置，包含一个"模组 id = 档位"的键值对列表，默认为空；档位为 FULL、GENERIC、OFF 三种，不区分大小写。
- **FR-002**: 未在配置里列出的模组 MUST 按 FULL 处理；档位无法识别的条目 MUST 按 FULL 处理并记一条日志；模组 id 不合法（只允许小写字母、数字、下划线）的条目 MUST 被忽略并记日志；同一模组重复列出时 MUST 取最后一条并记日志；列出 `minecraft` MUST 被忽略并记日志。
- **FR-003**: 原版菜单（玩家物品栏、箱子、熔炉、工作台等）MUST 永远按 FULL 处理，且 MUST NOT 受配置影响；其它模组在原版菜单类型上打开的界面，归属为原版。
- **FR-004**: 系统 MUST 判断一个界面属于哪个模组；无法判断时 MUST 按未列出（FULL）处理。
- **FR-005**: 某模组为 **OFF** 时，它的界面 MUST 被当作"其它界面"：面板 MUST 隐藏（保留"可见"状态）、MUST NOT 绘制、MUST NOT 拦截点击/滚轮/键盘、Ctrl 转移 MUST NOT 触发、MUST NOT 向服务端发送合并光标请求；界面关闭后面板 MUST 自动恢复。
- **FR-006**: 在 OFF 的模组界面上按面板热键，面板 MUST NOT 打开，并 MUST 在**玩家自己的聊天区**给出一条提示（说明这个界面所属的模组被配置为不显示面板；只有本人可见，不发送给服务器或其他玩家；玩家按 T 可以再次查看）。
- **FR-007**: 某模组为 **GENERIC** 时，系统 MUST NOT 执行任何针对该模组的专用适配（目前只有 JEI 的避让）；系统 MUST NOT 根据是不是 GENERIC 来决定面板能否显示在它的界面上、能否与它的菜单做 Ctrl+点击转移或合并光标（这些仍按通用逻辑进行，结果取决于该模组自己的实现）；为 **FULL** 时 MUST 与改动前的行为一致。
- **FR-008**: JEI 的避让适配 MUST 受配置控制：FULL 时让 JEI 避让面板区域；GENERIC 与 OFF 时不避让。该判断 MUST 在 JEI 每次询问区域时读取配置，使改动无需重启即生效。
- **FR-009**: 配置的改动 MUST 在不重启游戏的情况下生效；面板正开着时改成 OFF，当前正显示的该模组界面上面板 MUST 立即按 OFF 处理，进行中的手势 MUST 被安全取消，物品总数守恒。
- **FR-010**: 配置 MUST 能在游戏"模组"列表里通过配置界面编辑，界面 MUST 说明三档各自的含义；所有文字 MUST 提供中文与英文。
- **FR-011**: 配置文件被改坏、含非法内容或列了未安装的模组时，游戏 MUST NOT 崩溃，MUST 回退到可用的默认。
- **FR-019**: 配置有问题时，系统 MUST 在玩家自己的聊天区给出简短提示：(a) 单条的问题（格式不对被忽略、档位无法识别按 FULL、列了 `minecraft`、同一模组重复）逐条说明是哪一条；一次最多显示 5 条，其余合并成一行"还有 N 条，详见日志"，相同的提示只显示一次；(b) 整个文件有语法或格式错误时（NeoForge 会把玩家保存的文件备份为 `mcfloatingbackpack-client-N.toml.bak` 并写回默认配置），说明已备份为哪个文件、已恢复默认，并建议在游戏关闭时修改或使用游戏里的配置界面。游戏尚未进入世界时的问题 MUST 等玩家进入世界后再显示。
- **FR-012**: 服务端 MUST 在碰到别的模组菜单的入口（向打开的容器投递物品、从容器取出、合并面板光标）前经过**同一个门禁判断**；现阶段该判断 MUST 对任何输入返回"允许"，并 MUST 有单元测试；本 feature MUST NOT 改变网络协议，MUST NOT 增加服务端配置。
- **FR-013**: 019 的按键"让出再重放"机制 MUST NOT 受本配置影响，且 MUST NOT 提供对它的开关；文档里 MUST 说明这一点。
- **FR-014**: 依赖规则 MUST 由自动化测试检查：(a) `neoforge.mods.toml` 里除 `neoforge`、`minecraft` 之外的每个依赖都是 optional；(b) 白名单之外的第三方包只允许出现在 `compat/<模组 id>/` 下的源文件里；(c) 构建文件里的第三方模组坐标只出现在 `compileOnly` 或 `localRuntime` 的声明里。检查器 MUST 对每一类违规各有一个反例用例证明会失败。
- **FR-015**: 本 feature MUST NOT 改变面板在原版界面、容器界面上的任何现有行为（011～019），MUST NOT 引入新的必需依赖，MUST NOT 新增 mixin。
- **FR-016**: 受影响的文档（`docs/MCFloatingBackpack.md` 等）MUST 更新，说明配置项与三档含义；MUST NOT 修改 `docs/ideas`。
- **FR-018**: 面板**第一次**在某个**非原版**模组的容器界面上挂上去时（每个模组每次游戏会话只一次），系统 MUST 在日志里记一行说明该界面所属的模组 id，并提示"若有冲突，可在配置里把这个模组设为 OFF"，让玩家不用猜模组 id；MUST NOT 每帧或每次打开都重复记录。
- **FR-017**: 以下 MUST 登记为已知限制或未验证，而不是声称已满足：按菜单类型的命名空间判断界面归属在真实的精妙背包/旅行者背包界面上的表现；JEI 在 GENERIC 下的遮盖效果；Windows/Linux。

### Key Entities *(include if feature involves data)*

- **兼容档位**：FULL（默认）、GENERIC、OFF 三种取值之一。
- **模组 id**：一个模组的标识（如 `jei`、`sophisticatedbackpacks`）；配置里的键，小写字母、数字、下划线。
- **界面归属**：一个界面（或它的菜单）属于哪个模组；原版或无法判断时视为"原版/未列出"。
- **兼容策略**：给定配置，回答"面板能否在这个归属的界面上互动"和"是否执行对这个模组的专用适配"；原版永远是 FULL。
- **服务端门禁**：服务端对"能否对这个菜单做这件事"的统一判断，现阶段恒为允许。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在 `runClientCompat` 下，配置 `sophisticatedbackpacks = OFF` 后打开精妙背包界面，面板**不出现**（出现次数 0）；关闭界面后面板自动回来；旅行者背包界面（未列出）在同一设置下仍然正常挂面板。
- **SC-002**: 在同一设置下，原版箱子、熔炉、工作台、物品栏上的面板挂载与 Ctrl 转移，结果与没有配置时**完全一致**（011～019 的相应验证项逐项不变）。
- **SC-003**: JEI 三档的表现符合 US2：FULL 时避让、GENERIC/OFF 时不避让；来回切换 5 次**无需重启**，每次都生效。
- **SC-004**: 对至少 10 种非法配置写法（非法档位、非法 id、重复、`minecraft`、整体损坏的文件等）启动游戏，**0 次崩溃**，均回退到可用的默认。
- **SC-005**: 依赖规则的自动检查在当前代码库上通过；三类违规的反例用例**各自被判为失败**（3/3）。
- **SC-006**: 服务端门禁对任意输入返回"允许"（单元测试覆盖），三个入口都经过它；011/012/013 的转入、取出、合并的手测结果与改动前一致。
- **SC-007**: 配置界面在中文与英文下文字完整，三档说明可见。
- **SC-010**: 把 `sophisticatedbackpacks` 设为 `GENERIC` 后，面板在精妙背包界面上的显示、Ctrl+点击转移、光标合并的表现与设为 `FULL` 时**完全一致**（因为没有专有代码可关）；设为 `OFF` 才隐藏面板。
- **SC-011**: 写错配置（至少 5 种写法）和把文件改成语法错误时，进入世界后聊天区出现对应的简短提示，提示不超过 5 行加一行汇总；OFF 的界面上按热键，聊天区出现提示且按 T 能再次看到。
- **SC-009**: 面板第一次挂在精妙背包界面上时，日志里出现 1 行包含 `sophisticatedbackpacks` 的提示；之后反复打开同一模组的界面，同一会话内不再重复（1 次）。
- **SC-008**: 在开发机（macOS）上完成验证；Windows/Linux 无法验证，明确登记为未验证。

## Assumptions

- **JEI 的 OFF 与 GENERIC 相同**：这是上面通用规则的一个实例——JEI 只装饰别的界面、没有自己可以"打开面板"的容器界面；若字面执行"禁止在 JEI 之上打开面板"，装了 JEI 就等于不能用面板。并在配置说明里写明。若用户另有想法再改。
- **OFF 的提示**：按热键被拒绝时给一条简短的屏幕上方提示，避免玩家以为是 bug；提示文字中英文各一份。
- **OFF 对 JEI/EMI 这类叠加模组等同 GENERIC**：它们没有自己可以"打开面板"的容器界面（见背景第 1 条）。
- **配置形式**：一个字符串条目的列表，每条形如 `modid=LEVEL`；NeoForge 的配置没有现成的"映射"类型，具体怎么存留给 plan。
- **归属判断**：以菜单类型的注册命名空间为主；没有菜单类型的（玩家物品栏等）按原版；无法判断按未列出。需要在游戏里验证，登记为未验证。
- **客户端配置只管客户端**：多人服务器上它影响的只是本机的面板行为与 JEI 避让；它不是安全边界。
- **GENERIC 的含义**：用户补充说明——FULL 是专用适配（我们为该模组写的专有代码，代表主动兼容、可视为功能增强）；GENERIC 是没有专用适配（关闭这些专有代码；没写过的模组与 FULL 一样），它不决定面板能否显示或能否交换物品，那取决于该模组自己的实现；OFF 是面板不显示（面板与该模组的界面只能二选一）。我们不根据是不是 GENERIC 来判断是否支持 Ctrl+点击转移。这一点要写进配置说明与文档。
- 依赖：019（宿主界面与"其它界面"语义）、008（JEI 适配）、宪法 2.1.0 原则 VII。
- 开发机是 macOS，只能本机验证，Windows/Linux 只能推断；所有玩家可见的改动按宪法 V 在客户端会话里验证。
