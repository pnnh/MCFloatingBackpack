# 交付记录：064 禁止浮动背包嵌套

## 做了什么

- 面板的所有区域（主区域、工具区、垃圾桶）不再收浮动背包，也不收"里面装着浮动背包"的物品（深度扫描：原版容器与收纳袋结构化读取，深度上限 8；别的模组的数据编码后查五个物品 id）。判定在 `inventory/nesting/`（`NestingRules`、`NestedOrigins` 纯逻辑；`BackpackNesting` 适配）。
- **默认安全**：`BackpackInventory.mainTargetOrder` 对有风险的物品返回三段全空，物品栏 → 面板、自动拾取、容器 → 面板、终端 → 面板自动继承；垃圾桶还原用 `mainTargetOrderInternal`。点击、拖动分摊、垃圾桶推入与 Delete/倾倒各自显式判定；容器 → 面板与终端 → 面板在取出/提取之前判定。
- `FloatingBackpackItem` 重写无参 `canFitInsideContainerItems()` 返回 false：原版潜影盒、收纳袋、旅行者背包拒收。
- 旧数据不动：已嵌套的可取出；"刚从哪只背包拿起了什么"每个玩家一条临时记录，同一个物品放回同一只背包放行一次，关闭界面、下线、世界停止时清除。打开背包时，旧嵌套在服务器日志里写一行 INFO（按背包编号每个玩家一次）。
- 垃圾桶：一律拒绝浮动背包（021 的 FR-018 与第 101 行验收已加修订说明）。
- 不新增网络包（协议号 22），`DataRevision` 仍 6，不用 mixin 与反射，代码里没有第三方类型（接线测试断言）。
- 文档：README 两份、`docs/plan/no-nested-backpacks.md`、021 spec 修订。

## 与 spec 不同的地方（如实）

spec 的"面板光标 = 内部来源"前提在 plan 阶段被代码推翻（开着容器界面时拿起的物品在菜单携带物上），改成"来源记录"，spec 的边界情形、FR-003、假设已同步。游戏内验证了：在物品栏界面里拿起旧嵌套背包可以放回同一只背包；关闭界面后记录失效，再放被拒。

## 没验证 / 取舍

- **没有游戏内验证**：工具区放入、拖动分摊（`distribute`）、自动拾取、容器 → 面板、ME 终端或集成终端 → 面板、光标 → 垃圾桶页、倾倒（DUMP）、创造模式界面、漏斗往潜影盒推。这些都经同一个判定函数或 `mainTargetOrder`，接线测试断言了调用，但没有逐条点过。
- 旧嵌套在**垃圾桶**与**工具区**里的取出/放回没有试（记录写入在 `BackpackTrashPayload.take` 与点击路径里，接线测试断言了）。
- "被拒的一瞬间客户端没有闪现"没有逐帧确认；截图里被拒后的画面状态正确。
- 原版漏斗、发射器对 `canFitInsideContainerItems` 的遵守没有验证；潜影盒方块界面与收纳袋已验证。
- 一只空浮动背包编码后的字节数没有实测；spec 里"皮革三层约 4.7 万只"仍是估算。
- ME 网络里放几十只满背包的同步量没有测（不属于必做项，README 与 `docs/plan/no-nested-backpacks.md` 已写明网络存储不受限制）。
- 容器里 `latest.log` 的 ERROR 只有环境噪声（GL、X11 光标、旧数据包的 `iron_honey_tank` 函数），没有本模组的 ERROR。

## 已知局限

- 记录的漏洞（已知、可接受）：拿起旧嵌套后放进物品栏、同一界面里再放回**同一只**背包仍然放行，结果与拿起前一样，没有新增嵌套，也进不了别的背包。
- 误伤：名字或自定义数据里恰好写着完整浮动背包物品 id 的物品，放入时被当作"含有"而拒绝；只是拒绝，不丢物品。
- 精妙背包默认不拒收（管理员配置）；AE2、集成终端、精妙存储箱子没有钩子，不限制。
