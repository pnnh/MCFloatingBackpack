# Feature Specification: 禁止浮动背包嵌套

**Feature Branch**: `064-no-nested-backpacks`

**Created**: 2026-11-23

**Status**: Draft

**Input**: 用户（2026-11-23）要求：禁止浮动背包放进浮动背包；装了精妙背包、旅行者背包时也不能把浮动背包放进它们里面；同时分析还有哪些情形值得限制，并考虑旧数据（已经嵌套的只能取出、不能再放进去）。分析与三项决定（用户已选）：**直接禁 + 深度扫描**、**旧数据允许同一只背包内部重摆**、**垃圾桶也禁**；其它容器放进浮动背包不限制；网络存储（AE2、集成终端、精妙存储）没有可用钩子，不做（见"不做"）。相关：021（垃圾桶，FR-018 要改）、012/060（面板与容器、网络终端之间的转移）、057（快照会把嵌套整份再存一遍）、047（整理）。

## 背景

- 背包的内容是物品上的一个数据组件，物品放进另一个容器时是**整份按值复制**。浮动背包套浮动背包时，数据量按扇出连乘增长：皮革背包 36 格，三层各塞满是 36³ ≈ 4.7 万只背包（按每只空背包几百字节估算，**未实测**），会超过自定义载荷约 1 MiB 的上限，也会让玩家数据大到无法登录、同步；快照与备份还会把嵌套内容再存一遍。皮革背包很便宜，不开创造模式也能搭出来，所以这是服务器可被刻意搞坏的入口。原版禁止潜影盒套潜影盒、收纳袋有大小上限，是同一个原因。
- 现状：面板主区域对容量内的格子什么都收（`canPlaceMain`），只有"手里那只被换进自己的格子"一处防护。垃圾桶（021 FR-018）明确允许丢进浮动背包。
- 其它容器放进浮动背包（潜影盒、收纳袋等）**不会**连乘：潜影盒不能套潜影盒，扇出有界；而且"潜影盒放进背包"是最主流的用法（051 的"容器收纳"分类里就有潜影盒）。所以不限制。
- 绕路：背包 → 潜影盒 → 另一只背包。只禁"直接放"堵不住，所以还要禁"含有浮动背包的物品放进浮动背包"。
- NeoForge 提供标准接口 `canFitInsideContainerItems(ItemStack)`：原版潜影盒、收纳袋、旅行者背包的格子校验都会问它（旅行者背包已反编译确认，原版路径待游戏内验证）；精妙背包默认不认（它的 `containerItemsDisallowed` 默认关），只能由管理员配置。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 浮动背包放不进浮动背包 (Priority: P1)

玩家把一只浮动背包拖进、Ctrl+点击进、Shift 点击进另一只浮动背包的面板（主区域、工具区、垃圾桶），被拒绝：物品留在原处，弹出一句操作栏提示。自动拾取也不会把掉落的浮动背包吸进背包。

**Why this priority**: 这是这个 feature 的核心，直接堵住数据爆炸的入口。

**Independent Test**: 单元测试判定函数；游戏内用各条入口各试一次。

**Acceptance Scenarios**:

1. **Given** 光标（菜单携带物）上是一只浮动背包，**When** 点击另一只背包面板的主区域、任一工具区或垃圾桶的格子，**Then** 没有任何变化，光标上的背包仍在，操作栏提示"浮动背包不能放进浮动背包"；服务端与客户端状态一致（客户端不会短暂显示放进去了）。
2. **Given** 玩家物品栏里有浮动背包，**When** 用 Ctrl+点击、Shift 点击或拖动把它送进面板，**Then** 同样被拒绝，原位不动。
3. **Given** 地上掉着一只浮动背包，**When** 自动拾取工具要把它吸进当前背包，**Then** 不吸，掉落物留在原地（或按没装拾取工具的普通规则进物品栏）。
4. **Given** 容器界面（箱子、网络终端）里有浮动背包，**When** 用 012/060 的"容器 → 面板"转移，**Then** 浮动背包不进面板，留在容器里。
5. **Given** 普通物品，**When** 以上任一方式放入，**Then** 与以前完全一样。

---

### User Story 2 - 旧数据：只能取出，不能再放进去 (Priority: P1)

升级前已经嵌套的背包不丢、不被自动搬走。玩家可以把嵌套的那只**取出**；取出后它不能再放进任何浮动背包。**同一只背包内部**重新摆放（从面板光标放回自己的格子）仍然可以，因为不增加嵌套。

**Why this priority**: 不能因为新规则让玩家丢东西或"卡"住，旧世界必须平稳过渡。

**Independent Test**: 用旧版本数据造一只装着背包的背包，升级后验证三件事：能取出、取出后放不回、同包内重摆可以。

**Acceptance Scenarios**:

1. **Given** 面板里有一只嵌套的浮动背包，**When** 点它（拿到面板光标），**Then** 成功，面板光标上就是它。
2. **Given** 面板光标上是刚从**这只**背包面板里拿起的嵌套背包，**When** 点本背包任何一个允许的格子，**Then** 放得下（同一只背包内部重摆，不增加嵌套）。
3. **Given** 面板光标上是从面板里拿起的嵌套背包，**When** 点玩家物品栏或别的菜单格子，**Then** 取出到物品栏（和以前一样）。
4. **Given** 取出后的背包又在菜单光标或物品栏里，**When** 再往任何浮动背包（包括原来那只）放，**Then** 被拒绝（视作"外部来源"）。
5. **Given** 旧数据里嵌套的背包仍在它的位置，**When** 升级后打开、关闭、保存、同步、快照，**Then** 内容原样保留，没有被丢掉、移走或改写；日志里至多一条 INFO 说明"这只背包里有嵌套的浮动背包（旧数据）"，不报错。

---

### User Story 3 - 含有浮动背包的物品也放不进浮动背包 (Priority: P1)

潜影盒、收纳袋等**装着浮动背包**的物品，不能放进浮动背包，堵住"背包 → 潜影盒 → 背包"的绕路。空潜影盒、装别的东西的潜影盒照常放得进。

**Why this priority**: 没有它，只禁直接放入就能被轻易绕过。

**Independent Test**: 单元测试深度扫描；游戏内造一个装着浮动背包的旧潜影盒（`/give` 带组件），放进浮动背包被拒。

**Acceptance Scenarios**:

1. **Given** 一个装着浮动背包的潜影盒（旧数据或 `/give`），**When** 放进浮动背包面板，**Then** 被拒绝，提示说明"里面含有浮动背包"。
2. **Given** 空潜影盒或装着普通物品的潜影盒，**When** 放进面板，**Then** 照常放入。
3. **Given** 收纳袋里装着浮动背包，**Then** 同样被拒绝。
4. **Given** 多层（潜影盒里的收纳袋里有浮动背包），**Then** 递归检查，同样被拒绝。

---

### User Story 4 - 其它容器不再收浮动背包（原版与旅行者背包；精妙背包靠配置） (Priority: P2)

玩家想把浮动背包放进潜影盒、收纳袋、旅行者背包时被拒绝（它们本来就会问"能不能放进容器物品"）。精妙背包默认不拒绝，需要管理员在它的配置里打开；文档写清怎么配。

**Why this priority**: 这是"可选扩展"，保护的是另一个方向（容器装浮动背包），数据影响比 US1 小，但能减少新的嵌套来源。

**Independent Test**: 游戏内：潜影盒、收纳袋、旅行者背包的格子拒收浮动背包；精妙背包默认收（记录在文档），按文档设置后拒收。

**Acceptance Scenarios**:

1. **Given** 打开潜影盒界面，**When** 把浮动背包放进去（点击、Shift 点击、漏斗），**Then** 被拒绝（待游戏内验证原版各条路径）。
2. **Given** 收纳袋，**When** 把浮动背包放进去，**Then** 被拒绝。
3. **Given** 装了旅行者背包，**When** 把浮动背包放进它的物品格，**Then** 被拒绝。
4. **Given** 装了精妙背包，**When** 管理员未配置，**Then** 浮动背包仍可放进（我们不替人改别的模组的配置）；**When** 配置 `containerItemsDisallowed = true` 或把浮动背包的物品 id 写进 `disallowedItems`，**Then** 被拒绝（README 与配置说明里给出这两种做法）。
5. **Given** 没装这些模组，**Then** 行为只受原版潜影盒、收纳袋影响，不报错。

---

### User Story 5 - 垃圾桶也不收浮动背包 (Priority: P2)

垃圾桶的内容存在背包里，也是嵌套的入口，所以同样拒收浮动背包。**这修改 021 的 FR-018**（当初允许丢进浮动背包）。需要销毁一只背包时，只能在面板外处理。

**Independent Test**: 游戏内把浮动背包点向垃圾格、Delete 键、拖进垃圾桶工具区，都被拒绝；其它物品照旧。

**Acceptance Scenarios**:

1. **Given** 光标上是浮动背包，**When** 点垃圾格或垃圾桶工具区，**Then** 被拒绝并提示。
2. **Given** 悬停一只浮动背包按 Delete（删除到垃圾桶），**Then** 什么都不发生（至多提示）。
3. **Given** 垃圾桶里已有旧数据的浮动背包，**Then** 能取出、不丢；取出后不能再放回。

---

### Edge Cases

- **"同一只背包内部重摆"的判定**（plan 阶段核对后修订）：开着容器界面（含物品栏界面）时，从面板拿起的物品直接进入菜单的携带物，光标本身看不出来源。所以改为**记一笔来源**：玩家刚从某只背包面板里拿起了某个有嵌套风险的物品，只有把"同一个物品"放回"同一只背包"才放行（用掉即清，关闭界面、下线也清）；记不住或对不上时一律按外部处理（更严）。
- **整理（047）**：只在主区域内部重排，不新增嵌套，旧嵌套留在原背包里，不被拒绝、不丢。
- **快照还原（057）**：整体覆盖背包内容，不逐项检查（快照里可能有旧嵌套，原样还原）。
- **`/give`、`/data`、数据包函数、创造模式取物**：不经过玩家交互入口，不拦截；创造模式界面里的拖放按交互入口规则处理（见下）。
- **创造模式**：创造物品栏里把浮动背包点进面板同样被拒绝（沿用同一判定）；`027` 创造兼容路径必须覆盖。
- **客户端提示**：被拒时客户端不先"假装放进去"，以服务端结果为准；不新增网络包，沿用现有的槽位回发加操作栏提示。
- **同类物品**：垃圾桶、标签管理器、自动拾取工具、分类扩展件等本模组的其它物品**不受限**，可以放进浮动背包。
- **深度扫描开销**：只对"带容器类数据组件"的物品做扫描；普通物品不付代价。
- **消息语言**：提示、日志的中英文语言键各一份。
- **降级**：旧版本没有这条规则，会照旧允许；040/041 的降级拦截不受影响，本 feature 不写新的存档字段。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 在服务端对"放入浮动背包的任何区域"（主区域、三个工具区、垃圾桶）统一判定：本模组的五档浮动背包 MUST 被拒绝；被拒时 MUST NOT 改变任何一侧的物品，MUST 给玩家一条操作栏提示，并让客户端以服务端状态为准。
- **FR-002**: 判定 MUST 在所有进入面板的入口生效：点击放置、Shift/Ctrl 点击、拖动分摊、自动拾取、容器 → 面板（012）、网络终端 → 面板（060，被拒时物品退回终端）、创造模式界面（027）；整理（047）与快照还原 MUST NOT 被它拦下。
- **FR-003**: 系统 MUST 记录"刚从哪只背包面板里拿起了哪个有嵌套风险的物品"（每个玩家一条，不存盘）：同一个物品放回**同一只**背包时 MUST 放行（旧嵌套重摆，不增加嵌套），用掉即清；关闭界面、下线时 MUST 清掉；对不上、记不住时 MUST 按外部处理。其它情形（物品栏、容器、地上、别的背包）一律外部，取出后的嵌套背包 MUST 不能再放进任何浮动背包。
- **FR-004**: 系统 MUST 对含有浮动背包的物品做深度扫描：潜影盒、收纳袋的内容组件至少 MUST 递归检查；带有其它模组容器组件的物品，MUST 用通用方式（编码后查找本模组物品 id）兜底；命中时 MUST 拒绝放入浮动背包并提示"里面含有浮动背包"。扫描 MUST 只对带容器类组件的物品做，普通物品不付代价。
- **FR-005**: 五档浮动背包物品 MUST 重写 `canFitInsideContainerItems(ItemStack)` 返回 false，使原版潜影盒、收纳袋、旅行者背包（以及别的遵守该接口的容器）拒绝收浮动背包。
- **FR-006**: 精妙背包：本模组 MUST NOT 修改它的配置；README 与配置说明 MUST 写明两种做法（`containerItemsDisallowed = true` 或把五档浮动背包的 id 写进 `disallowedItems`）。
- **FR-007**: 旧数据：升级后已经嵌套的背包 MUST 原样保留（不丢、不移、不改写）；打开、保存、同步、快照 MUST 不报错；MAY 在日志里写至多一条 INFO，说明这只背包里有旧嵌套。
- **FR-008**: 垃圾桶：021 的 FR-018 MUST 修订为"允许丢入任何物品，**浮动背包除外**"；021 的相关验收场景（如光标上是本模组背包丢入垃圾桶）MUST 更新；垃圾桶里已有的旧浮动背包 MUST 能取出。
- **FR-009**: 本模组的其它物品（垃圾桶、标签管理器、自动拾取工具、分类扩展件、管子等）MUST 仍可放进浮动背包。
- **FR-010**: MUST NOT 新增网络包、改协议号（仍 22）、改背包存储数据（`DataRevision` 仍 6）；MUST NOT 使用 mixin 或反射；第三方类型只允许出现在现有 `compat/` 包里（本 feature 预期不需要新增第三方类型引用）。
- **FR-011**: MUST NOT 对 AE2、集成终端、精妙存储的网络与箱子做任何限制（没有可用钩子，见"不做"）；MUST 在 README 的兼容说明里如实写明这一点。
- **FR-012**: 系统 MUST 有自动测试：判定函数（浮动背包被拒、其它物品放行、来源内部/外部）、深度扫描（直接、一层、多层、空容器、不含背包的容器）、`canFitInsideContainerItems` 接线、各入口接线（源码文本检查）、语言键中英文齐全。**游戏内验证**：各入口各试一次、潜影盒/收纳袋/旅行者背包拒收、旧嵌套取出与放不回、精妙背包按配置拒收。
- **FR-013**: 文档 MUST 同步：README 两份、021 的 spec 修订、DELIVERY 写清已验证与没验证的、`docs/plan/` 里写一页分析（本规格的"背景"与不做的理由）。

### Key Entities *(include if feature involves data)*

- **嵌套判定**：纯逻辑：输入"物品是不是浮动背包"、"物品里含不含浮动背包"、"来源是内部还是外部"，输出放行、拒绝（直接）、拒绝（含有）。
- **来源记录**：每个玩家至多一条"刚从哪只背包拿起了哪个物品"的临时记录；放回同一只背包时放行一次，其它情形不放行；不存盘。
- **旧嵌套**：升级前存档里已存在的"背包里的背包"，不是新数据类型，只是一种被允许保留、不允许新增的状态。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 玩家用任何交互入口都**无法**让一只浮动背包进入另一只浮动背包的任何区域（游戏内逐条入口验证，0 条漏网）。
- **SC-002**: 潜影盒、收纳袋、旅行者背包拒收浮动背包（游戏内验证）；装着浮动背包的容器物品放不进浮动背包。
- **SC-003**: 升级前已嵌套的背包 **0** 丢失；取出成功，取出后放不回；同包内重摆成功。
- **SC-004**: 单元与接线测试全部通过，原有测试 0 失败。
- **SC-005**: 被拒时不出现客户端闪现放入或物品复制/消失（游戏内与日志核对）。

## Assumptions

- 面板光标与菜单携带物是两条路径；开着容器界面时，从面板拿起的物品落在菜单携带物上（`BackpackClickLogic.click` 的结果交给 `menu.setCarried`），所以"来源"不能从光标本身读出，需要临时记录（见 Edge Cases）。若这条记录在游戏内验证中不可靠，退路是"一律只能取出"（规则最简单，旧数据照样不丢）。
- 原版潜影盒、收纳袋、漏斗对 `canFitInsideContainerItems` 的遵守程度要游戏内验证（旅行者背包已反编译确认会问）；验证不到的路径如实写进 DELIVERY，不假设可用。
- 深度扫描的通用兜底"编码后查本模组物品 id"可能误伤极少数把我们的 id 写进名字或自定义数据的物品，视为可接受（误伤只是拒绝放入，不丢物品）。
- 网络存储（AE2、集成终端、精妙存储）：没有 `canFit` 或标签之类的钩子，拦截需要 mixin，违反宪法 VII；本 feature 不做，另行在游戏里实测"几十只满背包放进 ME 网络"的同步量与元件体积（对比同样数量的潜影盒）后，再决定要不要在文档里提醒；这一步**不属于**本 feature 的必做项。
- 其它容器放进浮动背包（潜影盒等）不限制：扇出有界，限制会伤到主流用法。
- 新规则不追溯：不自动清理旧嵌套，不弹窗骚扰；管理员可以用日志里那条 INFO 找到有旧嵌套的背包。
