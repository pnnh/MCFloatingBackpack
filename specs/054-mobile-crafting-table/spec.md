# Feature Specification: 移动工作台（右区工具，点一下打开原版合成界面）

**Feature Branch**: `054-mobile-crafting-table`

**Created**: 2026-11-13

**Status**: Draft

**Input**: 用户（2026-11-13）："参考旅行者背包……实现普通工作台、熔炉、唱片机这三种移动工作台扩展工具的可行性。它们像已经有的'垃圾桶'工具一样，只能放置在浮动背包面板的右侧扩展区域才会生效……当放置在右侧区域后，玩家可以点击展开……内部嵌入原版基础工作台和熔炉，实现对应的合成和烧制功能。"——可行性分析后确认：**工作台与熔炉走做法 A：点工具后由服务端打开原版界面**；三个都是新物品，每种右区最多一个；不考虑每档背包的限制；配方中等以上难度。本 feature 是第二个（053 唱片机之后）：**移动工作台**；熔炉是 055。全部规划见 [docs/plan/mobile-tools.md](../../docs/plan/mobile-tools.md)。

## Clarifications

### Session 2026-11-13（可行性分析阶段，用户已确认）

- Q: 嵌进面板还是打开原版界面？ → A: **做法 A：点工具后服务端打开原版的合成界面**，客户端是原版 `CraftingScreen`，浮动面板照常叠在上面。不在面板里自己画合成格、不自己实现合成逻辑。
- Q: 是新物品还是直接用原版工作台？ → A: **新物品** `mobile_crafting_table`（移动工作台），像垃圾桶一样；配方中等以上难度（见下）。
- Q: 放哪里、放几个？ → A: **只在右侧工具区生效**，**右区里最多放一个**；左区、下区放得下但不生效、不计入限制；不考虑皮背包右区格子少，也不做每档背包的限制。
- Q: 和 053 的关系？ → A: 053 的页是"面板里展开的页"，本 feature 没有页：点工具直接打开原版界面；"打开工具"这条请求要设计成 055（移动熔炉）也能用的通用形式。

## 背景

浮动背包的右区现在有垃圾桶（021）和移动唱片机（053）：放进右区、光标为空时左键点它，会展开挂在面板右边的页。本 feature 加第三个右区工具：**移动工作台**。它不展开页，而是**直接打开一个原版的工作台界面**（3×3 合成格、配方书、结果格）：玩家在任何地方都能合成，不需要放下一个工作台方块。

这样做的好处：配方、配方书、JEI / EMI 的配方转移、合成统计与进度、别的模组加的配方与合成事件全部由原版界面与菜单提供，我们只负责"打开它"与"工具不在了就关掉它"。旅行者背包的合成升级是嵌在它自己的背包菜单里的（自己的格子与控件），我们的面板是叠在原版界面上的浮层，不能照搬，所以走打开原版界面这条路。

## 物品与配方

- 物品 `mobile_crafting_table`：中文"移动工作台"，英文 "Mobile Crafting Table"；堆叠 1；创造物品栏放在移动唱片机之后；进 `never_trash`；16×16 手绘占位贴图（用户之后可用同名文件替换）；提示文字说明"放进右区，左键点它打开工作台"。
- 配方（有序，`category: misc`，不加解锁进度）：`IDI` / `ATB` / `ICI`，`I` 铁锭、`D` 钻石、`A` 铁镐、`B` 铁斧、`T` 工作台、`C` 箱子（约 10 铁锭 + 1 钻石）。

## 使用方式

1. 把移动工作台放进面板右区（右区最多一个）。
2. 光标为空时左键点它（Shift / Ctrl / 拖拽按现有工具的规则不触发；右键仍是拿起）：客户端发"打开工具"请求，服务端校验后打开原版合成界面，标题与原版一样（"合成"）。
3. 在界面里合成：放进材料、取结果，一切是原版行为；关界面（Esc 或 E）时合成格里剩下的东西由原版退还给玩家。
4. 合成界面开着时再左键点右区的移动工作台：**关掉**这个界面（再点一下就关，像页的展开与收起）。
5. 打开期间，如果移动工作台离开了右区（被拿走、换了背包、背包丢了）：界面由服务端关掉。

## 已查证的事实（读 1.21.1 源码与本仓库）

- `CraftingMenu(int, Inventory, ContainerLevelAccess)` 是公开的；它的 `stillValid` 要求 `access` 所在位置是工作台方块；`ContainerLevelAccess.NULL` 的 `execute` 什么都不做，合成结果算不出来，所以要用 `ContainerLevelAccess.create(世界, 位置)`，并子类化重写 `stillValid`。
- `stillValid` 由服务端每 tick 询问，返回假就关掉界面；所以"工具不在了就关"可以直接写进这个方法。
- 菜单类型是原版的 `MenuType.CRAFTING`，所以客户端是原版 `CraftingScreen`（客户端用 `ContainerLevelAccess.NULL` 构造，只显示用），JEI / EMI 的配方转移与配方书按原版工作。
- 服务端找"按 B 打开的那只背包"：`BackpackRef.resolve(player)`（手 → 背 → 物品栏），右区在 `BACKPACK_CONTENTS` 的 `tools().right()`。
- 面板与别的原版菜单本来就能共存（面板叠在箱子界面上、`BackpackMenuBridge` 处理与菜单光标的往来）。
- 网络协议现在是 19；新增一个客户端到服务端的包就要升协议号；新物品要升数据修订（053 已升到 4）。

## 尚未验证（plan 阶段先查证；验证前不得声称已满足）

- 从面板里打开另一个容器菜单，会不会干扰面板自己的光标、会话与"面板打开的是哪只背包"的判定（`OpenSessions`、`BackpackGate`、`PanelCursor`）。
- 打开时玩家光标上拿着东西、或已经开着箱子等别的菜单：原版 `openMenu` 会关掉旧菜单并退还光标上的东西，是否符合预期。
- 工作台界面开着时面板上的点击（拖拽、快速转移、点右区工具）与原版界面的格子互不干扰。
- 创造模式、没有界面（宿主界面）、物品栏界面、箱子界面里点右区的移动工作台是否都能打开。
- "关界面后回到哪里"：原版关合成界面回到游戏（没有界面），此时宿主界面（019）是否把面板接回来。
- `stillValid` 每 tick 解析背包的开销（应当只在界面开着时才有）。
- 要把"打开工具"请求做成 055 也能用的形式（一个通用的包，带"哪种工具"）：确切形状在 plan 阶段定。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 移动工作台物品：合成、放进右区、每区一个 (Priority: P1)

玩家用配方合成移动工作台，放进面板右区；右区最多放一个；放在左区或下区没有效果。

**Why this priority**: 没有物品就没有工具。

**Independent Test**: 创造栏取到；按配方合成；放进右区；再放第二个被拒并提示；放在左区或下区点它没有反应。

**Acceptance Scenarios**:

1. **Given** 配方表，**Then** 有一个有序配方，图样与材料与上面一致，结果 1 个；不加解锁进度。
2. **Given** 右区已有一个移动工作台，**When** 再放第二个，**Then** 被拒并提示"右区已经有一个移动工作台了"；同格替换允许；保存时已有多个的旧背包保留、不能再加。
3. **Given** 移动工作台在左区或下区，**Then** 点它不打开界面（也不计入右区的限制）。
4. **Given** 右区同时有垃圾桶、移动唱片机、移动工作台，**Then** 三者的限制互相独立，都能各放一个。
5. **Given** 中英文界面，**Then** 物品名与提示都有对应的语言键。

---

### User Story 2 - 点一下打开原版合成界面，合成、关掉 (Priority: P1)

玩家左键点右区的移动工作台，打开原版工作台界面；合成、取结果；关掉时剩下的材料退还。

**Why this priority**: 这是功能的目的。

**Independent Test**: 开发运行里造一只右区带移动工作台的背包；点它，界面打开；放进 4 块橡木板合成工作台、取走结果；关界面，合成格里剩下的东西回到物品栏；用 JEI 的"+"把配方转进合成格（若 JEI 在）；记录没验证的。

**Acceptance Scenarios**:

1. **Given** 右区有移动工作台、光标为空，**When** 左键点它，**Then** 打开原版合成界面（3×3 合成格、结果格、配方书），标题为原版的"合成"。
2. **Given** 界面开着，**When** 放入材料，**Then** 结果格显示正确的配方结果（原版逻辑），取走结果会扣料、退还剩余物品（如桶），并记合成统计。
3. **Given** 界面开着，**When** 用配方书或 JEI / EMI 转配方，**Then** 按原版工作（材料取自玩家物品栏）。
4. **Given** 界面开着，**When** 关闭它，**Then** 合成格里剩下的东西退还给玩家（原版行为），浮动面板照常。
5. **Given** 光标上拿着东西，**When** 点移动工作台打开界面，**Then** 光标上的东西不丢（原版 `openMenu` 的退还行为）。
6. **Given** 创造模式，**Then** 同样能打开与使用。

---

### User Story 3 - 再点一下关掉；工具不在了就关掉 (Priority: P2)

合成界面开着时再点一下移动工作台就关掉；移动工作台离开右区（拿走、换背包）时界面被关掉。

**Why this priority**: 不让"工具已经不在了，界面还开着"成为漏洞（用掉一个本该没有的工作台）。

**Independent Test**: 界面开着再点一下关掉；界面开着把右区的移动工作台拿出来，界面在下一 tick 关掉；换了背包（按 B 解析出的变了）也关掉。

**Acceptance Scenarios**:

1. **Given** 移动工作台打开的界面开着，**When** 再左键点右区的移动工作台，**Then** 界面关掉。
2. **Given** 界面开着，**When** 移动工作台被拿出右区（或右区没有了），**Then** 服务端在下一个 tick 关掉界面。
3. **Given** 界面开着，**When** 按 B 解析出的背包换了，或背包丢了，**Then** 界面被关掉。
4. **Given** 玩家死亡、下线，**Then** 界面随之关闭（原版行为）。

---

### User Story 4 - 数据与版本兼容 (Priority: P2)

新物品让数据修订 4 → 5；新增"打开工具"请求让协议 19 → 20；老背包照常载入；快照（030）能保存与恢复带移动工作台的背包。

**Why this priority**: 项目一贯的数据与联机底线。

**Acceptance Scenarios**:

1. **Given** 本 feature，**Then** 数据修订递增（4 → 5）并在 DELIVERY 写明理由（新的只能存在背包里的物品种类），同改 `DataRevisionTest` 与写死 4 的历史测试；协议号升到 20（新的客户端到服务端的包），同改写死 19 的历史测试。
2. **Given** 旧背包，**Then** 照常载入、功能不变；带移动工作台的背包快照恢复一致。
3. **Given** 协议号不同的两端，**Then** 按现有握手被拦下（既有机制，不新增）。

---

### Edge Cases

- **请求被伪造**（客户端发"打开工具"但右区没有）：服务端校验失败就什么也不做，不报错；不信任客户端说的"有"。
- **已经开着别的菜单**（箱子、熔炉……）：打开移动工作台会关掉旧菜单（原版 `openMenu` 的行为，旧菜单的光标物品退还），符合"我现在要用工作台"的意图；记入 DELIVERY。
- **已经开着移动工作台的界面再发"打开"**：视为关掉（User Story 3）。
- **受保护的背包**（更新版本保存的，040）：打开工作台是只读，不改背包数据，所以允许。
- **服务端没有这个模组 / 协议不同**：被握手拦下，不会走到这里。
- **与别的模组的菜单**：本 feature 只开原版 `CraftingMenu`，不碰别的模组的界面。
- **降级**：不支持（口径不变）。

## Requirements *(mandatory)*

### Functional Requirements

**物品、配方与放置**

- **FR-001**: MUST 有物品 `mobile_crafting_table`（堆叠 1），中英文名与提示；创造栏在移动唱片机之后；进 `never_trash`；16×16 手绘占位贴图与模型。
- **FR-002**: MUST 有一个有序配方：`IDI` / `ATB` / `ICI`（`I` 铁锭、`D` 钻石、`A` 铁镐、`B` 铁斧、`T` 工作台、`C` 箱子）；`category: misc`；不加解锁进度。
- **FR-003**: 移动工作台 MUST 只在**右侧工具区**生效；右区里 MUST 至多放一个（沿用 `ToolSingleRules`，服务端校验，客户端预览同口径，被拒时有提示 `limit.mobile_crafting_table`；同格替换允许；旧背包已有多个时保留、不能再加）；放在左区或下区放得下但不生效、不计入限制；该限制 MUST 与垃圾桶、移动唱片机的限制互相独立。

**打开与关闭**

- **FR-004**: 左键点右区的移动工作台（光标为空、无 Shift / Ctrl / 拖拽）MUST 向服务端发"打开工具"请求；右键 MUST 仍是拿起。请求 MUST 是通用形式（带"哪种工具"），055 的熔炉复用。
- **FR-005**: 服务端收到请求 MUST 校验：按 B 解析出的背包（`BackpackRef.resolve`）的右区确有这个工具；通过才打开，**不通过什么也不做**。
- **FR-006**: 打开的 MUST 是原版 `CraftingMenu` 的子类（`MenuType.CRAFTING`，标题为原版的"合成"）：用 `ContainerLevelAccess.create(世界, 玩家位置)` 取得合成结果，重写 `stillValid`；客户端 MUST 是原版 `CraftingScreen`；MUST NOT 自己实现合成逻辑或在面板里画合成格。
- **FR-007**: `stillValid` MUST 在每次被询问时核对"按 B 解析出的背包的右区仍有移动工作台"（并保留玩家存活等原版条件）；不再满足时界面被关闭。
- **FR-008**: 合成界面开着时，再次收到"打开"请求 MUST 关掉这个界面。
- **FR-009**: 打开期间的一切合成行为（结果格、取走、扣料、剩余物品、配方书、JEI / EMI 转移、统计、进度、关闭时的退还）MUST 保持原版行为。

**数据与兼容**

- **FR-010**: MUST 新增一个客户端到服务端的"打开工具"包，协议号 19 → 20；MUST NOT 新增存储字段、配置项、依赖、mixin；数据修订 MUST 递增（4 → 5）并在 DELIVERY 写明理由，同改 `DataRevisionTest` 与写死 4 / 19 的历史测试；011～053 的其余测试不改。
- **FR-011**: 老背包 MUST 照常载入；带移动工作台的背包做快照 MUST 保存与恢复一致。

**测试与文档**

- **FR-012**: 右区"各至多一个"（用 `ToolSingleRules`，已有的测试补一条覆盖移动工作台的接线）、"打开 / 关闭 / 校验"的决策表（纯逻辑：给定"右区有没有、界面开没开、请求种类"，得出"打开 / 关闭 / 忽略"）MUST 有单元测试；物品、模型、贴图、配方、语言键用资源测试；接线用源码文本检查；游戏里验证打开、合成、关闭、拿走工具时关闭（宪法 V）。
- **FR-013**: 文档 MUST 更新：`README.md` / `README_CN.md`（移动工作台一节）、`docs/plan/mobile-tools.md` 的状态、本 feature 的 `DELIVERY.md`。

### Key Entities *(include if feature involves data)*

- **移动工作台（Mobile crafting table）**：新物品，无状态；只在右区生效，每个背包右区至多一个。
- **打开工具请求（Open tool request）**：客户端到服务端的包，带"哪种工具"（本 feature 只有工作台；055 加熔炉），不带任何物品或背包数据。
- **移动工作台菜单（Mobile crafting menu）**：服务端的 `CraftingMenu` 子类，只改"位置与有效性"。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 决策表的单元测试覆盖：右区有 / 没有工具、界面开 / 没开、种类已知 / 未知，全部得出预期（打开、关闭、忽略）。
- **SC-002**: 游戏里（容器自动验证）：点移动工作台，打开原版合成界面；放材料得结果、取走后材料被扣；关界面材料退还；再点一下关掉；开着时把工具拿出右区，界面在 1 秒内关闭；右区放第二个被拒；左区、下区的工具点了没有反应；记录没验证的。
- **SC-003**: 一个没有移动工作台的玩家（伪造请求的路径）：服务端日志无错误、不打开界面（用纯逻辑决策表覆盖，游戏里不伪造）。
- **SC-004**: `./gradlew compileJava test` 通过；`DependencyRulesTest` 通过；协议号为 20；数据修订为 5；011～053 的测试除写死 4 与 19 的断言外不改而通过。

## Assumptions

- 配方是第一稿，用户可以只改一个 JSON；贴图是占位手绘，用户之后替换。
- 打开的界面里材料取自**玩家的物品栏**（原版行为），不自动从背包主区域取料；用面板把背包里的东西拖进合成格仍可用。
- 打开任何时候都允许（包括开着别的菜单时），"关掉旧菜单、打开新的"。
- 不做熔炉（055）、不做高炉与烟熏炉、不做每档背包的限制。
- "打开工具"请求的确切线格式在 plan 阶段定，要点是通用、不带客户端声称的物品信息。
