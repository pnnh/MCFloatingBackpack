## 实现了什么

- 面板可见时，在集成终端物品存储页或 AE2 的 ME 终端网格里 Ctrl+点击一个条目：服务端取一组（该物品的最大堆叠）放进背包；放不下的退回网络；退不回的放进玩家物品栏，再不行掉在脚下（WARN）。
- 手势挂在 `QuickTransferInput.beginFromScreen`：先问客户端识别器注册表，认得就发新请求并吞掉这次按下（不进入拖动手势，所以没有拖动）。
- 服务端：沿用 059 的门禁（`TAKE_FROM_CONTAINER`，OFF 拒绝并提示）；桥接口加 `handlesTake/take/giveBack`，`BridgeDispatch.tryTake/tryGiveBack` 与存入同规则（版本门、有效档位 FULL、出错关闭、返回值合法性检查）。
- 集成终端：`channel.extract(原型, 不比数量的精确匹配, false)`；AE2：用菜单自己的 `handleInteraction(serial, PICKUP_OR_SET_DOWN)` 把携带物当中转，AE2 自己判电力与权限，我们不引用它们的类型。
- AE2 进范围表 `[19.2.0, 19.3.0)`，`mods.toml` 可选依赖 `[0,)`，`build.gradle` `compileOnly ae2:19.2.20`（`transitive = false`，**不需要 GuideME**，T002 的探针类证实）；防漂移测试扩到 AE2。README 两份兼容表更新。

## 与 spec / plan 的偏离

- **集成终端的条目不是菜单 `Slot`**（research R14）：plan 阶段读字节码时把 Shift+点击用的"玩家物品栏格子"误当成了存储格子，游戏里第一次 Ctrl+点击条目什么也没发生才发现。改为：识别器接口收鼠标坐标；集成终端用公开的 `ContainerScreenTerminalStorage.getStorageSlotIndexAtPosition` 与页客户端的 `getSlot(channel, index)`；AE2 的 `RepoSlot` 才是真格子（用从 `QuickTransferInput` 抽出的同一个命中测试 `ScreenSlots`）。
- AE2 范围放宽到所有显示 ME 网格的终端（规格 FR-004 已据此修订）；请求不带数量（FR-002 已修订）。

## 用户真机反馈后的修复（2026-11-23）

用户在真机上发现：集成终端里数量不足一整组的条目（沙子 57、白桦原木 27、陶瓦 60 …）Ctrl+点击取不出来，只有 ≥ 64 的（原木 192、楼梯 64）可以。**根因**：`IntegratedTerminalsBridge.take` 用了 `getExactMatchCondition()`，这个条件连**数量**一起匹配——网络里的数量比原型的数量（我们要的一整组）少时，提取什么也不返回。我的容器验证只测了数量 ≥ 一组的条目；末影珍珠 40 → 16 → 16 → 8 那一轮最后的 8 个其实没取出来（当时把它当成"点得太快"），**之前报告里"不足一组 ✓"的说法是错的**。修复：改用 `getExactMatchNoQuantityCondition()`（只匹配物品与数据，数量只是"要多少"；集成终端自己的取物处理也是这个条件），接线测试断言不再出现 `getExactMatchCondition()`。AE2 不受影响（`PICKUP_OR_SET_DOWN` 取"至多一组"，容器里取 60 个成功）。

用户还报告：在集成终端里普通左键拿起条目、想放进面板时，光标上的物品被盖在面板下面（只露出一部分），放不进面板。**已在容器里复现、定位并修复（2026-11-23）**。

- **根因**：集成终端里"拿起"的东西**根本不是菜单的携带物**（`containerMenu.getCarried()` 一直是空的）。它在页对象 `TerminalStorageTabIngredientComponentClient` 里记一个"激活条目"（`activeSlotId` + `activeSlotQuantity`），由集成终端自己的屏幕在鼠标处画出来，直到点进一个格子才发包。而面板的光标逻辑只认菜单携带物，所以面板既不知道玩家手里有东西，也没有画它；集成终端画在 z≈232，面板在 800 以上，于是盖住了。（之前"读源码判断它是标准携带物"是错的，源码里只在物品/流体处理器里 `setCarried`；证据是容器里加了临时日志：拿着珍珠时 `screenCarried`、`playerCarried` 都是 `minecraft:air`，屏幕和玩家的菜单是同一个对象。）
- **修复**：`NetworkTerminalClient` 加两个默认方法 `held(screen)`（读页对象的公开 getter：`getActiveSlotId`、`getActiveSlotQuantity`、`getSlot`）与 `release(screen)`（`resetActiveSlot()`）；面板渲染在光标为空时用它在鼠标处**再画一份**（在面板之上，同一位置）；新类 `NetworkHeldDrop`：面板正文上的左键按下（不含拖动条、关闭键、缩放角；没有确认框）且手里有这样的物品、菜单携带物为空时，发 `BackpackNetworkTakePayload`（**新增 `amount` 字段**，0 = 一整组，Ctrl+点击仍是 0），并让集成终端放开激活条目；服务端把数量夹到"至多一组"（`NetworkTakeRules.amountFor(ops, what, requested)`），桥的 `take` 收到的 `what` 的数量就是要取的数量，`BridgeDispatch` 以它作为"不得多于"的上限。协议号不变（22，060 尚未发布，载荷格式在本特性内修改）。
- **容器验证**（`mcfb-c1`，集成终端 1.11.2，面板 F9 显示）：① 普通点击拿起末影珍珠（40 个）→ 鼠标移到面板上，珍珠与数量 "40" 画在面板之上（修复前整个消失）；② 点面板格子 → 背包里出现 16 个末影珍珠（珍珠一组 16，数量被夹到一组），网络总量 177 → 161，鼠标上没有残留；③ 再拿起圆石（128，激活数量 64）移到面板右下部分，画在面板上，点击 → 面板里 64 个圆石，网络总量 161 → 97；日志里没有 ERROR / "changed the item total"。
- **没验证 / 取舍**：IT 里手里拿着的数量大于一组时（珍珠 40）只存一组（16），剩下的仍留在 IT 的网络里、手里的激活条目被放开（不会丢，也不会多出）；点面板其它区域（工具区、标题栏）的行为是：只有"正文"算放入，拖动条、关闭键、缩放角照旧；放入不指定格子（按背包主区域自动放，和 Ctrl+点击一致）；IT 自己按住拖动分摊（`terminalDragSplitting`）时松手落在面板上没有专门处理。AE2 的拿起是菜单携带物，面板原本就跟随，不受影响。

## 已知局限（如实）

- 取出与放入背包之间没有事务：集成终端的 `extract` 若在网络已减少后才抛异常，物品可能不在背包里；兜底的方向是"不丢"（退回网络/玩家物品栏/脚下），出错路径沿用 058 的"关闭该兼容 + ERROR + 通知 op"。
- 客户端按自己安装的版本判断：范围外又被服务端 `allowUntestedVersions` 强制启用时，客户端不拦截手势，玩家只能用 013 的两步法（规格已写明）。
- 集成终端界面里默认的 `B` 键仍被它的"平衡合成网格"吞掉（058 已记录），验证用 F9。
- **AE2 终端存入的通用路径在日志里留下的"Quick transfer into open container changed the item total"ERROR 仍在**（012 起就有、物品实际正确进入网络，本次又看到 5 次）；不在 060 范围，可单独修。
- AE2 终端里合成网格、样板格不是 `RepoSlot`，不会被识别（不会误取）。
