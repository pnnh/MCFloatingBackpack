# Feature Specification: 按模组的服务端档位

**Feature Branch**: `059-server-compat-levels`

**Created**: 2026-11-20

**Status**: Draft

**Input**: 用户（2026-11-20）在 058 的讨论里提出：客户端把某个模组设为 GENERIC 关不掉服务端的专用适配，之前的 feature 里这类场景不止一处，是否要有服务端配置。分析的结论与决定记在 memory `project_server_compat_levels_059` 与 [docs/plan/third-party-compat.md](../../docs/plan/third-party-compat.md)（**不重新讨论**）：单开 059；服务端配置取与客户端同语法；服务端做决定时取两边档位中更严的；不改协议，服务端拒绝时用聊天提示；058 之后原计划的"终端 → 面板"反向顺延为 060。相关：020（客户端档位与服务端门禁 `ServerCompatGate` 的预留）、012/013（向打开的容器投递、从容器取出、光标交互）、033/034（Curios、Accessories 的背着来源）、058（集成终端桥、`[compat]` 服务端配置节）。

## Clarifications

### Session 2026-11-20（方案阶段，用户已确认）

- Q: 要不要做服务端档位、放在哪个 feature？ → A: 要；单开 059（058 只在 README 如实写明限制），反向顺延 060。
- Q: 服务端配置用什么形式？ → A: 与客户端同语法的 `modid=LEVEL` 列表（`[compat].modLevels`），原版不可配置，未列出的为 FULL；只做按模组的黑名单语义，不做白名单、不按玩家或权限细分。
- Q: 服务端档位与客户端档位怎么合并？ → A: 服务端做决定时取两者中更严的一个（OFF 严于 GENERIC 严于 FULL）。单人游戏的集成服务器能读到客户端配置，所以现有的 `curios=OFF` 之类的行为不变；专用服务器上客户端配置没加载，只有服务端档位。
- Q: 服务端各档位是什么意思？ → A: FULL 正常；GENERIC 关闭服务端的专用适配（集成终端桥、Curios 与 Accessories 背着来源），保留 012 的通用路径；OFF 让服务端对该模组的菜单拒绝一切物品交换，并同时关闭其专用适配。
- Q: 服务端拒绝时怎么让玩家知道？ → A: 不改协议，服务端给该玩家发一条聊天提示；对每个玩家每次打开界面限流；客户端不新增包、不改面板的显示逻辑。

## 背景

现状（已核对源码）：

- **服务端的物品交换入口**：向打开的容器投递物品（`BackpackQuickTransferPayload`）、从容器取出（`BackpackTakeFromContainerPayload`）、合并面板光标（`MergePanelCursorPayload`）、用菜单携带物的光标点击、拖动与丢进垃圾桶（`BackpackClickPayload`、`BackpackCursorGesturePayload`、`BackpackTrashPayload` 两处）都先问 `ServerCompatGate.allows(Action, 菜单所属模组)`，而这个判断**恒为允许**。每一处的询问都在服务端状态改变之前。垃圾桶"发送"入口（`BackpackTrashSendPayload`）只对原版菜单工作，已经拒绝其它模组的菜单。
- **背着来源**：033/034 的 Curios、Accessories 背着的背包由服务端决定"`B` 键打开哪只背包"，它们是否生效读的是**客户端**配置 `compat.modLevels`；专用服务器上客户端配置没有加载，所以恒为 FULL（代码注释自己写了这一点）。单人游戏里同一个进程能读到客户端配置，所以 `curios=OFF` 有效，专用服务器上无效。
- **058 的集成终端桥**由版本门、`allowUntestedVersions`、出错关闭三者决定是否启用，没有按模组的开关。
- **精妙背包、旅行者背包**：`compat/` 下没有它们的专用代码，只走 012 的通用路径；客户端 `ContainerScreenCompat` 里对它们有按类名的客户端判断，服务端没有按模组 id 的分支。
- 服务端配置文件已经存在（日志级别、057 的 `[snapshots]`、058 的 `[compat]`），本 feature 不需要新建基础设施。
- 宪法 VII：关系到物品移动、依赖该设置的判断必须在服务端做，客户端设置不是安全边界。

结果是：服主**没有办法**在专用服务器上说"不许面板碰某个模组的界面"，也没有办法单独关掉某个专用适配；单人游戏和专用服务器对同一个 `curios=OFF` 的反应不一致。

本 feature 做三件事：**服主说了算**（服务端档位）、**两边一致**（取更严者，单人游戏现有行为不变）、**说得清**（拒绝时给玩家提示，README 写明含义）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 服主禁止面板与某个模组的界面交换物品 (Priority: P1)

服主发现某个模组的界面在面板转移物品时有问题（吞物品、被刷物品），在服务端配置里写上 `modLevels = ["somemod=OFF"]`。之后玩家在那个模组的界面上 Ctrl+点击面板里的物品、从界面里取出物品、用面板光标点击，服务端都不做，物品不动；玩家收到一条聊天提示，说明这台服务器不允许面板与该模组的界面交换物品。原版界面和别的模组不受影响。

**Why this priority**: 这是服主唯一的"安全阀"，也是 020 当初预留门禁的目的；没有它，一个有问题的第三方界面只能靠玩家各自改客户端配置。

**Independent Test**: 服务端配置 `modLevels = ["sophisticatedstorage=OFF"]`，在精妙存储的箱子上 Ctrl+点击面板里的物品：物品留在面板里、收到提示；原版箱子上照常工作；去掉配置后精妙存储的箱子恢复。

**Acceptance Scenarios**:

1. **Given** 服务端配置 `somemod=OFF`，玩家打开该模组的容器界面，**When** 玩家 Ctrl+点击面板里的物品，**Then** 物品不被移动（背包与容器都不变），玩家收到一条说明"这台服务器不允许面板与 somemod 的界面交换物品"的聊天提示。
2. **Given** 同上，**When** 玩家在该界面里 Ctrl+点击容器格子想取出物品到面板，**Then** 同样不做、同样提示。
3. **Given** 同上，**When** 玩家用面板光标点击、拖动、合并或丢进垃圾桶且涉及该模组菜单的携带物，**Then** 不做，同样提示。
4. **Given** 同上，**When** 玩家打开原版箱子或另一个未被列出的模组的界面，**Then** 行为与改动前完全一致。
5. **Given** 同一次打开某个被拒绝的界面，**When** 玩家连续做多次被拒绝的操作，**Then** 提示只发一次；关闭后再打开该界面，再次被拒绝时再发一次。
6. **Given** 服务端配置 `somemod=OFF`，**When** 服主改配置后（不重开世界）玩家再操作，**Then** 新的档位立即生效。

### User Story 2 - 服主关闭服务端的专用适配，保留通用路径 (Priority: P1)

服主不想让面板对某个模组做专用处理，但通用的 Ctrl+点击仍然想要。他把该模组设为 `GENERIC`：集成终端（058）不再由桥直接存入网络，回到只走通用路径（在集成终端的存储页上无效果）；Curios、Accessories 的后背槽里的背包不再被当作"背着的背包"，`B` 键不再从那里找背包。

**Why this priority**: 专用适配是服务端代码，出了问题只有服主能在服务端关；以前专用服务器上 `curios=OFF` 完全无效。

**Independent Test**: 专用服务器上 `modLevels = ["integratedterminals=GENERIC"]`：集成终端上 Ctrl+点击面板物品不存入网络，改回 FULL 又能存入；`modLevels = ["curios=OFF"]`：把背包放进 Curios 后背槽，`B` 键不再认它。

**Acceptance Scenarios**:

1. **Given** 服务端 `integratedterminals=GENERIC` 且版本在范围内，**When** 玩家在集成终端的物品存储页 Ctrl+点击面板物品，**Then** 桥不被调用，物品不存入网络（通用路径在该页无效果，物品留在面板里）。
2. **Given** 服务端 `curios=GENERIC` 或 `OFF`，玩家把背包放在 Curios 后背槽，**When** 玩家按 `B`（或服务端按背着来源查找背包），**Then** Curios 槽里的背包不算背着的；其它来源（胸甲槽、手上、物品栏）不受影响。
3. **Given** 同上对 Accessories，**Then** 同样。
4. **Given** 服务端把某模组设为 `GENERIC` 而该模组没有专用适配（例如精妙存储），**When** 玩家在它的界面上 Ctrl+点击，**Then** 行为与 FULL 完全一样（通用路径照常）。
5. **Given** 服务端 `somemod=OFF`，**Then** 它的专用适配（若有）也被关闭（OFF 包含 GENERIC 的效果）。

---

### User Story 3 - 单人游戏与客户端配置的现有行为不变，取更严者 (Priority: P2)

玩家在单人游戏里本来就用客户端配置 `compat.modLevels`（例如 `curios=OFF`）。这些设置继续有效。在多人服务器上，服务端档位与（能读到的）客户端档位取更严的：专用服务器只看服务端的；局域网房主的集成服务器两个都看。

**Why this priority**: 防止这次改动让现有的单人游戏设置失效，是向后兼容的底线。

**Independent Test**: 单人世界里客户端配置 `curios=OFF`、服务端配置为空：行为与改动前相同；两边都设时取更严的一个；专用服务器上客户端配置不影响服务端。

**Acceptance Scenarios**:

1. **Given** 单人游戏，客户端 `modLevels` 里 `curios=OFF`，服务端配置没有列出 curios，**When** 玩家按 `B`，**Then** 结果与改动前一样（Curios 槽里的背包不算背着的）。
2. **Given** 客户端 FULL、服务端 OFF，**Then** 有效档位是 OFF；**Given** 客户端 OFF、服务端 FULL，**Then** 有效档位是 OFF（集成服务器能读到客户端配置时）；**Given** 客户端 GENERIC、服务端 OFF，**Then** OFF。
3. **Given** 专用服务器，**Then** 服务端档位就是有效档位，不受任何玩家的客户端配置影响（客户端配置也不会被服务端读到）。
4. **Given** 服务端配置里没有列出某模组、客户端也没有，**Then** FULL。

---

### User Story 4 - 配置写错、热改、原版不可配置 (Priority: P2)

服主把配置写错了（缺等号、未知档位、重复项、写了 `minecraft`）。错误项只让它自己失效，不影响别的项；写进服务器日志。改配置后不需要重开世界。

**Why this priority**: 管理员配置的容错；沿用客户端同样的规则，避免两套行为。

**Independent Test**: 配置里混着正确与错误的项，核对只有错误项被忽略、日志说明原因；改配置后不重开世界新的档位生效；`minecraft=OFF` 被忽略。

**Acceptance Scenarios**:

1. **Given** 配置里 `["sophisticatedstorage=OFF", "bad entry", "x=NOPE", "sophisticatedstorage=GENERIC", "minecraft=OFF"]`，**Then** 只有格式正确、档位已知的项生效，其余写服务器日志（说明原因，与客户端配置的报告同样的措辞）；重复项后者生效；`minecraft` 被忽略。
2. **Given** 服务器已在运行，**When** 服主改了配置并保存，**Then** 下一次需要判断时就用新的值（无需重开世界）。
3. **Given** 服务端配置未载入（例如服务器刚起），**Then** 一律 FULL，不报错。

---

### User Story 5 - README 与测试说清并守住含义 (Priority: P2)

README 里 058 写的"按模组的档位是客户端配置，专用服务器上……暂时不能单独关闭"改成新的说明：有服务端配置、取更严者、各档位在服务端和客户端各是什么意思。自动测试守住有效档位、允许表、限流、接线。

**Why this priority**: 文档写错会误导服主；接线测试防止以后新增的服务端入口绕过门禁。

**Independent Test**: 读 README 两份的说明与本 spec 的含义一致；接线测试通过。

**Acceptance Scenarios**:

1. **Given** README.md 与 README_CN.md，**Then** 不再说"暂时不能单独关闭"，写明服务端配置的位置与语法、有效档位取更严者、三档在服务端的含义、拒绝时玩家会收到提示。
2. **Given** 新增一个服务端入口不经过门禁，**Then** 接线测试失败（至少覆盖现有 6 个入口都经过同一个门禁）。

### Edge Cases

- **客户端不知道服务端的档位**：客户端面板仍然显示、手势仍然发出，只是服务端不做并回一条聊天提示（不改协议的代价）。提示文字要让玩家明白"这是服务器的设置"，不是模组坏了。
- **服务端 OFF 而玩家已经打开了该界面**：下一次被拒绝的操作才发提示（每次打开至多一条）；已经发生的转移不撤销。
- **服务端 GENERIC/OFF 的 Curios/Accessories 与客户端渲染不一致**：客户端仍按自己的配置绘制背部层，可能画出服务端不认的背包；`B` 键找不到背着的背包时沿用现有的"没有背包"的反应。不为此改协议。
- **玩家的背包正放在被关闭的来源里**（例如 Curios 槽）：不删除、不移动，只是不再被当作背着的；改回档位或换到别的槽就恢复。
- **热改档位的瞬间有操作在进行**：每个操作在入口判断一次，不做中途回滚。
- **同一个模组既在客户端被设为 OFF 又在服务端 FULL**：专用服务器上客户端设置只影响客户端（面板不在那个界面显示）；单人游戏里集成服务器取更严者，也是 OFF。
- **菜单的所属模组无法判断**（没有注册名的菜单）：按原版处理（与 020 一致，`MenuOwner` 给出 `minecraft`），不被服务端档位影响。
- **专用适配被档位关闭后又被版本门打开**：两个条件都要满足才启用（`FULL` 且版本门通过）；任一不满足就不启用。
- **提示限流的状态**：只在内存里，玩家下线、服务器重启后清空；不写盘。

## Requirements *(mandatory)*

### Functional Requirements

**服务端配置与解析（US4）**

- **FR-001**: 服务端配置 MUST 提供 `[compat].modLevels`：字符串列表，每项形如 `modid=LEVEL`（`LEVEL` 为 FULL、GENERIC、OFF），语法、解析、错误项的处理 MUST 与客户端配置的同名项一致（复用同一份解析规则）：格式错误、未知档位、重复项（后者生效）、`minecraft` 只让该项自己无效，不影响别的项。默认为空列表。
- **FR-002**: 配置注释 MUST 写明：三档在**服务端**的含义（FULL 正常；GENERIC 关闭服务端的专用适配，保留通用路径；OFF 服务端拒绝与该模组界面的一切物品交换并同时关闭其专用适配）；原版不可配置；未列出的为 FULL；与客户端配置的关系（取更严者）；改动不需要重开世界；一个例子。
- **FR-003**: 错误项 MUST 写服务器日志（WARN，措辞与客户端配置的报告一致，并说明这是服务端配置）；同一份配置内容的同一个问题 MUST NOT 反复写。服务端配置未载入时 MUST 视为空列表（全部 FULL）。
- **FR-004**: 服务端 MUST 在每次需要判断时读取当前的配置值，改动保存后无需重开世界即生效。

**有效档位（US3）**

- **FR-005**: 服务端做决定时使用的**有效档位** = 服务端档位与（该进程里已加载的）客户端档位中更严的一个，严格程度 OFF > GENERIC > FULL。专用服务器上客户端配置不存在，有效档位就是服务端档位。原版（`minecraft`）恒为 FULL。
- **FR-006**: 在没有服务端配置项的情况下（列表为空），所有现有行为 MUST 与 059 之前完全一致，包括单人游戏里客户端 `modLevels` 对 Curios、Accessories 背着来源的作用。

**服务端各档位的含义（US1、US2）**

- **FR-007**: 有效档位为 **OFF** 的模组：`ServerCompatGate` MUST 对该模组的菜单的每一种动作（向容器投递、从容器取出、合并光标、用菜单光标）返回"不允许"；6 个现有入口都 MUST 经过它，且询问发生在服务端状态改变之前（现状已满足，MUST 保持）。被拒绝时背包与容器的内容 MUST 保持不变。
- **FR-008**: 有效档位为 **GENERIC 或 OFF** 的模组，其服务端专用适配 MUST 不启用：058 的集成终端桥不被调用（档位是桥启用的第四个条件，与版本门、`allowUntestedVersions`、出错关闭并列，任一不满足则不启用）；Curios、Accessories 的背着来源在服务端不生效（背着来源生效与否问**服务端有效档位**，只有 FULL 才生效）。
- **FR-009**: 有效档位为 **GENERIC** 的模组仍 MUST 允许 012 的通用路径与光标交互；没有专用适配的模组上 GENERIC 与 FULL 完全一样。
- **FR-010**: 客户端渲染侧（Curios、Accessories 的背部层等）MUST 继续只读客户端配置，不受服务端档位影响；客户端的档位含义与 020 一致，不变。
- **FR-011**: 原版菜单（含创造模式物品栏界面）MUST NOT 受服务端档位影响（宪法 VII：原版第一优先、不可关闭）。

**拒绝时的提示（US1）**

- **FR-012**: 服务端因 OFF 拒绝一次物品交换时，MUST 给该玩家发一条聊天提示，说明这台服务器不允许浮动背包与哪个模组的界面交换物品（含模组 id）。提示 MUST 走语言文件（中英文）。
- **FR-013**: 提示 MUST 按（玩家，打开的界面）限流：同一个玩家对同一次打开的界面至多一条；界面关闭后再打开，再次被拒绝时可以再发。限流状态 MUST 只保存在内存，玩家下线时清除。拒绝本身 MUST 写一条 DEBUG 日志（含玩家、模组 id、动作）。
- **FR-014**: 本 feature MUST NOT 新增网络包、MUST NOT 改协议号（保持 21）、MUST NOT 改客户端面板的显示逻辑（面板仍显示，手势仍发出，由服务端拒绝并提示）；若实现中发现必须改协议才能做对，MUST 在 plan 里说明理由再动。

**文档与测试（US5）**

- **FR-015**: README.md 与 README_CN.md 里 058 写的"按模组的档位是客户端配置……暂时不能单独关闭"MUST 改成新的说明：服务端配置的位置（`serverconfig/mcfloatingbackpack-server.toml` 的 `[compat]` 节）与语法、有效档位取更严者、三档在服务端的含义、拒绝时的提示、客户端 GENERIC 对服务端现在的作用；兼容表后的说明同步。
- **FR-016**: 系统 MUST 有自动测试：有效档位取更严者（全部 3×3 组合）、各动作 × 各档位的允许表、限流、解析复用同一份规则、配置注释与语言键、接线（6 个入口都问同一个门禁；门禁读服务端有效档位；Curios/Accessories 来源在服务端问服务端有效档位；桥问档位）。

### Key Entities *(include if feature involves data)*

- **服务端档位表**：服务端配置里解析出的"模组 id → 档位"，与客户端的同形（未列出为 FULL，原版恒 FULL）。
- **有效档位**：对一个模组，服务端档位与客户端档位（若已加载）中更严的那个。
- **服务端门禁**：对（动作，菜单所属模组）回答"允许吗"，OFF 为否；是 6 个服务端入口共用的唯一判断。
- **拒绝提示状态**：每个玩家当前已经提示过的（模组，打开的界面）记录，只在内存里。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 服务端配置 `somemod=OFF` 后，在该模组的界面上，面板与界面之间 6 种服务端交换动作 **0 次**成功（物品与容器内容都不变），每次打开界面玩家**恰好收到 1 条**提示；原版界面与其它模组的行为与改动前一致。
- **SC-002**: 专用服务器上 `curios=OFF`（或 `GENERIC`）使 Curios 后背槽里的背包**不再**被当作背着的，改回 FULL 后恢复；改动后**不重开世界**即生效。
- **SC-003**: 服务端配置为空时，现有的全部自动测试与单人游戏的 `curios=OFF` 行为 **100% 不变**。
- **SC-004**: 有效档位的 9 种组合（服务端 3 档 × 客户端 3 档）有测试，结果全部等于"更严者"。
- **SC-005**: 一份混有正确与错误项的配置，只有错误项被忽略，日志里每个错误项一条说明；没有任何一项错误导致其它项失效。
- **SC-006**: 集成终端在 `integratedterminals=GENERIC` 时存入**不**工作，改回 FULL 时工作；两种状态各在游戏里验证一次。

## Assumptions

- 集成服务器（单人游戏、对局域网开放）与客户端同一个进程，能读到客户端配置；专用服务器读不到，这是 020 就有的事实，本 feature 据此定"取更严者"。
- 玩家的客户端不知道服务端的档位；在服务端 OFF 的界面上客户端面板仍会显示并发出手势，服务端拒绝并提示。这是不改协议的有意代价（已与用户确认）；若以后要让客户端提前隐藏面板，另开 feature。
- 服务端 `Curios`/`Accessories` 的背着来源被关闭而客户端仍按自己的配置绘制，会出现"画出了背包但 `B` 键找不到"的不一致；本 feature 不处理（改动需要协议）。
- 精妙背包、旅行者背包在 `compat/` 下没有专用代码，服务端没有按模组 id 的分支；它们在服务端只受 OFF（拒绝交换）的影响，GENERIC 与 FULL 无区别。
- `MenuOwner` 给出的"菜单所属模组"（菜单类型的命名空间）沿用，不改它的判定规则。
- 配置的读取成本很小（沿用客户端同样的"列表对象不变就不重新解析"的做法），不会成为每次交换的负担。
- 058 的 `CompatRuntimeState` 与 `BridgeDispatch` 保持可测的纯逻辑；"档位"作为桥启用的第四个条件放在哪个类里由 plan 决定。
- 终端 → 面板的反向（集成终端与 AE2）是 060，不在本 feature。
