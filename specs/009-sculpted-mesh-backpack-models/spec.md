## 补录说明

本 spec 与前面的 spec 不同：它**不是先写规格再实现**，而是对已经落地的实现做事后补录（见 `git log` 中 `504a56b` 至 `66140a8` 的提交）。因此：

- 凡写成"必须"的要求，描述的是**当前源码实际表现出的行为**；
- 实现后才发现、或尚未在游戏里验证的部分，不写成已满足，而是放进"已知限制"；
- 实现层面的事实（文件、加载方式、数值）只在 Assumptions 与 `plan.md`/`research.md` 里记录，用于追溯，不作为玩家可见的验收条件。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 五个等级都是精致的背包，图标、手持、背上是同一套外形 (Priority: P1)

玩家拿到任意等级的浮动背包（皮革、铁、金、钻石、下界合金）时，在物品栏图标、手持、背在身上三种场景里，看到的是同一只做工精致的背包：有包身、顶盖、前口袋、两侧口袋和扣具，材质和配色符合该等级（皮革棕、铁灰、金色、钻石青、下界合金黑紫），而不是 006 里由几个方块拼出来的简易外形。

**Why this priority**: 这是本功能存在的原因——外观是玩家对背包的第一印象，也是五个等级之间最直观的区别。

**Independent Test**: 在创造模式依次取出五个等级的背包，分别放在快捷栏（看图标）、拿在手上、装备到胸甲栏后切第三人称（看背上），确认三处是同一只背包、五档之间一眼能区分。

**Acceptance Scenarios**:

1. **Given** 玩家的物品栏里有任意等级的浮动背包，**When** 查看物品图标，**Then** 图标朝向的是背包的正面（有扣具与口袋的一面），能认出是背包以及大致等级。
2. **Given** 玩家把任意等级的背包拿在手上，**When** 第一人称或第三人称查看，**Then** 显示的是与图标同一套外形，且朝向的是正面。
3. **Given** 玩家把任意等级的背包装备到胸甲栏，**When** 切换到第三人称并从身后看，**Then** 背上显示的是同一套外形，从身后看到的是背包的正面（有扣具与口袋的一面）。
4. **Given** 玩家依次查看五个等级，**When** 不看物品名称，**Then** 能凭外形和配色分辨出各个等级。
5. **Given** 另一名玩家装备了浮动背包，**When** 本地玩家在第三人称或联机时看到对方，**Then** 对方背上显示的外观与自己背上的一致（所有玩家共用同一渲染路径）。

---

### User Story 2 - 背上的背包贴身、完整、没有穿帮 (Priority: P2)

这些背包没有肩带，玩家背上之后，如果背包和身体之间有明显空隙，看起来就像是悬空要掉下来。玩家希望背包尽量贴着后背，从各个角度（含仰视）看都是一个完整的实体：不透出天空或身体、底部不是空腔。

**Why this priority**: 它直接影响"背着背包"这一最常见场景的观感，但前提是 P1 的外形已经存在。

**Independent Test**: 装备背包后用 F5 绕到侧面、身后、从下往上仰视各看一遍，确认背包紧贴后背、没有透光的缝或空洞、底部是封闭的平面。

**Acceptance Scenarios**:

1. **Given** 玩家背着任意等级的背包，**When** 从侧面看，**Then** 背包近身一面基本贴齐躯干背面，没有肉眼明显的悬空缝隙。
2. **Given** 玩家背着任意等级的背包，**When** 从任意角度（含仰视）看，**Then** 背包表面不应出现能透出天空或人物皮肤的细缝。
3. **Given** 玩家背着下界合金背包，**When** 从下往上看，**Then** 下口袋的底部是封闭的平面，不是凹进去的空腔。
4. **Given** 五个等级的背包尺寸不同，**When** 分别背在身上，**Then** 每一档的近身面都贴着后背（不因档位变高变厚而离身体更远）。

---

### User Story 3 - 背包受环境光照影响，并支持光影包 (Priority: P3)

玩家期望背包像游戏里其它物体一样受昼夜、洞穴和阴影影响，夜里不会自己发光。安装了光影包的玩家还希望背包带有表面凹凸细节。没有安装光影包的玩家则不应受到任何影响。

**Why this priority**: 属于观感打磨：光照正确性对所有玩家有影响但不阻塞使用；光影包支持只对一部分玩家有意义，是可选增强。

**Independent Test**: 白天和夜里（或进入洞穴）分别背着/拿着背包，确认亮度随环境变化；在装有光影包的客户端中确认背包表面有凹凸质感，在没有光影包的客户端中确认外观无异常。

**Acceptance Scenarios**:

1. **Given** 玩家背着或拿着背包，**When** 从白天走进夜晚或洞穴，**Then** 背包亮度随环境降低，不会保持全亮。
2. **Given** 玩家没有安装光影包，**When** 正常使用背包，**Then** 外观与启动流程不受随附法线贴图的任何影响，也没有因此新增的警告或依赖。
3. **Given** 玩家安装了支持 PBR 法线贴图的光影包，**When** 查看背包，**Then** 能看到由法线贴图带来的表面凹凸效果。

---

### User Story 4 - 维护者能从设计素材重新生成背包资源 (Priority: P3)

维护者（本项目开发者）需要在以后调整某个等级的外观（例如换模型、调亮度、修复缺陷）时，能从版本库里找到原始设计素材、处理脚本与处理记录，重新生成并替换游戏里的资源，而不依赖某个人本机上的临时文件。

**Why this priority**: 不直接影响玩家，但外观资源体积大、处理步骤多且有若干坑（坐标约定、UV 翻转、网格缺陷），没有记录就无法复现。

**Independent Test**: 维护者只凭仓库里的设计目录和文档，能说清每个等级的资源是怎么从原始素材处理出来的，并能重新生成其中一个等级。

**Acceptance Scenarios**:

1. **Given** 仓库中的设计目录，**When** 维护者想了解某个等级模型的来源与处理方式，**Then** 能在设计文档中找到来源文件、处理步骤、已知缺陷与未验证项。
2. **Given** 一台没有安装额外版本库扩展工具的构建环境，**When** 构建模组，**Then** 随模组打包的资源是完整可用的文件，不会是占位文本。
3. **Given** 设计目录里体积较大的模型源文件，**When** 提交到版本库，**Then** 它们采用不会让仓库历史无限膨胀的方式管理。

---

### Edge Cases

- **下界合金的正面朝向不确定**：该模型几乎左右镜像对称（正反两面都有翻盖、扣具和口袋），无法从形状判断哪一面才是"正面"。当前按钻石同样的方向处理，实际可能与设计稿正面相反。
- **钻石的翻盖向后包过去**：背面最外缘是翻盖而不是主体，所以主体背面离后背会多出约 0.05 个方块（不到 1 像素）的间隔。
- **金背包最高**：背上时高度可能略超出躯干范围。
- **原始网格仍有少量开放边**：个别角度可能出现细小透光（见已知限制）。
- **没有安装 JEI、光影包或其它可选模组**：外观必须照常工作。
- **多人同屏**：多个玩家同时穿戴不同等级的背包时，每个人背上显示各自等级的外观。
- **没有安装大文件管理扩展的环境克隆仓库**：设计目录里的大文件会是占位文本，但不影响游戏本体的构建和运行（随模组打包的资源是完整文件）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须为皮革、铁、金、钻石、下界合金五个等级各自提供一套独立的、可区分的背包外形与配色；五个等级不得共用同一个占位外形。
- **FR-002**: 同一等级的背包在物品栏图标、手持（第一与第三人称）和背在身上三种场景下，必须使用同一套外形（同一份模型），不得各自一套。
- **FR-003**: 在三种场景下，背包展示给观察者的都必须是正面（带扣具与口袋的一面）：图标和手持朝向观察者，背上则从身后可见。
- **FR-004**: 五个等级的背包都不带肩带；背在身上时，背包近身面必须贴近躯干背面，不得出现肉眼明显的悬空缝隙。
- **FR-005**: 背包的背上位置必须对五个等级同时成立：不同等级的背包尺寸不同，但近身面都必须贴着后背。
- **FR-006**: 背包表面不得出现会让背后景物透出来的缝隙，口袋底部等应为实体的面必须封闭，不得是凹进去的空腔。
- **FR-007**: 背包的亮度必须随游戏环境光照变化（昼夜、洞穴、阴影），不得始终保持全亮。
- **FR-008**: 系统必须随附供光影包使用的法线贴图；未安装光影包时，该贴图不得对外观、启动或依赖产生任何影响，且不得成为硬依赖。
- **FR-009**: 背包贴图与模型的对应关系必须正确（不得出现贴图上下颠倒、各部位贴图错位的现象），外观应与设计效果图一致。
- **FR-010**: 五个等级之间的体量关系：宽度一致，档位越高包越高、越厚。
- **FR-011**: 背上背包的大小必须能与手持背包的大小各自独立调整，调整背上大小不得改变手持大小。
- **FR-012**: 背上背包的渲染必须对所有玩家生效，包括联机中的其他玩家。
- **FR-013**: 本功能不得改变任何既有玩法：容量、升级、打开/关闭规则、面板、库存、互拖等行为保持不变。
- **FR-014**: 版本库必须保存每个等级外观资源的原始设计素材、处理脚本与处理记录（包括处理中发现的坑与已知缺陷），使后续维护者能复现资源。
- **FR-015**: 随模组打包的外观资源必须是完整可用的文件，不得依赖任何额外的版本库扩展才能构建；设计目录中体积较大的模型源文件应采用不会让仓库历史无限膨胀的方式管理。

### Key Entities

- **等级外观**：对应一个背包等级的一整套外观资源，包括形状（模型）、基础色贴图、光影包用的法线贴图，以及决定图标/手持/展示框中朝向与大小的显示参数。
- **背部展示**：背包装备到胸甲栏后，在玩家背上的呈现，决定背包相对躯干的位置、大小与朝向。
- **设计素材记录**：设计目录中的原始素材（效果图、原始模型）、处理脚本与说明文档，记录资源如何从素材处理成游戏资源。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在不看物品名称的情况下，观察者能凭图标和背上外形区分全部五个等级（沿用 006 SC-003 的 5 名观察者、每人 5/5 的口径；本项**尚未做过正式观察测试**）。
- **SC-002**: 同一等级的背包在图标、手持、背上三处外形一致：对五个等级逐一检查，三处看到的是同一只包。
- **SC-003**: 对五个等级，从侧面看背上的背包，近身面与躯干背面的间隔不超过 1 像素（约 0.06 个方块）。设计上钻石以外的等级接近 0，钻石约 0.05 个方块；**尚未在游戏内逐档实测**。
- **SC-004**: 对五个等级，从正面、背面、侧面和仰视各检查一遍，肉眼看不到会透出天空或人物皮肤的缝隙，底部无空腔。**当前未完全满足**，见已知限制。
- **SC-005**: 白天与夜晚（或洞穴）对比，背包亮度随环境明显变化，夜里不发光。
- **SC-006**: 在没有安装光影包的环境下，背包外观与启动流程与不带法线贴图时完全一致；在带光影包的环境下能看到法线带来的凹凸效果（后者**尚未在光影包下实测**）。
- **SC-007**: 白天正常光照下，背包可见表面的平均亮度与设计效果图中背包部分的平均亮度相比，偏差不超过 ±25%（两边用同一套取样方式比较）。当前亮度是按平均亮度粗略估算调整的，**尚未在游戏内逐档对比验证**。
- **SC-008**: 维护者仅凭仓库中的设计目录与文档，即可说明任一等级资源的来源与处理步骤。

## 已知限制（当前未满足，需后续处理）

这些条目是补录时如实记录的缺口，**不是**已满足的要求。每条后面注明性质，具体处理方案不在本 spec 内决定，留给后续 feature。

1. **共用方块图集膨胀（影响所有玩家，优先级最高）【已由 010 解决】**：**（以下是补录 009 时的状态，保留以便追溯。结果：[010-backpack-texture-budget](../010-backpack-texture-budget/spec.md) 把贴图降到 512×512，并用图集 `filter` 把 `_n` 排出共用图集，实测图集 2048×1024、估算显存约 11MB；清晰度的手持与背上已由用户确认，图标、盲测与光影下的法线凹凸仍待确认，见 010 的 DELIVERY.md。）** 十张 1024×1024 贴图（五张基础色加五张法线，图集会扫描整个 `textures/item/` 目录，法线贴图也被拼进去，这一点是 010 的研究阶段才发现的）会被拼进游戏共用的方块图集，实测日志显示该图集从 1024×1024 涨到 4096×4096，按估算显存占用从约 6MB 涨到约 85MB，影响所有玩家的所有方块贴图。部分低端硬件能否承受未知。这与 006 "不要求 64×64 以上写实贴图"的取向相反。后续需要决定贴图分辨率下限、是否单独图集等；本 spec 不规定。
2. **网格仍有开放边**：因自动减面会撕裂这类网格，当前使用完整原始网格，其自带的开放边没有处理：皮革 16、铁 122、金 325、钻石 169、下界合金 114 条。个别角度可能有细小透光。
3. **没有性能预算**：每档约 1.6 万到 2.0 万三角面，同时用于图标、手持和背上渲染（含他人的背包），没有定义或测量过帧率影响。
4. **背上位置的个别偏差**：钻石的主体背面离后背多约 0.05 个方块；金背包较高，背上可能略超出躯干。
5. **显示参数未逐档验证**：铁、金、钻石、下界合金的图标与手持显示参数沿用皮革的数值，只有皮革和下界合金在游戏里被看过。
6. **下界合金的正面朝向不确定**（见边界情况）。
7. **亮度调整是估算值**：皮革提亮较多，铁轻微提亮，下界合金很轻提亮，金与钻石不调整；依据是贴图与参考效果图的平均亮度粗略比较，误差较大。
8. **没有高光/粗糙度贴图**：源模型自带的这类数据没有区分度，光影包下的金属质感与高光暂时没有。
9. **随模组打包的大文件不走 LFS**：每次重新导出会让仓库历史增长（五个模型各约 2MB）。这是为了避免没装 Git LFS 的构建环境把占位文本打进 jar 的取舍。

## 对 006 的修订范围

本功能取代了 006 中与外观相关的下列条款（006 文档已同步修订并保留原意说明）：

- 006 FR-010 要求每个等级"能看出包身、顶盖与肩带"：**肩带部分被取代**——当前五个等级都是无肩带设计（用户明确决定）；包身与顶盖仍成立。
- 006 FR-011 与 SC-004 要求贴图"不低于 32×32 像素"：**该下限仍成立，但已不是实际约束**——当前贴图为 512×512（010 起；009 补录时为 1024×1024）；"贴图"约束转由已知限制 1 讨论。
- 006 research / contracts / plan / tasks 中"共用父模型 + 子模型只换贴图"、立方体元素模型、32×32 贴图、`textures/entity/backpack_<tier>.png` 的描述：**被取代**，现状是每个等级独立的网格模型与独立贴图，背部直接渲染物品自己的模型。
- 006 FR-012（背部与手持外形一致）、FR-001/FR-002/FR-009 等玩法条款：不受影响，仍然成立。

## Assumptions

- 本 spec 只覆盖外观：模型、贴图、图标/手持/背上渲染、素材管线。容量、升级、开关、面板、库存等玩法（见 005、006、007、008）不在范围内，不得被本功能改变。
- 可拆卸的左/右/后小包与升级组件玩法已明确延后，不在本 spec 内；当前五个等级都按"完整模型、无可拆卸部件"处理，原先的"基础款/完整款"二分设计不再沿用。
- 模型来源是 AI 生成工具产出的雕刻网格，原始素材放在设计目录（`design/demo/`）。对外发布时的 AI 素材授权属于项目决策，沿用 `docs/plan/005-gameplay-item-tiers.md` 第 12 节的约定，本 spec 不展开。
- 背包外观依赖 NeoForge 21.1.251 自带的 OBJ 模型加载器，这是 NeoForge 本体的一部分，不是第三方模组，因此不违反宪法第 IV 条（可选兼容不得成为硬依赖）。
- 光影包支持是可选增强：按社区通行的 LabPBR 法线贴图格式提供贴图，不要求、不依赖任何光影加载器。
- 当前实现快照（供追溯，细节见 `plan.md`/`research.md`）：每个等级一个 `neoforge:obj` 物品模型 JSON（带 `flip_v` 与 `emissive_ambient: false`）、一个 OBJ+MTL、一张 1024×1024 基础色贴图和一张 `_n` 法线贴图；背部渲染直接调用物品渲染器渲染该等级物品自己的烘焙模型（FIXED 显示上下文，背上缩放 0.68），因此没有手搭几何；设计目录下的 `.obj` 走 Git LFS（`design/**/*.obj`），随模组打包的 `.obj` 为普通文件（避免没装 git-lfs 的构建环境把 LFS 指针文本打进 jar）。
- 这些实现事实在数值上（缩放、位移、gamma、各档平移量）都是经过推算或粗估的，实际验收以游戏内观察为准（宪法第 V 条）；凡写明"尚未验证"的项目，在客户端会话中验证之前不得标记为完成。
- 贴图分辨率、图集占用与性能预算问题留给后续 feature，不在本 spec 中实现。
