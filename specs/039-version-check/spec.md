# Feature Specification: 版本一致性提示

**Feature Branch**: `039-version-check`

**Created**: 2026-11-10

**Status**: Draft

**Input**: 用户要求（2026-11-10）：玩家登录服务器时，如果客户端与服务器安装的**本模组**版本不一致，就在聊天区**只给他自己**输出一条警告，提醒他手动升级或降级，并提醒版本差异不宜过大、改版本之前一定先备份存档；服务器同时记日志。只检测本模组自己的版本，不管其它模组（作者的另一个独立模组 MCompatIssues 能比较全部模组，但不能假设玩家装了它，所以本模组内置这个最基本的检测）。不改现有网络协议号（仍是 17）。

## 背景与已确认的决策

网络协议只拦住"包格式"不一致：两端协议号不同就无法进服。但协议号不变的版本之间仍可能不一致——036～038 的协议都是 17，规则与界面却变了。例如客户端与服务器共用同一套放入规则：客户端用它做预览，服务器用它裁判；服务器改了判定而旧客户端不知道，预览就与服务器的实际结果不一致。以前 `mod_version` 一直是 0.1.0，两端差异根本比不出来；现在版本号已按语义化版本规范（`docs/plan/release-process.md`：0.x 阶段 MINOR 表示规则、数据格式或网络协议有变化，PATCH 只修缺陷）。

已确认的决策（用户，2026-11-10，**不重新讨论**）：

1. **比较规则**：**MAJOR.MINOR 必须一致**才算一致；**PATCH 不同不警告**（只是修缺陷）；预发布后缀（如 `-rc1`）不同按不一致处理；比较的是模组版本字符串（`neoforge.mods.toml` 里的 `version`），显示时带完整版本号。**不另外维护"规则修订号"。**
2. **提示内容**（聊天里只给本人，中英文）：
   - 客户端版本比服务器**旧** → 提醒升级到与服务器相同的版本；
   - 客户端比服务器**新** → 提醒降级到服务器的版本，或联系服主把服务器升级；
   - **两种情况都要写**：版本差异不宜过大，否则可能出现未知问题；升级或降级之前一定先备份存档；
   - 提示里带上客户端与服务器的完整版本号。
3. **何时提示**：玩家登录服务器时，每次登录最多一次；**单人游戏与自己开的局域网主机不提示**（服务器就是自己的客户端）；两端一致时**什么都不输出**。不加配置项、不加命令。
4. **机制**：新增一个**可选**的网络包（放进单独的注册器、自己的版本号，**不改现有的协议号 17**，不影响现有包的协议校验）：服务器在玩家登录后把自己的模组版本发给客户端；客户端比较后只在本地聊天输出提示，并回一个包把自己的版本告诉服务器（服务器据此写日志）。
5. **老客户端**（版本落后到根本没有这个功能的客户端）：服务器发现它没有这个通道，改由**服务器给他发一条中英双语的纯文本聊天提示**（他的客户端没有这个功能的语言键，所以必须是直接写好的文字），并在服务器日志里记一条。这恰好覆盖版本最落后的人。
6. **服务器侧记录**：登录时记录玩家的模组版本与是否一致；已有的诊断日志（`[diag server]`）头部带上该玩家的模组版本。
7. **顺带的兜底**：客户端对放入的预测，遇到**不认识的类别**时放行（现在返回"不能放"），由服务器裁判；不需要网络包。

## Out of Scope（本阶段不做）

- **其它模组的版本**（交给 MCompatIssues，README 只推荐、不依赖）；**降级保护**（背包数据里写版本标记，单独的 040）。
- 自动升级、自动下载、拒绝登录、自动关闭功能；配置项与命令；"差异程度分级"（差一个 MINOR 与差五个 MINOR 提示的内容相同，都带"差异不宜过大"的提醒）。
- 修改现有网络包与协议号；"规则修订号"。

## 已查证的事实（读本仓库源码与 NeoForge 21.1.251 的 API；规格要尊重）

- 现有网络包都在 `BackpackNetwork.register` 里用同一个注册器 `event.registrar(MOD_ID).versioned("17")` 注册；协议号只管这些包。
- NeoForge 21.1.251 的 `PayloadRegistrar` 有 `optional()` 与 `versioned(String)` 方法；`ICommonPacketListener` 有 `hasChannel(CustomPacketPayload.Type)` 等重载（反编译核对过），所以"可选包 + 判断对方有没有这个通道"在 API 层面存在；**在登录后的哪个事件里可用、对没有通道的客户端发包会怎样，尚未验证**。
- 现在 `mod_version` 是 `0.1.0`（`gradle.properties`），发布 jar 里的 `neoforge.mods.toml` 里 `version="0.1.0"`（构建后核对过）；开发运行里取到的是什么尚未核对。
- 客户端有一个只给本人看的聊天输出（`FloatingPanelEvents.chat`，带模组名前缀，调用 `minecraft.gui.getChat().addMessage`），不发给服务器或别人。
- `ItemCategoryMatcher.matches` 对数据标签键表里没有的类别返回"不能放"；客户端预测（`ClientPlacement`）用它，所以版本落后的客户端遇到不认识的类别行会误拦。
- 服务器的诊断日志（`DiagLog`、`BackpackWatchService`）有带玩家名的 WARN 行，没有玩家的模组版本。

## 尚未验证（plan 阶段先查证；验证前不得声称已满足）

- 新增可选包：`optional()` 的包放进单独的注册器，是否真的让没有这个通道的客户端仍能登录、且不影响现有 `versioned("17")` 包的校验（含注册顺序）；`hasChannel` 在玩家登录后的哪个事件里可用（通道协商是否已完成）；对没有通道的客户端 `sendToPlayer` 是抛异常还是静默丢弃。
- 怎样得到两端各自的本模组版本字符串（`ModList` 里的模组信息），以及它在开发运行与发布 jar 里的值。
- 怎样判断"单人游戏与自己开的局域网主机"，同时让**局域网里别的玩家**照常被提示（他们的版本可能与房主不同）。
- 客户端收到握手包时聊天是否已可用，是否要延迟到进入世界后的下一个 tick 再显示，以及怎样避免被登录时刷屏的系统消息冲掉。
- 版本字符串的边界：`0.1.0`、`0.2.0-rc1`、带构建元数据 `0.2.0+abc`、不规范的字符串、空值；0.x 阶段 PATCH 不警告的规则同样成立。
- 老客户端的服务器侧提示：用一个没有这个功能的构建（如 038 的构建）当"老客户端"来验证；"版本不同的两端"怎样在开发里得到（改 `mod_version` 构建两个 jar，或一端用旧 commit 的构建）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 版本不一致时，玩家在聊天里收到只有自己看得到的警告 (Priority: P1)

玩家登录服务器，如果他的浮动背包版本与服务器的 MAJOR.MINOR 不同，聊天里出现一条警告：说明两端的完整版本号，告诉他该升级还是降级，并提醒差异不宜过大、改版本前先备份存档。

**Why this priority**: 这是本功能的全部目的：让玩家在出现"预览与实际不一致"这类怪问题之前就知道版本不对。

**Independent Test**: 用两个不同 MINOR 的构建，一端当服务器、另一端当客户端，登录。

**Acceptance Scenarios**:

1. **Given** 客户端 0.1.0、服务器 0.2.0，**When** 玩家登录，**Then** 他的聊天里出现一条警告，写明客户端 0.1.0 与服务器 0.2.0，建议**升级**到服务器的版本，并提醒版本差异不宜过大、改版本之前先备份存档。
2. **Given** 客户端 0.3.0、服务器 0.2.0，**When** 玩家登录，**Then** 警告建议**降级**到服务器的版本，或联系服主把服务器升级，同样提醒差异与备份。
3. **Given** 警告出现，**Then** 只有这位玩家自己看得到，服务器上的其他玩家与聊天记录里没有任何痕迹。
4. **Given** 同一次登录，**Then** 警告最多出现一次，不重复刷屏。
5. **Given** 中文与英文两种语言，**Then** 警告文字都齐全。
6. **Given** 警告里写了版本号，**Then** 带完整版本号（如 `0.1.0`、`0.2.0-rc1`），不是截断的。

---

### User Story 2 - 一致时什么都不说；该不提示的情形不提示 (Priority: P1)

两端一致、只差 PATCH、单人游戏、自己开的局域网主机，都不输出任何提示。

**Why this priority**: 误报和刷屏会让玩家学会无视警告，比没有警告更糟。

**Independent Test**: 分别用一致、只差 PATCH、单人游戏、局域网主机登录，看聊天与日志。

**Acceptance Scenarios**:

1. **Given** 两端版本完全一致，**Then** 聊天里没有任何关于版本的输出。
2. **Given** 客户端 0.2.1、服务器 0.2.0（只差 PATCH），**Then** 不警告。
3. **Given** 客户端 0.2.0-rc1、服务器 0.2.0（预发布后缀不同），**Then** 按不一致处理，给出警告。
4. **Given** 单人游戏，**Then** 不提示。
5. **Given** 玩家自己开的局域网，**When** 房主自己进入世界，**Then** 不提示；**When** 别的玩家加入，**Then** 照常按版本比较提示（他们的版本可能与房主不同）。
6. **Given** 不一致已被提示过一次，**When** 玩家退出再登录，**Then** 新的一次登录再提示一次（"每次登录最多一次"）。

---

### User Story 3 - 版本太旧、根本没有这个功能的客户端，由服务器提醒 (Priority: P1)

某位玩家用的是早于本功能的旧版本，他的客户端没有这个功能；服务器发现这一点，直接给他发一条中英双语的文字提示，并在日志里记一条。

**Why this priority**: 版本最落后的人最需要被提醒，而他恰好没有任何客户端代码来提醒自己。

**Independent Test**: 用没有这个功能的构建（如 038）当客户端，登录有这个功能的服务器。

**Acceptance Scenarios**:

1. **Given** 客户端没有这个功能，**When** 他登录，**Then** 他仍能登录（这个功能不能让旧客户端进不了服务器），并在聊天里收到一条服务器发来的**纯文本、中英双语**提示：你的浮动背包版本过旧，请升级到与服务器相同的版本，升级前先备份存档。
2. **Given** 这条提示，**Then** 只有这位玩家看得到；内容不依赖他客户端里的语言键（他的客户端没有这些键）。
3. **Given** 这位玩家登录，**Then** 服务器日志里有一条 WARN，写明玩家名、"客户端没有版本检测功能（版本过旧）"与服务器版本。
4. **Given** 同一次登录，**Then** 这条提示最多一次。
5. **Given** 单人游戏与局域网主机，**Then** 不发这条提示。

---

### User Story 4 - 服务器日志记下每位玩家的模组版本 (Priority: P2)

服务器管理员追查问题时，在日志里能直接看到玩家用的版本，不用再问"你用的什么版本"。

**Why this priority**: 帮助排查，不影响玩家体验。

**Independent Test**: 让几位版本不同的玩家登录，看服务器日志；再触发一次诊断日志的 WARN。

**Acceptance Scenarios**:

1. **Given** 两端不一致的玩家登录，**Then** 服务器日志有一条 WARN：玩家名、客户端版本、服务器版本、结果（客户端更旧 / 更新）。
2. **Given** 两端一致的玩家登录，**Then** 不写 WARN（最多一条低级别记录）。
3. **Given** 已有的诊断日志警告（例如背包"不见了"的警告）触发，**Then** 警告头部带上该玩家的模组版本（已知时；不知道时写"未知"）。
4. **Given** 服务器日志级别设置（已有的 `logging.level`），**Then** 本功能的日志遵守它。

---

### User Story 5 - 版本落后的客户端遇到不认识的类别行时不误拦 (Priority: P2)

旧客户端连到新服务器，遇到它不认识的类别行（例如通用行）时，预览宁可多放行，由服务器裁判，而不是错误地显示"放不进"。

**Why this priority**: 这是版本差异最常见的一种可见后果；改动不需要任何网络包，成本最低。

**Independent Test**: 构造一个客户端不认识的类别的行，在上面放物品。

**Acceptance Scenarios**:

1. **Given** 背包里有一个客户端不认识类别的行，**When** 光标上拿着任何物品移到这一行的格子上，**Then** 客户端不显示"放不进"的红色高亮，点击会发给服务器，由服务器决定。
2. **Given** 已知类别（10 个分类与通用），**Then** 预测行为与现在完全一样（放不进的仍然红色高亮）。
3. **Given** 服务器拒绝了放入，**Then** 与现在一样零变化、没有物品丢失或复制。

---

### Edge Cases

- **无法解析的版本字符串**（任何一端的版本字符串不是语义化版本、或取不到）：无法判断是否一致，**默认当作不一致并提示**，提示里写出原始字符串，并说明"无法比较"；不报错、不崩溃。
- **两端都是 `0.1.0` 的开发版但代码不同**：检测不出来（版本相同就是一致）；这是已知局限，发布前才改版本号的约定意味着开发版之间的差异不会被发现。
- 握手包到达时聊天还不能用（刚登录）：提示不能丢，要在聊天可用后显示。
- 玩家在提示出现前就退出：不报错。
- 服务器上多位玩家同时登录：各自独立提示，互不影响。
- 服务器重启、玩家重连：按"每次登录一次"处理。
- 老客户端与新客户端混在同一台服务器上：各自按自己的情形处理。
- 局域网里房主关闭局域网或退出：不产生提示。
- 客户端回的版本包丢失、延迟或根本不回：服务器日志里就没有"客户端报告的版本"，不影响客户端提示；服务器不会因此踢人或阻塞。

## Requirements *(mandatory)*

### Functional Requirements

**比较与提示**

- **FR-001**: 系统 MUST 在玩家登录服务器时比较客户端与服务器的**本模组**版本：MAJOR.MINOR 都相同才算一致；PATCH 不同 MUST NOT 警告；预发布后缀不同 MUST 按不一致处理；构建元数据（`+...`）不参与比较。
- **FR-002**: 不一致时 MUST 在该玩家的聊天里输出警告，**只有他自己看得到**；内容 MUST 包含：客户端与服务器的完整版本号；客户端更旧时建议升级到服务器的版本，客户端更新时建议降级到服务器的版本或联系服主升级服务器；**两种情况都 MUST 提醒**版本差异不宜过大、否则可能出现未知问题，以及升级或降级之前一定先备份存档。
- **FR-003**: 警告 MUST 有中英文两种语言；每次登录 MUST 最多出现一次；一致时 MUST NOT 输出任何版本相关的内容。
- **FR-004**: 无法比较（任何一端的版本不是语义化版本或取不到）MUST 当作不一致并提示，提示里写出原始字符串并说明无法比较；MUST NOT 抛出异常或影响登录。
- **FR-005**: 单人游戏与玩家自己开的局域网的主机本人 MUST NOT 被提示；局域网里加入的其他玩家 MUST 照常被提示。

**机制与兼容**

- **FR-006**: MUST 新增一个**可选**的网络包用于握手：服务器 → 客户端带服务器的模组版本；客户端 → 服务器带客户端的模组版本；MUST 使用单独的注册器与自己的版本号，MUST NOT 修改现有网络包或协议号 17，MUST NOT 影响现有包的协议校验；没有这个功能的客户端 MUST 仍能登录。
- **FR-007**: 服务器 MUST 在玩家登录后发起握手；对没有这个通道的客户端 MUST NOT 发这个包。
- **FR-008**: 对没有这个通道的客户端，服务器 MUST 改为发一条**纯文本、中英双语**的聊天提示（不使用语言键），说明其浮动背包版本过旧、请升级到与服务器相同的版本、升级前先备份存档，并在服务器日志里记一条 WARN；每次登录最多一次；单人游戏与局域网主机 MUST NOT 发。
- **FR-009**: 客户端的提示 MUST 在聊天可用时显示（不能因为登录刚结束而丢失），并且不会因为后面的系统消息而看不到。

**日志**

- **FR-010**: 服务器 MUST 在日志里记录登录玩家的模组版本与比较结果：不一致与老客户端记 WARN；一致的不记 WARN；遵守已有的 `logging.level` 设置。
- **FR-011**: 已有的服务器诊断日志的 WARN 头部 MUST 带上该玩家的模组版本（已知时；未知写"未知"）。

**兜底与范围**

- **FR-012**: 客户端的放入预测对**不认识的类别** MUST 放行（不显示"放不进"、不拦截点击），由服务器裁判；对已知类别的预测 MUST 保持不变。
- **FR-013**: MUST NOT 检测其它模组的版本；MUST NOT 新增配置项、命令；MUST NOT 自动升级、下载、拒绝登录或关闭功能；MUST NOT 修改现有网络包与协议号。
- **FR-014**: 文档 MUST 更新：README 与发布说明的"多人游戏"一节写明版本规则（MAJOR.MINOR 一致）；`docs/plan/release-process.md` 记录本功能的状态。

### Key Entities *(include if feature involves data)*

- **模组版本**：本模组的版本字符串，来自模组元数据（发布时来自 `mod_version`）；比较时用 MAJOR、MINOR、预发布后缀，PATCH 与构建元数据不参与。
- **比较结果**：一致 / 客户端更旧 / 客户端更新 / 无法比较；决定提示的内容。
- **握手**：一对可选的网络消息，服务器告诉客户端自己的版本、客户端回报自己的版本；对没有这个功能的客户端不存在，由服务器的纯文本提示代替。
- **版本提示**：玩家聊天里只有自己看得到的一条警告（中英文）；老客户端的版本是服务器发的纯文本版本。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: MAJOR.MINOR 不同的客户端登录服务器，**100%** 的登录在聊天里收到一条只有自己看得到的警告，包含两端版本号、升级或降级的方向、"差异不宜过大"与"先备份存档"；一致的、只差 PATCH 的、单人游戏与局域网房主的登录，**0 条**版本相关输出。
- **SC-002**: 没有这个功能的老客户端登录有这个功能的服务器：**仍能登录**（登录成功率不下降），并收到一条服务器发来的中英双语纯文本提示，服务器日志有一条对应 WARN。
- **SC-003**: 同一次登录里警告**最多 1 次**；连续登录 10 次，每次不一致的登录各提示 1 次、没有重复或遗漏。
- **SC-004**: 版本字符串的各种边界（正常、预发布、构建元数据、不规范、空值）共至少 10 种输入，比较与提示类型的选择全部与规则一致，没有一个导致异常。
- **SC-005**: 现有网络协议号与现有包不变：旧客户端与服务器之间原有的协议校验行为与改动前一致（用 038 的构建当客户端验证）。
- **SC-006**: 客户端遇到不认识的类别行时，**0 次**误显示"放不进"；已知类别的预测与改动前逐项一致。
- **SC-007**: 服务器日志里每位不一致玩家的登录可以一眼看出玩家名、两端版本与结果，诊断日志的 WARN 头部带玩家的模组版本。

## Assumptions

- 版本比较只看 MAJOR.MINOR 与预发布后缀；0.x 阶段 MINOR 就是规则与数据变化的级别，所以 PATCH 不警告的规则对 `0.x.y` 同样成立（`docs/plan/release-process.md`）。
- 发布前才改 `mod_version` 的约定意味着**开发版之间的代码差异检测不出来**（版本相同就是一致）；这是已知局限，不另加构建标识。
- 无法比较时默认当作不一致并提示，是"宁可多提醒一次"的取舍。
- 局域网里别的玩家被提示依据的是房主客户端的版本；房主本人不提示。
- 老客户端提示的文字是纯文本（中英双语），因为那个客户端没有本功能的语言键；它不能随客户端语言切换。
- 本功能只提醒，不阻止：版本不一致的玩家仍然可以进服、继续玩。
- 日志的详细级别沿用已有的服务器日志级别设置，不新增配置。
