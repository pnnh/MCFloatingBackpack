# Feature Specification: 取消"无界面 HUD 模式"，改为兜底的透明宿主界面

**Feature Branch**: `019-fallback-host-screen`

**Created**: 2026-11-05

**Status**: Implemented（实现完成；验证未完成：宿主基本表现、状态与光标物品、按键状态、已知限制观察与 50 次压力已由用户确认；011～017 回归已于 2026-11-07 由用户确认；切换维度、隐藏期间丢背包未验证，Windows/Linux 未确认，见 DELIVERY.md）

**Input**: User description: "取消浮动面板的\"无界面 HUD 模式\"，改为\"兜底透明宿主 Screen\"。没有其它界面时由模组显示一个透明宿主界面，使面板始终有一个界面可挂；任何其它界面（按 E 的物品栏、精妙背包、工作台、聊天……）打开时宿主让位，面板像现在一样挂在容器界面上；其它界面关闭后宿主自动恢复。玩家打开面板后必须仍能按 E 或其它模组的按键打开其它界面。"

> **020 说明**：020 在这里的"其它界面"语义之上加了一个客户端配置：把某个模组设为 `OFF` 后，它的容器界面被当作"其它界面"（面板隐藏、不拦截、不转移，关闭后恢复）；原版容器不可配置；019 的按键"让出再重放"与模组无关，不受影响。详见 `specs/020-compat-switches/`。

## 背景与已确认的决策

到 018 为止，面板有两种存在方式：打开着容器界面时挂在界面上（靠界面事件驱动渲染与输入），和**没有任何界面**（HUD 模式）时画在游戏画面上（靠另一套 HUD 渲染与世界鼠标输入驱动，还要手动释放/抓取鼠标，光标也是面板自己的第二套）。HUD 模式是为了"不打开界面也能用面板、还能一边走路"，但它让每个面板功能都要为两条输入路径、两条渲染路径各做一遍，而且即将到来的 018 标签管理器要为它在 HUD 下的键盘接管专门造一个临时界面。用户评估后认为 HUD 模式的必要性不强，决定改成"始终有一个界面"。

已确认的决策（用户已裁决，不重新讨论）：

1. **方案 C**：没有其它界面时，由模组显示一个**透明的宿主界面**，使面板始终有一个界面可挂。面板自己的光标、`MergePanelCursorPayload`、`screenOpen` 标志、Alt 换主手**暂时保留**（以后再逐步换成原版的光标功能，不在本 feature 做）。
2. **宿主只是兜底，不是替代品**。这是本 feature 最重要的约束，已写入宪法 2.0.0 的原则 I：
   - 核心规则只有一条：**面板可见，并且当前没有任何其它界面 → 显示宿主界面。**
   - 任何其它界面（玩家按 E、按键绑定、其它模组打开的）一出现，宿主就让位；那个界面关闭后，只要面板仍可见，宿主自动恢复。所以面板下面始终有一个界面。
   - 宿主不暂停游戏，不存放物品，不得挡住打开其它界面的按键，**只用来承载面板**。
3. **玩家在世界里按面板热键打开面板后，必须仍能按 E 打开原版物品栏，也能用其它模组的按键打开其它界面**（例如精妙背包的快捷键）。否则就违背了做浮动背包的初衷。
4. **宿主打开期间完全接管键盘和鼠标**：玩家不能移动、不能转向，世界交互（挥手、放置、右键方块）失效。用户已明确接受。想操作世界，先关面板。
5. **非容器界面**（聊天、暂停菜单、选项等）打开时：宿主让位，**面板隐藏但"可见"状态保留**，界面关闭后宿主恢复、面板重新出现。**玩家死亡、断线**：清除"可见"状态。
6. **面板不可见时，本 feature 完全不介入**：E 等一切同原版。

已查证的事实（读 NeoForge 21.1.251 源码与本仓库源码；规格要尊重，不要重新猜）：

- `Minecraft.setScreen(null)`（"回到游戏"）**不会**触发 `ScreenEvent.Opening`，只会触发 `ScreenEvent.Closing(旧界面)`；而在 `Closing` 里不能再调用 `setScreen`（会重入，旧界面的 `removed()` 会被调两次）。所以"恢复宿主"不能靠事件，需要每 tick 检查"面板可见且没有界面"。关闭其它界面到宿主出现之间，可能有一帧鼠标被抓取又被释放的闪动，需客户端验证。
- 有界面打开时，`KeyboardHandler.keyPress` 不设置也不点击按键映射，`Minecraft.handleKeybinds`（物品栏、聊天、成就、其它模组的按键映射都在这里或类似的 tick 里消费）只在**没有界面**时运行。所以宿主必须自己转发按键。设想的机制是"**让出再重放**"：宿主收到一个已绑定功能的按键时先让出，再对该键触发按键映射，让下一 tick 的原版逻辑照常处理；若因此打开了新界面就照常显示，否则 tick 检查把宿主放回来。E、聊天键、其它模组"打开界面"的按键都走同一条路径。移动、攻击、使用这类世界动作按键由宿主直接吞掉，不触发让出（否则会闪）；具体吞哪些由 plan 阶段确定。
- 原版对 F1（隐藏界面）、F3（调试信息）及其组合键是按键码直接处理的，**只在没有界面时生效**，不经按键映射，"让出再重放"重放不了它们。
- 原版 `InventoryScreen` 在创造模式下会把自己替换成创造物品栏（面板不支持创造界面）；宿主是自己的界面，所以创造模式下面板自己也能用。
- 现状：面板可见时若打开了既不是容器界面也不是空的界面（聊天、选项、暂停菜单），面板会被**直接关闭**（会话也关闭）；ESC 在面板可见时先关面板、不进暂停菜单；从 HUD 切到容器界面时，面板自己的光标物品会合并进界面的携带物（`MergePanelCursorPayload`）。
- 输入框焦点的按键走 `ScreenEvent.KeyPressed.Pre`，先于界面自己的 `keyPressed`，因此将来 018 的输入框里打字 e 不会触发"让出"。

## Out of Scope（本阶段不做）

- Q 丢弃、快捷栏互相拖放、反向转移、点界面外丢弃等原版光标功能：**以后逐步实现**，面板光标暂时仍是第二种光标来源。
- 快捷轮盘等基于透明界面的新玩法：**另开 feature**；宿主界面本阶段**只承载面板**，不为将来的用途预先设计。
- 018 标签管理器本身。019 先于 018 实现；019 完成后 018 的 plan 要简化（去掉 `TagInputScreen` 例外与"HUD 键盘捕获"）。
- 创造模式**创造物品栏**界面上的面板行为：沿用现状，不在本 feature 里扩展。
- 服务端规则、网络协议、物品存储：不动。
- 让 F1、F3 这类原版直接按键码处理的功能在宿主下可用（登记为已知限制，见下）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 没开任何界面时，面板出现在透明宿主上，用起来和原来一样 (Priority: P1)

玩家在世界里按面板热键（默认 B）或右键背包物品。面板出现在游戏画面上，游戏世界画面不变暗、不模糊、没有任何多余的界面元素；鼠标被释放，可以直接点面板。面板的所有现有操作——拖动、缩放、点击拿起/放下、右键、Ctrl 转出（011/012）、拖动均分与收集（013）、Shift 选区与 Alt 换主手（014）、三个工具区与各自的滚动（016）、合法尺寸（017）——结果与原来的 HUD 模式完全一致。

**Why this priority**: 这是 019 的核心；如果面板在新宿主上不能原样工作，其余都没有意义。

**Independent Test**: 在世界里按 B，把 005～017 的面板验收项（quickstart 清单）逐项做一遍，对照原 HUD 的结果。

**Acceptance Scenarios**:

1. **Given** 没有打开任何界面且面板不可见，**When** 玩家按热键，**Then** 面板出现，游戏画面没有变暗或模糊，鼠标被释放，物品栏、聊天等界面都没有被打开。
2. **Given** 面板已出现，**When** 玩家走一遍拖动、缩放、拿起/放下、右键、Ctrl 转出、拖动均分与收集、Shift 选区、Alt 换主手、工具区滚动、滚轮，**Then** 每一项的结果与 019 之前的 HUD 模式一致，物品总数守恒。
3. **Given** 面板已出现，**When** 玩家按 W、A、S、D 或移动鼠标，**Then** 角色不移动、不转向，这是预期行为。
4. **Given** 在单人游戏里面板已出现，**When** 过了一段时间，**Then** 世界时间继续流逝、怪物继续行动（宿主不暂停游戏）。
5. **Given** 面板已出现，**When** 玩家再按热键，**Then** 面板关闭，鼠标重新被抓取，回到正常的游戏状态，没有残留界面。

### User Story 2 - 面板开着时，仍能用 E 或其它按键打开别的界面，关闭后面板自动回来 (Priority: P1)

面板在世界里开着（宿主在下面）。玩家按 E，原版物品栏打开，宿主让位，面板像现在一样挂在物品栏界面上，和物品栏之间的所有交互（011/012 的 Ctrl 转出等）不变。玩家再按 E 或 ESC 关掉物品栏，宿主自动恢复，面板还在原位，无需再按热键。同样的流程适用于其它模组打开界面的按键（例如精妙背包的"打开背包"快捷键）以及聊天键、成就键等。

**Why this priority**: 用户明确指出这是最重要的体验要求，否则与做浮动背包的初衷相违背。

**Independent Test**: 面板开着时，依次按 E、聊天键、成就键，开发机用 `runClientCompat` 再按精妙背包的快捷键；每次都核对界面是否打开、面板是否随之挂上或隐藏、关闭后面板是否回来。

**Acceptance Scenarios**:

1. **Given** 面板开着（宿主在下面），**When** 玩家按 E，**Then** 原版物品栏**一次按键就**打开，面板挂在它上面，面板与物品栏界面之间的交互与 019 之前一致。
2. **Given** 面板挂在物品栏界面上，**When** 玩家按 E 或 ESC 关掉物品栏，**Then** 宿主自动恢复，面板仍在原位、状态（位置、尺寸、滚动、选区）不变，玩家没有再按热键。
3. **Given** 面板开着，**When** 玩家按聊天键，**Then** 聊天界面打开，面板隐藏但保持"可见"状态；聊天关闭后宿主恢复，面板重新出现。
4. **Given** 面板开着且已装好精妙背包兼容运行环境，**When** 玩家按精妙背包的"打开背包"快捷键，**Then** 精妙背包界面打开，面板挂在它上面；关闭后面板回来。
5. **Given** 先打开一个工作台，再按热键让面板挂在工作台界面上，**When** 玩家关闭工作台，**Then** 宿主出现、面板仍在，玩家无需再按热键。
6. **Given** 面板开着，**When** 玩家连续做"E 开、E 关、聊天开、ESC 关"各 20 次，**Then** 没有一次出现"按了没反应"、界面被宿主盖住、两个界面叠在一起或需要再按一次键。

### User Story 3 - ESC 与非容器界面 (Priority: P2)

面板开着时，ESC 的行为与现在一致：宿主在下面时，ESC 先关面板，**不**打开暂停菜单；要进暂停菜单，在面板关闭后再按一次 ESC。面板挂在容器界面上时，ESC 照原版先关掉容器界面，宿主随之出现，面板仍在；再按一次 ESC 关面板。聊天、选项、暂停菜单等非容器界面打开时，面板隐藏，但"可见"状态保留；这些界面关闭后面板回来。

**Why this priority**: ESC 与暂停菜单是最容易出现"卡在界面里出不来"的地方，必须明确。

**Independent Test**: 面板开着时分别在宿主下、物品栏界面下按 ESC；打开聊天后关闭；验证每一步面板和界面的状态。

**Acceptance Scenarios**:

1. **Given** 宿主在下面，**When** 玩家按 ESC，**Then** 面板关闭，暂停菜单**不**打开，游戏回到正常状态。
2. **Given** 面板挂在物品栏界面上，**When** 玩家按 ESC，**Then** 物品栏界面关闭，宿主恢复，面板仍可见；**再按** ESC，面板关闭。
3. **Given** 面板可见，**When** 因为任何原因弹出了暂停菜单或选项界面，**Then** 面板隐藏、"可见"状态保留；暂停菜单关闭后宿主恢复、面板重新出现。
4. **Given** 面板可见，**When** 玩家死亡或断线，**Then** "可见"状态被清除；重新进入世界后面板不可见（与现在一致）。

---

### User Story 4 - 状态不丢、光标物品不丢 (Priority: P2)

宿主与其它界面来回切换的过程中，面板的位置、尺寸、滚动、选区不变；正在进行的拖动、缩放、批量转出等手势被安全取消，不丢物品、不复制物品；面板自己光标上的物品，在宿主让位给容器界面时合并进界面的携带物，让位给非容器界面时仍留在面板光标上，关闭面板时按现有规则退还。

**Why this priority**: 切换是新机制的高频路径，物品安全是底线（宪法 II）。

**Independent Test**: 面板光标上拿着物品，依次按 E（容器界面）、关闭、聊天、关闭、关闭面板；每一步核对物品总数。

**Acceptance Scenarios**:

1. **Given** 面板光标上拿着 N 个物品，**When** 玩家按 E 打开物品栏，**Then** 这些物品按现有规则合并到界面的携带物上，总数不变。
2. **Given** 面板光标上拿着物品，**When** 玩家按聊天键，**Then** 物品仍在面板光标上；聊天关闭后仍然在。
3. **Given** 正在拖动均分、Ctrl 转出或缩放面板，**When** 玩家按 E 或界面被别处打开，**Then** 手势被取消，物品总数守恒，没有残留的预览。
4. **Given** 面板在界面之间来回切换若干次，**When** 回到宿主，**Then** 面板的位置、尺寸、滚动、选区与切换前一致。

---

### User Story 5 - 创造模式与按键状态 (Priority: P3)

创造模式下，没有界面时按热键，面板同样能在宿主上使用。玩家按着移动键时打开或关闭面板，松开后按键状态不会卡住（不会一直在走）。

**Why this priority**: 都是边界情况，但是 C 方案相对"打开原版物品栏"方案的优势之一，也是新机制容易出错的地方。

**Independent Test**: 创造模式下按热键并使用面板；按住 W 的同时按热键，再松开 W。

**Acceptance Scenarios**:

1. **Given** 玩家处于创造模式、没有打开任何界面，**When** 按热键，**Then** 面板在宿主上出现并可用。
2. **Given** 玩家处于创造模式，**When** 按 E 打开创造物品栏，**Then** 行为沿用 019 之前的现状（面板在创造物品栏界面上是否显示与之前一致）。
3. **Given** 玩家按住 W 正在前进，**When** 同时按热键打开面板、再松开 W，**Then** 面板打开后角色停止，松开 W 后再关闭面板，角色不会自己继续走。

### Edge Cases

- 宿主让位之后、其它界面真正出现之前的**空档**（"让出再重放"的那一个 tick）：宿主不得在这个空档里被立刻恢复，导致按键被吞或界面被盖住。
- 关闭其它界面后宿主出现之前，可能有**一帧**鼠标被抓取再释放的闪动，需客户端验证闪动是否可以接受；鼠标位置回到屏幕中心与原版开界面一致，可以接受。
- 其它模组的"打开界面"按键**不一定**经过按键映射的 `consumeClick`，"让出再重放"可能对它们无效：登记为已知限制，遇到再逐个处理。
- F1、F3 及其组合键这类原版按键码直接处理的功能，宿主在场时**不可用**：登记为已知限制；暂停菜单与 `F3+Esc` 同理。
- 窗口失焦时原版会自动打开暂停菜单，但它只在没有界面时才这样做；宿主在场时不会自动弹出暂停菜单。这是预期的副作用，记录即可。
- 世界交互失效是预期行为：宿主在场时右键方块（工作台、箱子）打不开；想操作世界，先关面板，或者先打开界面再按热键让面板挂上去。
- JEI、EMI 等叠层模组在宿主界面上是否出现、是否影响面板的"JEI 安全区"（008）：**未验证**，需在客户端观察后登记。
- 玩家切换维度时（传送门过场界面）：面板按"非容器界面"处理，过场结束后是否回来由现有的背包会话校验决定；若背包已无法访问，按现有规则关闭。
- 多人服务器与单人一致，不需要新的服务端行为；宿主在场不会让玩家在服务器上"被暂停"，也不会影响服务器上其他玩家。
- 面板热键在宿主上、各种容器界面上都必须能开关面板（原本 `UNIVERSAL` 冲突上下文的要求保持）。
- 玩家在宿主在场时打开聊天并输入内容：输入的字符进入聊天框，不得被宿主当作按键转发再触发别的界面。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 当面板可见且没有任何其它界面时，系统 MUST 显示一个透明的宿主界面，使面板始终有一个界面可挂。宿主 MUST NOT 让游戏画面变暗、模糊或出现任何多余的界面元素。
- **FR-002**: 宿主 MUST NOT 暂停游戏；单人游戏中世界在宿主在场时继续运行。宿主 MUST NOT 持有任何物品存储。
- **FR-003**: 任何其它界面（无论由玩家、按键绑定还是其它模组打开）打开时，宿主 MUST 让位；不得出现宿主盖在其它界面上、或宿主与其它界面同时可见。
- **FR-004**: 其它界面关闭后，只要面板仍可见，宿主 MUST 自动恢复，无需玩家再按热键；恢复发生在界面关闭后很短的时间内（见 SC-002）。
- **FR-005**: 面板不可见时，本 feature MUST 完全不介入：不显示宿主、不拦截任何键盘或鼠标输入，E 等一切同原版。
- **FR-006**: 面板的所有现有打开途径（热键、右键背包物品，以及将来由服务端会话驱动的打开）MUST 在没有其它界面时使宿主出现；有其它界面时 MUST 仍按现有方式叠加到该界面上。
- **FR-007**: 宿主在场时，打开其它界面的按键（原版的物品栏、聊天、命令、成就等，以及其它模组绑定的"打开界面"按键）MUST 照常生效，且**第一次按键就生效**。移动、攻击、使用、丢弃这类世界动作按键 MUST 被吞掉，不得触发让位。
- **FR-008**: 宿主在场期间，玩家 MUST NOT 能移动或转向；打开或关闭宿主时 MUST NOT 留下卡住的按键状态（例如按着移动键时打开面板，松开后角色不会自己继续走）。
- **FR-009**: 面板挂在容器界面上时的所有行为（011/012 的 Ctrl 转出、013 的拖动、014 的选区、016 的工具区与滚动、017 的合法尺寸、003 的跨界面拖动）MUST 与 019 之前完全一致。
- **FR-010**: 面板在宿主上的所有交互 MUST 与 019 之前的 HUD 模式完全一致，包括使用面板自己的光标、Alt（macOS Option）+点击交换主手、Ctrl 转出到玩家物品栏、滚轮滚动工具区。面板的外观与交互 MUST NOT 因为有没有容器界面而出现差异（光标来源除外）。
- **FR-011**: 面板可见期间，游戏中 MUST 始终有一个界面存在。模组 MUST NOT 再在"没有界面"的状态下自行释放或抓取鼠标、驱动面板的渲染或输入。
- **FR-012**: 非容器界面（聊天、暂停菜单、选项等）打开时，面板 MUST 隐藏但保持"可见"状态（位置、尺寸、滚动、选区、背包会话都保留），该界面关闭后 MUST 重新出现。这取代现状中"面板被直接关闭"的行为。
- **FR-013**: ESC 的行为 MUST 为：宿主在场时，ESC 关闭面板，**不**打开暂停菜单；面板挂在容器界面上时，ESC 先按原版关闭该容器界面，宿主随之恢复，再按一次 ESC 关闭面板。
- **FR-014**: 面板热键 MUST 在宿主与各种界面上都能开关面板。
- **FR-015**: 玩家死亡、断线或登出时，"可见"状态 MUST 被清除；重新进入世界后面板不可见（与现状一致）。
- **FR-016**: 宿主与其它界面切换时，正在进行的手势（拖动均分、Ctrl 转出、选区拖选、缩放、移动面板）MUST 被安全取消，物品总数守恒，不得留下残留预览或半完成状态。
- **FR-017**: 面板自己光标上的物品：宿主让位给容器界面时 MUST 按现有规则合并进界面的携带物；让位给非容器界面时 MUST 仍留在面板光标上；关闭面板时 MUST 按现有规则退还。任何情况下物品总数守恒，不丢失、不复制。
- **FR-018**: 创造模式下没有界面时，面板 MUST 能在宿主上打开和使用；创造物品栏界面上的行为沿用现状。
- **FR-019**: 本 feature MUST NOT 修改服务端物品规则与网络协议（预期不新增网络包，协议版本不变）。
- **FR-020**: 受影响的历史文档 MUST 更新，把"无界面 HUD 模式"的描述改成"宿主界面"（003、007、011、012、013、014、016 的相关处，以及 `docs/MCFloatingBackpack.md`）；018 的文档 MUST 记录它对 019 的依赖。不得修改 `docs/ideas`。
- **FR-021**: 以下内容 MUST 登记为已知限制或未验证，而不是声称已满足：F1/F3 等按键码直接处理的功能在宿主下不可用；不经 `consumeClick` 的其它模组按键可能无效；JEI/EMI 在宿主界面上的表现；Windows/Linux 未验证。

### Key Entities *(include if feature involves data)*

- **宿主界面**：模组提供的透明界面。只在"面板可见且没有其它界面"时存在，不持有任何物品，只承载面板；任何其它界面出现它就让位。
- **面板可见状态**：面板是否处于打开状态（含服务端的背包会话）。它与"现在有没有显示出来"不是一回事：被聊天、暂停菜单等非容器界面隐藏时，可见状态仍然保留。
- **面板光标**：没有容器界面时面板自己的光标（物品暂存在背包数据里）。本阶段保留，宿主在场时使用它；容器界面在场时使用界面的携带物。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 面板开着时按 E，物品栏在**第一次按键**就打开；连续 20 次"E 开、E 关"没有一次需要再按、没有一次出现界面被盖住或叠在一起。
- **SC-002**: 任意一个其它界面（物品栏、聊天、成就、工作台）关闭后，面板在 **0.3 秒内**重新出现，不需要玩家再按热键。
- **SC-003**: 开发机（`runClientCompat`）上，面板开着时精妙背包的"打开背包"快捷键能打开其界面，关闭后面板回来；若不成立，已在已知限制中登记。
- **SC-004**: 宿主上，005～017 的面板验收项（quickstart 清单）逐项与 019 之前的 HUD 结果一致；容器界面上同一组验收项同样一致。
- **SC-005**: 宿主在场 30 秒，单人游戏的世界时间继续推进（不暂停）；游戏画面与面板关闭时相比没有变暗或模糊。
- **SC-006**: 连续 50 次开关面板和界面切换（热键、E、ESC、聊天混合）后：没有卡住的按键、没有鼠标状态异常、没有残留或重复的宿主；面板光标上物品的总数始终守恒；`run/logs/latest.log` 没有新增报错。
- **SC-007**: 按住移动键时打开、关闭面板，松开后角色不会自己继续移动。
- **SC-008**: 受影响文档里不再有把"无界面 HUD 模式"当作当前行为的描述（`grep` 检查），018 的文档记录了依赖。
- **SC-009**: 在开发机（macOS）上完成验证；Windows/Linux 无法验证，明确登记为未验证。

## Assumptions

- 面板的"可见"状态与背包会话的对应关系沿用现状：被非容器界面隐藏期间，服务端会话保持打开，由现有的会话校验决定是否因为背包不可访问而关闭。
- 宿主在场时世界交互全部失效是用户已接受的代价；ESC 在宿主下关闭面板（沿用现状）是默认行为。
- "吞掉哪些世界动作按键、让哪些通过"的具体清单留给 plan 阶段；原则是：打开界面或切换功能类的按键通过，移动、跳跃、潜行、冲刺、攻击、使用、选取、丢弃等世界动作类按键吞掉。
- 宿主出现时鼠标回到屏幕中心，与原版开界面一致，可以接受。
- 本阶段不新增网络包；面板光标、`MergePanelCursorPayload`、`screenOpen`、Alt 换主手原样保留。
- 开发机是 macOS，只能在本机验证；Windows/Linux 只能推断，登记为未验证。
- 019 先于 018 实现；018 的 plan 在 019 完成后再简化。
