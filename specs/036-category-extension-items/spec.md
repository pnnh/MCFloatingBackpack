# Feature Specification: 分类扩展：10 个扩展件物品

**Feature Branch**: `036-category-extension-items`

**Created**: 2026-11-10

**Status**: Draft

**Input**: 用户决定（2026-11-10）把原计划的顺序调换：先做"物品"，再做"界面"。"分类扩展"的数据与规则（035）已经写好，但没有任何扩展件物品，所以它在游戏里看不见也验证不了。本 feature 给它 **10 个扩展件物品**（食物、工具、武器、盔甲、矿物、农作物、木材、药水、红石、唱片扩展）：物品本身、一张 16×16 平面贴图、合成配方、中英文名称与提示，并把它们注册成 035 的"扩展件解析器"，让放进功能区的扩展件真的给背包增加一行。**界面（分类底色、分隔线、黄点与悬停提示、客户端预览）不在本 feature，是下一个 feature（037）。**

> **编号说明**：`docs/plan/category-extensions.md` 里原来的拆分是 035 数据与规则、036 界面、037 物品。顺序调换后：**035 数据与规则（已完成）→ 036 物品（本 feature）→ 037 界面**。

## 背景与已确认的决策

035 已经做了：背包里的"逻辑行列表"（每行 9 格、一个类别、可见或隐藏）、行数随放着的扩展件数核对（三个功能区 + 面板光标）、放入时的类别判定（我们自己的物品标签 `mcfloatingbackpack:extension/<类别>`，或这只背包标签册里带有类别 id 的手动标签）、转移与自动拾取的目标顺序、行总数上限 35、`ExtensionPacks`（"扩展件解析器"，目前什么都认不出，等着被注册）。本 feature 让它活起来。

已确认的决策（用户，2026-11-09 / 11-10，来自 `docs/plan/category-extensions.md`，不重新讨论）：

1. **名字**：统称"分类扩展"，物品叫"食物扩展""工具扩展""武器扩展""盔甲扩展""矿物扩展""农作物扩展""木材扩展""药水扩展""红石扩展""唱片扩展"；英文 "Food Extension" 等。
2. **形态同标签管理器、垃圾桶、自动拾取**：普通物品、**一张 16×16 的平面贴图**（物品栏、手持、掉落物、展示框都是同一张，不做 3D 模型）、**最大堆叠 1**、进创意栏与 JEI、有合成配方。
3. **可以放进三个功能区（左、右、下）的任一格才有功能**；放在主区域或其它地方它就是普通物品。**允许放多个**（现有的"每区最多一个"只针对垃圾桶、标签管理器、自动拾取）；每放一个，背包多一行 9 格、只存该类别的物品（行的规则见 035）。
4. **配方**：每个扩展件一个配方，符合类别特点，不能太简单；共同点是 **4 个铁锭做"框"**（和垃圾桶、自动拾取的风格一致），其余体现类别。用户看过草案，**暂时没有要改的**。核心材料：

   | 扩展 | 核心材料 |
   |---|---|
   | 食物 | 烟熏炉、木桶、金胡萝卜、面包 ×2 |
   | 工具 | 砂轮、铁镐、铁斧、铁锹、铁锄 |
   | 武器 | 铁剑、弓、盾牌、箭 ×2 |
   | 盔甲 | 锻造台、铁头盔、铁靴子、皮革 |
   | 矿物 | 高炉、钻石、铜锭、金锭、青金石 |
   | 农作物 | 铁锄、水桶、干草块、骨粉 ×2 |
   | 木材 | 切石机、铁斧、任意原木 ×3 |
   | 药水 | 酿造台、玻璃瓶 ×2、下界疣、萤石粉 |
   | 红石 | 红石块、红石比较器、红石中继器、活塞 |
   | 唱片 | 唱片机、钻石、音符盒、任意音乐唱片 |

5. 035 已经把预设标签 `crop`、`potion`、`disc` 加好了，类别 id 与标签 id 一一对应；本 feature 不再动标签。

由我按已有惯例设计的部分（可在 plan 阶段微调）：

- **配方的版型**：有序配方，**4 个铁锭在四个角**，上、下、左、右、中间这 5 格放核心材料。核心材料有 5 件的类别（食物、工具、武器、矿物、农作物、木材、药水）直接放满；**只有 4 件的三个类别（盔甲、红石、唱片）需要补第 5 件**，草案：盔甲 +1 块皮革（两块皮革）、红石 +1 红石粉、唱片 +1 青金石。这三条是我补的，请在 plan 阶段确认或改。"任意原木""任意音乐唱片"用物品标签（`#minecraft:logs`、`#c:music_discs`；plan 阶段查证 `#minecraft:music_discs` 不在本机资源里，改用 NeoForge 的 `#c:music_discs`）。
- **提示文字（tooltip）**：每个扩展件的物品提示一行："放进浮动背包的功能区，增加一行只能存 %s 的格子"，`%s` 取现有预设标签的名字（`tag.mcfloatingbackpack.preset.<id>`：食物、工具……），所以不需要给每个类别另写一条。
- **物品 id**：`<类别id>_extension`，例如 `mcfloatingbackpack:food_extension`、`mcfloatingbackpack:crop_extension`、`mcfloatingbackpack:disc_extension`。
- **一个物品类**：`CategoryExtensionItem(String category)`，最大堆叠 1，别的什么都不做（同 `TagManagerItem`）；`ExtensionPacks` 里注册一个解析器：`stack.getItem() instanceof CategoryExtensionItem item ? item.category() : null`。注册放在两端都执行的初始化里（服务端规则要用，客户端以后的界面也要用）。
- **创意栏**：10 个扩展件排在自动拾取后面，按类别的固定顺序（食物、工具、武器、盔甲、矿物、农作物、木材、药水、红石、唱片）。

## 过渡期的已知限制（界面是下一个 feature，这里如实写明）

本 feature 完成后，扩展行**已经能用**，但没有任何专门的界面：

- 可见行的格子**当作普通格子接在主网格最后面**，没有底色、没有分隔线、没有类别提示；面板合法尺寸（017）按**含扩展行的总格数**重新计算（例如皮革背包 36 格加 1 行 = 45 格，合法列数变成 3、5、9），缩放时有可能和没放扩展件时不一样。
- 拿走扩展件时被隐藏的行**没有任何标识**（没有黄点、没有提示），玩家只会发现格子少了一行；里面的物品仍保存在背包数据里，把对应的扩展件放回去就会接回来（035 的规则）。
- 客户端的拖拽预览、选区、快速转移手势**不知道类别规则**：往不匹配的行拖时预览会照常显示，但松手时服务端拒绝、零变化（035 的规则在服务端）。
- 因此本 feature 的目标是**让规则在游戏里被验证**，不是交付给玩家的最终体验；界面完成之前不会发布。

## Out of Scope（本阶段不做）

- 一切界面：行的底色与分隔线、黄点与悬停提示、锁定/隐藏行的显示、客户端对类别规则的预览与过滤、标签面板里显示"按数据标签推断出的类别" → 下一个 feature。
- 背包搜索与整理（含 `hidden` 条件）→ 之后单独做。
- 配置项、命令、新网络包、新数据组件；新增类别（本批只有 10 个）。
- 修改 035 的规则（若验证中发现 035 的缺陷，另行修复并记录，不在本 feature 的范围内悄悄改）。

## 已查证的事实（读本仓库源码；规格要尊重）

- 现有三个功能件的做法：`TagManagerItem`（`super(properties.stacksTo(1))`）、`TrashCanItem`、`AutoPickupItem` 都是不做任何事的普通物品；`ModItems.ITEMS.register(id, () -> new XItem(new Item.Properties()))`；创意栏在 `ModItems.TAB` 的 `displayItems` 里逐个 `output.accept`；平面物品模型是 `models/item/<id>.json`（`minecraft:item/generated`，`layer0` 指向 `item/<id>`），贴图 `textures/item/<id>.png`（16×16）；配方在 `data/mcfloatingbackpack/recipe/<id>.json`，`type` 是 `minecraft:crafting_shaped`，键的写法是 `{"item": "..."}` 或 `{"tag": "..."}`（标签管理器的配方就用了 `{"tag": "c:strings"}`）。
- 自动拾取的配方是 `IEI / RHR / IDI`（铁锭、末影珍珠、红石、漏斗、钻石），本 feature 沿用"铁锭在角上"的风格。
- 035 的 `ExtensionPacks.register(Function<ItemStack,String>)` 已存在，`categoryOf` 在载入、保存与放入工具区时被调用；注册表为空时什么都认不出。
- 035 的 `ExtensionPackRules.canPlace`（工具区放入检查）只对 `categoryOf` 非空的物品生效；`ToolAreaRules` 不限制扩展件的个数。
- 工具区容量：皮革 19 格、铁 … 下界合金 35 格（左右 = ceil(容量/9) 行，下 = 9+2），所以一只背包最多同时放 35 个扩展件，与行总数上限 35 一致。
- 共用方块图集的现状是 2048×1024（`design/demo/tools/check_atlas_budget.sh`）；物品贴图也进这个图集，所以新增 10 张 16×16 要重新度量。

## 尚未验证（plan 阶段先查证；验证前不得声称已满足）

- 10 张 16×16 贴图让共用图集增加多少：现状 2048×1024，预算不超过 2048；必须在加完后实测，度量不了就写"未度量"。
- 配方里每个原版物品在 1.21.1 的确切 id（`minecraft:smoker`、`minecraft:barrel`、`minecraft:golden_carrot`、`minecraft:grindstone`、`minecraft:smithing_table`、`minecraft:blast_furnace`、`minecraft:hay_block`、`minecraft:bone_meal`、`minecraft:stonecutter`、`minecraft:brewing_stand`、`minecraft:glass_bottle`、`minecraft:nether_wart`、`minecraft:glowstone_dust`、`minecraft:redstone_block`、`minecraft:comparator`、`minecraft:repeater`、`minecraft:piston`、`minecraft:jukebox`、`minecraft:note_block`）与标签 `#minecraft:logs`、`#minecraft:music_discs` 是否存在、能否在配方里作为键使用；有没有哪个配方与现有配方撞车。
- 10 张贴图的来源（ludo.ai / pixellab 生成后缩成 16×16，或自绘）、能否在不同类别间保持统一风格；用什么提示词与流程，记入交付说明。
- 贴图在物品栏、创意栏、JEI、手持、掉落物、展示框里的实际观感；10 个图标放在 18 像素的格子里是否看得出区别（缩小到面板格子的大小）。
- 过渡期里含扩展行的面板在各个档位下合法尺寸与滚动是否可用（017 的规则按更大的总格数重新算）；如果有档位下出现"没有任何合法尺寸"之类的问题，要记录并交给界面 feature。
- 035 验证清单里"游戏里验证不了的几项"在有了扩展件之后能否验证：可见行的网络与组件同步往返、扩展行里放物品的各条路径（点击、拖拽、聚拢、快速转移、自动拾取、垃圾桶取回）、保存时可见行变化后的整份同步、行总数 35 的拒绝与提示。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 10 个扩展件物品：合成、创意栏、外观 (Priority: P1)

玩家能在合成台合成每一种扩展件，也能在创意栏与 JEI 里找到它们；它们是一张平面贴图的普通物品，最大堆叠 1。

**Why this priority**: 没有物品就没有后面的一切。

**Independent Test**: 在创造世界打开创意栏的模组页签；对每个扩展件用配方合成一次；看 JEI 的配方；把它们拿在手上、扔在地上、放进展示框。

**Acceptance Scenarios**:

1. **Given** 创意栏的模组页签，**Then** 能看到 10 个扩展件，排在自动拾取后面，顺序是食物、工具、武器、盔甲、矿物、农作物、木材、药水、红石、唱片，名字依次是"食物扩展"……"唱片扩展"（英文 "Food Extension" ……）。
2. **Given** 一份按配方摆好的材料（四角铁锭 + 5 格核心材料），**When** 在工作台合成，**Then** 得到 1 个对应的扩展件；摆放顺序错误或缺料则合成不出来。
3. **Given** JEI（开发运行时默认带着），**Then** 每个扩展件都能看到它的配方，"任意原木""任意音乐唱片"显示为可替换的一组。
4. **Given** 一个扩展件，**Then** 它的物品栏、手持、掉落物、展示框外观都是同一张 16×16 平面贴图，没有 3D 模型。
5. **Given** 任一扩展件，**When** 尝试堆叠，**Then** 最大堆叠是 1。
6. **Given** 任一扩展件，**When** 看物品提示，**Then** 第二行是"放进浮动背包的功能区，增加一行只能存 食物 的格子"（把"食物"换成该类别的名字；英文同理）。
7. **Given** 10 个扩展件，**Then** 彼此在 18 像素的格子里也能分辨出类别。

---

### User Story 2 - 放进功能区，背包多一行；拿走时数据不丢 (Priority: P1)

玩家把扩展件放进三个功能区的任一格：背包主区域多一行 9 格，只存该类别的物品；拿走时那一行从主区域里消失，里面的物品仍保存在背包里，放回去就回来。

**Why this priority**: 这是分类扩展的核心玩法，也是 035 规则第一次在游戏里被验证。

**Independent Test**: 皮革背包放 1 个食物扩展，往多出的行里放面包、圆石，拿走再放回。

**Acceptance Scenarios**:

1. **Given** 一只没有扩展行的背包，**When** 把食物扩展放进左、右、下区的任一格，**Then** 主区域多出 9 个格子（接在主网格最后面，过渡期没有底色与分隔线）。
2. **Given** 那一行，**When** 往里放面包（食物），**Then** 放得进去；放圆石被拒绝，零变化。
3. **Given** 食物行里有物品，**When** 拿走食物扩展，**Then** 那一行从主区域消失，主区域格数回到原来；**When** 再把食物扩展放回去，**Then** 那一行回来，里面的物品都在。
4. **Given** 食物行是空的，**When** 拿走食物扩展，**Then** 那一行直接消失，之后放回的是新的空行。
5. **Given** 同时放了两个食物扩展和一个工具扩展，**Then** 有两个食物行和一个工具行，按放置的先后接在主网格后面；拿走一个食物扩展：优先删空的食物行，没有空行才隐藏最后一个食物行。
6. **Given** 面板光标上拿着一个扩展件（从功能区拿起、还没放下），**Then** 它的行仍在；把它放进另一个功能区格子，行不跳到最后；只有它真正离开背包（放回物品栏、丢出去）才算拿走。
7. **Given** 一个扩展件在别的途径消失（创造模式删除、被别的模组拿走），**When** 下次打开背包，**Then** 对应的行按 035 的规则被隐藏或删除，没有物品丢失。
8. **Given** 同一类别的行里放了东西、背包被保存重进世界，**Then** 行与物品原样还在。

### User Story 3 - 类别判定：数据标签与手动标签 (Priority: P1)

扩展行只收属于该类别的物品：原版与 `c:` 标签里的物品、带 `food`/`potion_contents` 的物品，以及玩家用标签管理器给物品手动打上类别标签的物品。

**Why this priority**: 判定决定了每一行是否好用。

**Independent Test**: 对每个类别各放几种典型物品、几种不属于的物品；手动打标签。

**Acceptance Scenarios**:

1. **Given** 食物行，**Then** 面包、金苹果、烤土豆放得进去，圆石放不进去；药水行放得进药水与喷溅药水。
2. **Given** 工具行，**Then** 铁镐、剪刀、钓鱼竿放得进去；铁剑放不进去（它属于武器）。
3. **Given** 一个模组物品没有被任何标签收录，**When** 用标签管理器给它打上 `food` 标签并放进食物行，**Then** 放得进去；删掉标签后行里已有的它仍在，只是同类物品放不进去了。
4. **Given** 两个类别都匹配的物品（三叉戟：工具、武器），**Then** 进"第一个有空位的匹配行"（按行的先后）。
5. **Given** 木材行，**Then** 原木、木板、去皮原木、木棍放得进去；红石行放得进红石粉、红石块、活塞、中继器、拉杆；唱片行放得进音乐唱片。

---

### User Story 4 - 转移、自动拾取、聚拢、垃圾桶：现有功能对扩展行生效 (Priority: P1)

035 已经把规则做在服务端；这里在游戏里验证它们真的工作。

**Why this priority**: 这些路径在 035 里只有单元测试，没有在游戏里跑过。

**Independent Test**: 放好一个食物扩展，把面包放在物品栏，用 Ctrl 快速转移；开自动拾取捡面包；双击聚拢。

**Acceptance Scenarios**:

1. **Given** 背包有一个食物行，**When** 把物品栏里的面包用 Ctrl 快速转移进背包，**Then** 面包先并进食物行里已有的没满的面包栈，再放食物行的空格，放不下的才进主区域。
2. **Given** 有自动拾取（左区），地上有面包，**Then** 同样先进食物行；食物行满了才进主区域。
3. **Given** 没有匹配的行，**Then** 物品只进主区域，与有扩展件之前完全一样。
4. **Given** 双击聚拢面板里的某种物品，**Then** 范围包括主区域和所有可见行里的同种物品；隐藏行里的不参与。
5. **Given** 垃圾桶、选区、Ctrl 转出，**Then** 对可见行与主区域一视同仁；隐藏行里的物品不会被动。
6. **Given** 垃圾桶取回物品，**Then** 取回的物品按同样的顺序（匹配的可见行 → 主区域）放回。
7. **Given** 点击、拖拽往不匹配的行放物品，**Then** 服务端拒绝、格子与光标零变化（客户端预览可能显示，这是过渡期的已知限制）。
8. **Given** 创造模式的"生存物品栏"页签，**Then** 以上操作与生存模式一致（特别留意 027 的创造光标：拿着物品的光标在面板与物品栏之间不丢东西，**035 之后发现过一次创造模式下背包丢失的事件，原因未明；这里要在验证时留意并保持诊断日志打开**）。

---

### User Story 5 - 数量上限、升级与保存 (Priority: P2)

行总数最多 35，升级保留，保存与快照不丢。

**Why this priority**: 边界与持久化。

**Independent Test**: 下界合金背包放满扩展件；升级、快照恢复。

**Acceptance Scenarios**:

1. **Given** 一只背包已有 35 个行（可见 + 隐藏），**When** 再放一个会新增一行的扩展件，**Then** 放不进去，格子与光标零变化，并给出提示；放一个能接回隐藏行的扩展件不受限。
2. **Given** 带扩展行与隐藏行的背包，**When** 在锻造台升级，**Then** 扩展行、隐藏行与里面的物品都保留，工具区里的扩展件仍在。
3. **Given** 带扩展行的背包，**When** 030 的备份恢复，**Then** 行与物品随内容一起恢复。
4. **Given** 一只背包在一个玩家物品栏里、另一只在手上，**Then** 各自的行互不影响（每只背包各自保存）。
5. **Given** 背包放在不同来源（手上、胸甲槽、Curios、Accessories），**Then** 扩展件与行的行为一致。

---

### Edge Cases

- 把扩展件放进主区域（不是功能区）：它只是普通物品，不产生行。
- 在创造模式用创意栏直接拿 35 个以上扩展件放进一只皮革背包：皮革的功能区只有 19 格，放不满 35 个；下界合金 35 格正好放满。
- 一个扩展件的 `count > 1`（旧数据或别的模组）：按 1 个计，记日志（035 的防御性规则）。
- 扩展件在面板光标上时关闭面板或创造界面：回到物品栏，按 035 的规则算"拿走"。
- 工具区里放了扩展件，把背包升级成更大一档：工具区容量变大，行不受影响。
- 没有 Curios/Accessories 的环境（`-PcleanRuntime`）：功能不受影响。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: MUST 新增 10 个物品 `mcfloatingbackpack:{food,tool,weapon,armor,ore,crop,wood,potion,redstone,disc}_extension`，都是 `CategoryExtensionItem`：不做任何事的普通物品，**最大堆叠 1**。
- **FR-002**: 每个物品 MUST 只有**一张 16×16 的平面贴图**（`textures/item/<id>.png`）和一个 `minecraft:item/generated` 的物品模型（`models/item/<id>.json`），物品栏、手持、掉落物、展示框外观一致，不做 3D 模型；贴图 MUST 一次性生成（ludo.ai 或 pixellab 等生成后缩成 16×16，或自绘）；10 个图标风格统一且彼此可分辨；生成方式与来源记入交付说明。
- **FR-003**: 每个物品 MUST 有一个**有序合成配方**（`data/mcfloatingbackpack/recipe/<id>.json`）：四角是铁锭，其余 5 格按"背景与已确认的决策"第 4 条的核心材料；只有 4 件核心材料的盔甲、红石、唱片补第 5 件（草案：皮革、红石粉、青金石），结果数量 1；所有配方互不相同，不与已有配方撞车。
- **FR-004**: 创意栏 MUST 在自动拾取后面按类别固定顺序列出 10 个扩展件；JEI 里 MUST 能看到每个配方。
- **FR-005**: 中英文语言键 MUST 齐全：`item.mcfloatingbackpack.<id>_extension`（名字，中文"食物扩展"……"唱片扩展"，英文 "Food Extension" ……）与一条通用的物品提示（带 `%s` 的"放进浮动背包的功能区，增加一行只能存 %s 的格子"，`%s` 用 `tag.mcfloatingbackpack.preset.<类别>` 的名字）；两种语言的键集合一致。
- **FR-006**: 物品提示 MUST 显示在每个扩展件上（所有 10 个），内容按当前语言。
- **FR-007**: MUST 在两端都执行的初始化里调用 `ExtensionPacks.register(...)`，让 `CategoryExtensionItem` 的类别成为 035 的"扩展件解析器"的答案（其它物品返回 `null`）；注册只做一次。
- **FR-008**: 放进左、右、下区任一格的扩展件 MUST 使背包多一行对应类别的 9 格（035 的规则），可以放多个相同的；放在主区域或其它地方 MUST 没有任何功能。
- **FR-009**: 行里放入物品的规则、拿走/放回的规则、行总数 35 的上限与提示、转移与自动拾取的目标顺序、聚拢范围，MUST 与 035 的 spec 完全一致；本 feature 不修改这些规则。
- **FR-010**: 本 feature MUST NOT 新增界面（底色、分隔线、黄点、悬停提示、客户端预览）、设置项、命令、网络包、数据组件；**协议版本 MUST 保持 17**。
- **FR-011**: 共用方块图集 MUST 不超过 2048×1024；加完 10 张贴图后 MUST 度量并记录，度量不了就如实写"未度量"。
- **FR-012**: 没有扩展件时 MUST 与 035 完成时的行为完全一致（旧背包、没有扩展行的新背包都不受影响）。
- **FR-013**: 过渡期的已知限制（可见行当作普通格子接在主网格后面、隐藏行无标识、客户端预览不知道类别规则、合法尺寸按含行的总格数重算）MUST 写进交付说明，且不得被说成"最终体验"。

- **FR-014**: 一个会新增行的扩展件在行总数已达 35 时被拒绝（035 的规则）的同时，MUST 给玩家一条提示（actionbar：中文"这只背包的扩展行已达上限（35）"、英文 "This backpack already has the most extension rows (35)"）。这是补上 035 留下的缺口（035 只做了拒绝与零变化，没有提示），不是新规则。

### Key Entities

- **扩展件（CategoryExtensionItem）**：一个类别 id + 最大堆叠 1 的普通物品；10 个实例。
- **扩展件解析器（ExtensionPacks，035）**：被注册后回答"这个物品栈是哪个类别的扩展件"。
- **配方**：10 个有序配方，四角铁锭 + 5 格核心材料。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 10 个物品都能在创意栏与 JEI 里找到，每个都能按配方合成，物品提示与名字中英文都对。
- **SC-002**: 把任一扩展件放进功能区，背包多一行对应类别的 9 格；拿走与放回的各种情形（有物品、空行、多个、光标上）结果符合 035 的 US1 场景，**没有任何物品丢失**。
- **SC-003**: 035 的 quickstart 第 C 节里"游戏里验证不了的几项"在本 feature 的客户端会话里被验证或如实写成"仍未验证"。
- **SC-004**: 图集度量 2048×1024（或如实记录"未度量"）；协议仍是 17；自动化测试全部通过（含新增的资源检查：10 个物品的模型、配方、语言键与注册表一一对应）。
- **SC-005**: 没有扩展件时的行为与 035 完全一致（回归检查）。

## Assumptions

- 035 的规则（行列表、核对、放入检查、目标顺序）按它的 spec 工作；本 feature 是它的第一个真实使用者，验证中发现的缺陷另行处理。
- 开发运行时（`./gradlew runClient`）默认带 JEI、Curios、Accessories、精妙背包、旅行者背包。
- 过渡期的含扩展行面板只用于验证，界面 feature 完成前不发布。
