# Research: 010-backpack-texture-budget

本阶段把 spec 里的几个"未验证假设"变成了实测结论。**凡写"实测"的都是在本机跑 `./gradlew runClient` 读 `run/logs/latest.log` 里 `blocks.png-atlas` 一行得到的；凡写"读源码"的来自 `neoforge-21.1.251-sources.jar`；凡写"推断"的没有直接验证。**

实验方法：把 5 张贴图临时替换成不同尺寸，起客户端 45 秒，读图集尺寸，实验结束后把工作区还原（已用 `cmp` 确认与提交内容逐字节一致）。

## 最重要的发现：法线贴图 `_n` 其实被拼进了共用图集（推翻了 spec 的一个假设）

spec 和 009 都写过"法线贴图没有被模型引用，所以不进图集"。**这是错的。**

- **依据（读源码）**：原版 `assets/minecraft/atlases/blocks.json` 有一条 `{"type": "directory", "source": "item", "prefix": "item/"}`，它会把**所有命名空间**下 `textures/item/` 里的**全部 PNG** 当作精灵拼进图集，不管有没有模型引用。`<tier>_floating_backpack_n.png` 就在这个目录里。
- **依据（实测）**：见下表。基础色贴图缩到 128、`_n` 仍是 1024² 时，图集依然是 4096×2048；把 `_n` 挪走后同样的 128 就回到 1024×1024（见矩阵第 1、2 部分对比）。

### 实测矩阵（blocks 图集尺寸）

| 场景 | 基础色边长 | 图集尺寸 |
|---|---|---|
| 第 1 部分：5 张 `_n`（1024²）都在图集里（现状） | 1024 | **4096×4096** |
| | 768 | 4096×4096 |
| | 512 | 4096×2048 |
| | 384 / 256 / 128 | 4096×2048 |
| 第 2 部分：`_n` 临时移出资源目录 | 1024 | 4096×2048 |
| | 512 | 2048×1024 |
| | 256 | 1024×1024（回到纯原版水平） |
| 第 3 部分：`_n` 在目录里，但用图集 `filter` 源把它们剔除 | 1024 | 4096×2048 |
| | 768 | 4096×2048 |
| | **640** | **2048×2048** |
| | **512** | **2048×1024** |

结论：
1. 现在 4096×4096 是 **10 张** 1024² 贴图（5 基础色 + 5 法线）一起撑出来的，光缩基础色解决不了问题（基础色缩到 128 图集仍是 4096×2048）。
2. 只要把 `_n` 排除出图集，同样的 1024 基础色就能让图集小一半（4096×4096 → 4096×2048）。
3. 要满足 spec 的 2048×2048 上限，**在排除 `_n` 的前提下**，基础色最大是 **640**（正好 2048×2048，没有余量）；**512** 得到 2048×1024（有一倍余量）。768 不行。

## Decision 1: 用图集 `filter` 源把 `_n` 排除出共用图集

**Decision**: 新增 `src/main/resources/assets/minecraft/atlases/blocks.json`：

```json
{ "sources": [ { "type": "minecraft:filter",
                 "pattern": { "namespace": "mcfloatingbackpack", "path": "item/.*_n" } } ] }
```

**Rationale**:
- **读源码**：`SpriteSourceList.load` 对 `atlases/blocks.json` 取 `getResourceStack`，把所有资源包里的同名文件的 `sources` 依次拼成一个列表；`SourceFilter.run` 调用 `output.removeAll(pattern)`，从此前已收集的精灵里删除匹配项。所以我们的文件排在原版的 `directory` 源之后，就能把 `_n` 删掉。
- **实测**：矩阵第 3 部分证明它有效（`_n` 在目录里、1024 基础色时，图集与"`_n` 不存在"时一样是 4096×2048）。
- 这是原版机制，不是第三方依赖，不违反宪法 IV；只匹配本模组命名空间，不影响其它模组。

**推断/风险（未验证）**：光影加载器（Iris / Oculus / NeOculus）的 PBR 支持是自己从资源里按 `<精灵名>_n` 读取法线贴图的（推断，我没有读 Iris 的源码，本机也没装），而不是从原版图集里取，所以把 `_n` 从原版图集里剔除应当不影响光影包看到法线。**必须在装了光影包的客户端里确认**，在此之前不能宣称法线贴图"继续可用"（spec FR-006/US2 场景 4）。

**Alternatives considered**:
- 把 `_n` 移到图集不扫描的目录（例如 `textures/pbr/`）：光影包按"精灵名 + `_n`"找，目录一变就找不到了，会直接破坏光影支持，排除。
- 不管 `_n`，只缩基础色：基础色缩到 128 图集仍是 4096×2048，达不到上限，排除。

## Decision 2: 基础色贴图用 512×512，不用 640

**Decision**: 每档基础色贴图 512×512。

**Rationale**:
- 实测 512 → 图集 2048×1024（满足上限 2048×2048 且有一倍余量）；640 → 2048×2048（刚好顶着上限，没有余量）。
- **余量的意义**（推断）：玩家同时装了其它带物品/方块贴图的模组时，图集内容会增加；512 版本的 2048×1024 在面积翻倍内仍可能保持在 2048×2048 以内，640 版本只要多出一点就会跳到 4096×2048，立刻超出上限。
- 显存见 Decision 5：512 版 11MB，640 版 22MB。

**Alternatives considered**: 640（质量略好、没有余量，排除）；384/256（质量损失更大且收益已饱和：256 才回到纯原版 1024×1024，而 512 已经只有 2048×1024）。

## Decision 3: 缩放方式用"盒式缩放 + 轻锐化"，不用 Lanczos

**Decision**: 从 GLB 里取出的 2048 原图出发，`BOX` 缩到 512，再做一次 `UnsharpMask(radius=1.0, percent=90, threshold=2)`，然后按各档原有的 gamma 调亮（皮革 0.62、铁 0.89、下界合金 0.91、金与钻石不调）。

**依据（实测，5 档平均，边缘对比度保留用 2048 原图的总变差比，1.0=与原图相同）**：

| 方式 | 皮革 TV | 铁 TV | 金 TV | 钻石 TV | 下界合金 TV |
|---|---|---|---|---|---|
| 现状：1024 Lanczos | 0.77 | 0.81 | 0.79 | 0.79 | 0.80 |
| 512 Lanczos（第一版"糊"的做法） | 0.63 | 0.66 | 0.66 | 0.65 | 0.64 |
| 512 BOX | 0.59 | 0.61 | 0.61 | 0.59 | 0.60 |
| 512 NEAREST | 0.68 | 0.70 | 0.70 | 0.69 | 0.70 |
| **512 BOX + 轻锐化** | **0.83** | **0.87** | **0.89** | **0.87** | **0.85** |

- 目视对比（`compare2.png`，把 2048 原图中 300×300 的区域放大到 330 像素，比游戏里近得多）：512 BOX+轻锐化的边缘硬度接近现状 1024 Lanczos，明显好于 512 Lanczos；金色铆钉处有轻微亮边，可接受。
- 总变差比只是代理指标，**锐化后的数值超过 1024 现状，部分来自锐化造成的人为对比**，不能直接当成"比现状更清晰"；它说明的只是"不比现状软"。

**"按体素网格对齐缩放"这条路不可行（实测）**：在 2048 皮革贴图上统计近似常色的游程长度，分布从 4 像素到 24 像素以上（最常见 4、5、6、8、9……），没有单一的体素格子尺寸，各 UV 区域密度不同，无法找到一个全局整数倍缩放。

**重要纠正（对之前结论的修订）**：此前"512 看起来糊"的玩家反馈（皮革第一版 512），发生在 `flip_v` 的 bug 还没修好的时候，同一张截图里贴图本来就是错位的，所以**它不能证明 512 在 UV 正确的情况下就糊**。我们从来没有在 UV 正确的情况下在游戏里看过 512 的背包。因此 512 是否达到"近看略软但不糊"，当前只有离线对比的证据，**必须在游戏里验证**（quickstart）。

**Alternatives considered**: 640 最近邻（TV 0.73~0.75，但非整数倍缩放会有不均匀的锯齿，且仍要承担 640 没有余量的问题）；纯最近邻 512（TV 0.68~0.70，细线条会被丢掉）。

## Decision 4: 不走"背包贴图不进共用图集"这条路

**Decision**: 不采用独立纹理（非图集）方案。

**Rationale（读源码）**:
1. **模型 JSON 里的贴图图集是写死的**：`BlockModel.Deserializer.getTextureMap` 里 `ResourceLocation resourcelocation = TextureAtlas.LOCATION_BLOCKS`，所有 `textures` 都用它；`UnbakedGeometryHelper.resolveDirtyMaterial` 的 javadoc 明说"The target atlas will always be TextureAtlas.LOCATION_BLOCKS"。所以走标准的烘焙模型路径，贴图只能在 blocks 图集里。
2. 唯一的非图集路径是 NeoForge 的"renderable"：`ObjModel` 里的 `bake(CompositeRenderable.PartBuilder, ...)` 用的是 `"textures/" + path + ".png"` 的独立贴图位置（`UnitTextureAtlasSprite`）。要用它得写：自己调用 `ObjLoader.INSTANCE.loadModel` 加载模型、注册 `IClientItemExtensions.getCustomRenderer`（自定义物品渲染器）、重写 `BackpackBackLayer`。这等于绕开整条标准烘焙模型管线，JEI / 物品栏图标 / 手持变换 / 光照都要自己兜底。
3. **独立贴图没有 mipmap**：`SimpleTexture.load` 里 `TextureUtil.prepareImage(id, 0, ...)` 和 `image.upload(..., false, true)`，只上传第 0 级（读源码）。把一张 512 或 1024 的贴图缩小显示成十几二十像素的图标时，没有 mipmap 会严重走样闪烁（推断：这是没有 mipmap 的通常后果，没有实测）。图集内的精灵反而有 mipmap（日志里的 `x4`）。
4. 工作量与风险远大于本 feature 的范围，spec 的范围边界也写明"不改变模型几何、玩法"，大改渲染管线超出了"贴图预算"。

**Alternatives considered**: 独立图集（`RegisterMaterialAtlasesEvent` 能注册新图集，但模型 JSON 的贴图写死 blocks，需要自写几何加载器），工作量同上，排除。

## Decision 5: 显存按图集尺寸推算，没有实测 GPU 显存

**Decision**: 显存增量用图集尺寸推算：`宽 × 高 × 4 字节 × 1.332`（5 级 mipmap，日志里的 `x4` 是 mip 最大级，共 5 级：1 + 1/4 + 1/16 + 1/64 + 1/256）。

| 图集尺寸 | 估算显存 |
|---|---|
| 1024×1024（纯原版 / 009 之前，实测） | 约 5.6MB |
| 2048×1024（**本方案**，实测尺寸） | 约 11.2MB |
| 2048×2048（上限） | 约 22.3MB |
| 4096×2048 | 约 44.7MB |
| 4096×4096（现状，实测尺寸） | 约 89.4MB |

**说明**: 图集**尺寸**是实测，显存是由尺寸推算的，没有在 GPU 里直接测量（Minecraft 不提供读取单张纹理显存的接口，需要外部 GPU 工具）。本方案相对现状节省约 78MB（约 87%），相对纯原版仍多约 5.6MB（2 倍面积）。

## Decision 6: 亮度偏差在 ±10% 以内（实测）

**Decision**: 缩放后沿用各档原有的 gamma，不需要重新校正。

**依据（实测）**：按网格实际使用的 UV 区域面积加权，对比各候选 512 贴图与当前文件（1024 Lanczos + gamma）的平均亮度（单位：偏差百分比）：

| 档位 | 当前亮度 | 512 Lanczos | 512 BOX | 512 NEAREST | 512 BOX+轻锐化 |
|---|---|---|---|---|---|
| 皮革 | 61.8 | +0.0% | +0.5% | −0.1% | +0.2% |
| 铁 | 57.0 | −0.0% | +0.3% | −0.1% | +0.6% |
| 金 | 119.0 | +0.0% | +0.2% | −0.0% | +0.2% |
| 钻石 | 113.5 | +0.0% | +0.2% | −0.1% | +0.6% |
| 下界合金 | 46.6 | +0.3% | +0.9% | +1.2% | +2.9% |

所有方案、所有档位偏差都在 ±3% 以内，远小于 spec SC-004 的 ±10%。所选方案（BOX+轻锐化）最大偏差是下界合金的 +2.9%。

## Decision 7: 法线贴图同样降到 512

**Decision**: `_n` 贴图也从 GLB 的 2048 原图重新出，缩到 512，并沿用 009 的 LabPBR 转换（G 翻转，B/A 填 255）。

**Rationale**: `_n` 被排除出图集后不再影响图集尺寸，保持 1024 也不会撑大图集；但光影加载器通常期望 PBR 贴图和基础色同尺寸（推断，未验证），尺寸一致更稳妥，同时让随包的贴图文件体积明显变小（具体数字在实现后再量）。

**风险（推断/未验证）**: 光影包下法线细节会比 1024 少一半分辨率；需要在装了光影包的客户端里确认凹凸效果仍然可见。

## Decision 8: 不做"按硬件自动选择贴图质量"

**Decision**: 单一质量档，不做自适应。

**Rationale**: 实测显示单一的 512 + 排除 `_n` 已经把图集降到 2048×1024，满足上限（spec Assumptions 里"除非单一档无论如何满足不了才放宽"的条件没有触发），自适应只会带来资源包规则、设置界面和测试矩阵的额外复杂度。

## 对 spec / 009 的修订（本次发现）

1. 010 spec 的"法线贴图不进图集"（边界情况、FR-006、Assumptions）是**错的**，见上；已修订。
2. 010 spec / 009 研究里"512 会把方格纹理抹糊（玩家反馈"糊"）"的归因不准确，已修订为"离线对比 + 未在 UV 正确的情况下验证"。
3. 009 已知限制 1 写的是"五张 1024×1024 贴图撑大图集"，实际是 **10 张**（含 5 张 `_n`）；已修订。
