# Feature Specification: 背包贴图预算与共用图集占用

**Feature Branch**: `010-backpack-texture-budget`

**Created**: 2026-11-04

**Status**: Draft

**Input**: User description: "009 把五档背包换成雕刻网格模型，每档一张 1024×1024 基础色贴图。这些贴图会被拼进游戏共用的方块图集，实测日志显示该图集从 1024×1024 涨到 4096×4096，影响所有玩家的所有方块与物品贴图。需要在尽量保持背包外观质量的前提下，让背包贴图对共用图集（以及显存）的占用降到合理范围，并定义'合理范围'的可衡量标准，不预设技术方案。来自 009 已知限制 1 / tasks F001。"

## Clarifications

### Session 2026-11-04

- Q: 共用方块图集的可接受上限是多少？ → A: **2048×2048**。（估算显存约 22MB，对比现在 4096×4096 的约 89MB；5 张 1024² 贴图约 520 万像素放不进 2048² 的约 420 万像素，所以方案必须让背包贴图变小或不进共用图集，具体怎么做留给 plan 阶段。）
- Q: 外观清晰度相对当前 1024×1024，下降到什么程度可以接受？ → A: **近看略软但不糊**——皮革方格纹理仍能一格一格地分辨出明暗变化，细节略有损失可以接受；不接受糊成色块或噪点。
- Q（有合理默认值，未向用户提问）: 是否允许按玩家设置/硬件自动选择不同贴图质量？ → A: 默认**不做**，见 Assumptions。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 不用背包的玩家也不为它多付显存代价 (Priority: P1)

只要安装了本模组，游戏启动时背包贴图就会被一并加载。目前这会让游戏里**所有**方块和物品共用的那张大图集的边长扩大 4 倍（实测日志里 `blocks.png-atlas` 从 1024×1024 变成 4096×4096），显存占用按估算从约 6MB 涨到约 85MB。这笔开销由所有玩家承担，包括从来没拿过这个背包、只是装了这个模组的玩家。玩家希望安装本模组之后，游戏的整体显存与兼容性占用不要被背包贴图明显拖大。

**Why this priority**: 它是 009 记录的影响面最大的已知问题：被影响的不是背包用户，而是所有玩家的所有贴图；而且这是玩家在设置菜单里无法规避的代价。

**Independent Test**: 在只装原版和本模组的干净客户端启动游戏，读取游戏日志里共用方块图集的尺寸，对比装本模组前后的数值；确认增长在可接受范围内。

**Acceptance Scenarios**:

1. **Given** 干净的客户端（原版 + 本模组，无其它模组与资源包），**When** 启动游戏到主菜单，**Then** 共用方块图集的尺寸不超过 **2048×2048**（当前为 4096×4096）。
2. **Given** 同一个客户端，**When** 玩家从未拿到过任何背包，**Then** 背包贴图带来的显存增量与拿到了背包的玩家相同、不随是否使用而变化，且不超过上述上限所对应的增量。
3. **Given** 玩家同时安装了其它带大量贴图的模组或高清资源包，**When** 启动游戏，**Then** 背包贴图对图集的增量不应再成为触发图集继续翻倍的主要原因（见边界情况）。

---

### User Story 2 - 用背包的玩家看到的背包仍然清晰 (Priority: P1)

玩家拿到背包后，在物品栏图标、手持、背在身上三种场景下看到的背包，应当仍然保持 009 确认过的外观：皮革的方格纹理清晰，扣具、口袋、铆钉等细节可辨，五个等级一眼可区分，亮度不被破坏。降低贴图占用不能以"糊成一团"为代价（皮革第一版用 512×512 时，玩家反馈过"糊"；**但那次反馈发生在 UV 翻转 bug 修复之前，不能当作 512 本身不行的证据**，见 research.md）。

**Why this priority**: 与 US1 同等重要：只要外观明显变差，降低占用就失去意义——玩家宁可要原来的清晰度。两者之间的取舍是本功能的核心难点。

**Independent Test**: 把降低占用后的五档背包与当前 1024×1024 版本放在同一个场景里逐档对比（图标、手持、背上），并做一次盲测，看观察者是否认为清晰度可接受。

**Acceptance Scenarios**:

1. **Given** 降低占用后的皮革背包，**When** 在手持和背上两个场景下近看，**Then** 方格纹理仍能分辨出一格一格的明暗变化，不是糊成色块或噪点；清晰度的下降程度以"近看略软但不糊"为底线：方格纹理仍能一格一格地分辨出明暗变化，细节略有损失可以接受，但不得糊成色块或噪点。
2. **Given** 降低占用后的五个等级，**When** 观察者不看物品名称，**Then** 仍能凭外形与配色区分全部五个等级（沿用 009 SC-001 的口径）。
3. **Given** 降低占用后的任意等级，**When** 查看图标、手持与背上，**Then** 朝向仍是正面（扣具与口袋的一面），亮度与当前版本相比没有明显变化。
4. **Given** 玩家安装了光影包，**When** 查看背包，**Then** 法线贴图带来的凹凸效果仍然可用。

---

### User Story 3 - 低端硬件也能正常启动和渲染 (Priority: P2)

玩家使用的是较旧的集成显卡或显存较小的设备。过大的图集可能超出该显卡支持的最大纹理尺寸，或者把显存挤满。玩家希望安装本模组后，游戏仍能正常启动、方块和物品不出现缺失或花屏。

**Why this priority**: 它是 US1 的一个具体后果，也是"部分低端硬件能否承受未知"这一条的验证场景；但需要特定硬件才能验证，因此优先级低于 US1/US2。

**Independent Test**: 在最大纹理尺寸较小的环境（真实旧硬件，或能限制纹理尺寸的测试环境）里启动游戏，确认图集创建成功、没有贴图缺失、没有启动报错。

**Acceptance Scenarios**:

1. **Given** 一个最大纹理尺寸为 2048 的环境，**When** 启动游戏，**Then** 共用图集创建成功，方块和物品贴图完整，没有缺失贴图或启动失败。
2. **Given** 同一环境，**When** 玩家拿到并使用任意等级背包，**Then** 外观显示正常，没有因为贴图加载失败而显示成缺失贴图（紫黑块）。

---

### User Story 4 - 维护者能度量并守住预算 (Priority: P3)

维护者（本项目开发者）需要有一个可重复的方法来度量"背包贴图对图集和显存的占用"，并在以后新增或替换背包贴图（例如新等级、更换素材）时，能知道是否超出预算，而不是等玩家反馈才发现图集又被撑大了。

**Why this priority**: 不直接影响玩家，但这次问题就是因为没有预算和度量手段、直到 009 实测日志才发现。

**Independent Test**: 维护者按文档里记录的度量方法，能得到当前占用数字，并判断它是否在预算内。

**Acceptance Scenarios**:

1. **Given** 仓库中的预算说明，**When** 维护者想知道当前背包贴图是否超预算，**Then** 能按说明得到共用图集尺寸与估算显存增量，并与预算对比。
2. **Given** 维护者新增了一张尺寸更大的背包贴图，**When** 按同样方法度量，**Then** 能发现它使图集超出预算。

---

### Edge Cases

- **玩家使用高清资源包或装了其它大贴图模组**：此时共用图集本来就更大，背包贴图的增量应当足够小，不会成为让图集继续翻倍的那一张"压垮骆驼的稻草"。
- **只想要小贴图的玩家**：目前玩家无法单独关闭背包贴图的开销（贴图随模组加载）。是否提供可选的质量档位，见 Assumptions。
- **贴图分辨率与方格纹理的关系**：清晰度对比（把 2048 原图缩小后用最近邻放大到同尺寸）显示：低于 256 时方格纹理糊成噪点而不是变成清晰的像素风；512 用 Lanczos 缩放会把原本清晰的方格纹理抹软（用盒式缩放加轻锐化后与 1024 现状接近，见 research.md）；1024 基本保持原图清晰度。所以"一刀切降到 32/64"不可行，这是本功能最核心的取舍。金色五金件的边缘在 2048 原图里本身就是软边，与分辨率无关，不能当作本功能引入的模糊。
- **法线贴图**：**研究阶段发现此前的判断是错的**——图集会扫描 `textures/item/` 下的所有 PNG，5 张 `_n` 法线贴图（1024²）也被拼进了共用图集，与 5 张基础色一起共 10 张撑出了 4096×4096。所以法线贴图**在本问题范围内**：必须让它们不再占用共用图集（实测依据见 research.md）。
- **亮度**：当前亮度是按贴图平均亮度做过校正的；改变贴图分辨率或处理方式时，不应因此让背包明显变亮或变暗。
- **光影包**：装了光影包的玩家仍应看到法线带来的凹凸。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须使安装本模组后的游戏共用方块图集尺寸不超过 2048×2048（宽和高都不超过 2048）。
- **FR-002**: 背包贴图对共用图集（及显存）的增量必须与玩家是否拿过、使用过背包无关，并且不超过上限对应的增量。
- **FR-003**: 降低占用后，五个等级的背包在图标、手持、背上三种场景下的清晰度必须达到"近看略软但不糊"的底线：方格纹理仍能一格一格地分辨，不得糊成色块或噪点。
- **FR-004**: 降低占用后，五个等级仍必须可区分，且朝向（正面朝向观察者）与 009 保持一致。
- **FR-005**: 降低占用后，背包的整体亮度相对当前版本的偏差必须在可接受范围内（默认 ±10%，见 SC-004），不得因处理方式变化而明显变亮或变暗。
- **FR-006**: 法线贴图必须继续可用（光影包下凹凸效果仍然可见），并且不得占用共用图集。
- **FR-007**: 本功能不得改变模型几何、不得改变任何既有玩法（容量、升级、打开/关闭规则、面板、库存、互拖），不得引入对第三方模组或光影包的硬依赖。
- **FR-008**: 版本库必须记录背包贴图占用的度量方法与预算数值（共用图集尺寸、估算显存增量、测量环境），使维护者能重复测量并发现超预算。
- **FR-009**: 在最大纹理尺寸为 2048 的硬件环境下，游戏必须能正常创建图集并显示背包，不得出现贴图缺失或启动失败。

### Key Entities

- **共用方块图集**：游戏把所有方块与物品贴图拼成的一张大图；它的尺寸决定显存占用，也受 GPU 最大纹理尺寸限制。背包贴图是其中的一部分，其尺寸会推动整张图集的尺寸。
- **背包贴图**：每个等级一张基础色贴图（当前 1024×1024）；另有每档一张法线贴图（目前也被拼进了共用图集，是图集膨胀的一半原因，必须排除）。
- **贴图预算**：对背包贴图占用共用图集与显存的上限，以及度量它的方法和测量环境。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 干净客户端（原版 + 本模组）启动后，共用方块图集的宽和高都不超过 2048。当前为 4096×4096，**尚未达成**。
- **SC-002**: 背包贴图带来的共用图集显存，在不使用背包与使用背包两种情况下相同，且按估算不超过约 22MB（2048² × 4 字节 + mipmap）。当前按估算约 89MB（4096²），是估算值，未在游戏内测量。
- **SC-003**: 在盲测中，不少于 80% 的观察者认为降低占用后的皮革背包"近看略软但不糊"，即方格纹理仍能分辨、不是色块或噪点。
- **SC-004**: 降低占用后，各等级背包按网格实际使用区域面积加权的平均亮度，与当前版本相比偏差不超过 ±10%。
- **SC-005**: 5 名观察者不看名称，凭图标和背上外形区分全部五个等级（每人 5/5，沿用 009 SC-001）。
- **SC-006**: 在最大纹理尺寸为 2048 的验证环境中，游戏能正常启动、背包显示正常，无缺失贴图。
- **SC-007**: 维护者仅凭仓库里的说明，在 10 分钟内能测得共用图集尺寸并判断是否超预算。

## Assumptions

- 已知张力（来自澄清结果，并经研究阶段修订）：图集里实际有 **10 张** 1024² 贴图（5 基础色 + 5 法线），约 1050 万像素，远放不进 2048² 的约 420 万像素。已有证据：低于 256 时方格纹理糊成噪点；之前 512 的"糊"反馈发生在 UV 翻转 bug 修复之前，并不能证明 512 本身不行；源素材是对齐的体素网格，换成保持硬边的缩放方式是否能让 512 保持清晰是**未验证的假设**，需要在 plan 阶段实测。
- 本 feature 只处理贴图预算与图集占用，不改变模型几何，不修网格开放边（009 F003），不做帧率/面数的性能预算（009 F002），不做高光贴图。
- 具体技术方案（降分辨率、单独图集、按需加载、动态降级等）属于 plan 阶段的决定，本 spec 不预设；但方案必须满足上面的需求与成功标准。
- 默认**不引入**"根据玩家设置或硬件自动选择不同贴图质量"这类自适应方案：它会带来额外的资源包规则、设置界面与测试矩阵，复杂度与收益不成比例；如果 plan 阶段发现单一质量档无论如何都无法同时满足 US1 与 US2，再回头与用户确认是否放宽。
- 当前事实依据：游戏日志里 `blocks.png-atlas` 一行，009 之前（贴图为 128×136 级别）为 1024×1024，009 之后为 4096×4096；估算显存按每像素 4 字节加 mipmap 约 1/3 计算，只是估算，plan 阶段需要在游戏内实测。
- 低端或旧集显的最大纹理尺寸是否低于 4096 **未验证**，不能当作已知事实；plan 阶段需要给出验证办法。
- 贴图的亮度已经按平均亮度做过 gamma 校正；缩放贴图的方式不应改变这一校正的效果，如果改变了需要重新校正。
- 本功能不得修改 `docs/ideas/` 目录（用户手写的想法文件）；相关规划或设计文档如需另写，放在 `docs/plan/`。
