# Feature Specification: 分类扩展：数据与规则

**Feature Branch**: `035-category-extension-rules`

**Created**: 2026-11-09

**Status**: Draft

**Input**: 用户描述："增加几个新的扩展功能区组件，放在主区域以外的 3 个区域才会生效……放置后它会为目标背包增加一行存储空间，这一行只能存特定类别的物品。"整体规划与全部决策见 `docs/plan/category-extensions.md`。"分类扩展"是一组放进浮动背包三个功能区任一格就生效的功能件，每放一个给背包增加一行（9 格）只能存某一类物品的存储。本 feature 只做**数据与规则**（无界面、不注册扩展件物品），为 036（界面）与 037（物品、贴图、配方、语言键）打地基。

## 背景与已确认的决策

已有的功能件（标签管理器 018、垃圾桶 021、自动拾取 024）放进工具区（左、右、下三个功能区）才生效。分类扩展是同一类功能件，放进功能区的任一格，为所在的背包增加一行只能存某类物品的存储。

已确认的决策（来自用户，不重新讨论）：

1. **名字**：统称"分类扩展"，物品将来叫"食物扩展""工具扩展""矿物扩展"等（037 才做物品）。
2. **一行 = 9 格**，与档位无关。
3. **10 个类别**：食物、工具、武器、盔甲、矿物、农作物、木材、药水、红石、唱片。
4. **类别的判定用我们自己的物品标签** `mcfloatingbackpack:extension/<类别>`（整合包可用数据包扩充）：里面并入原版与 `c:` 标签和显式物品；食物另加"物品有 `food` 数据组件"。已核对的并入关系（读本机 1.21.1 与 NeoForge 21.1.251 的数据）：

   | 类别 | 并入 |
   |---|---|
   | 食物 | `food` 组件 ∪ `#c:foods` |
   | 工具 | `#minecraft:pickaxes`、`axes`、`shovels`、`hoes`；`#c:tools/shear`、`fishing_rod`、`brush`、`igniter`、`wrench`（`#c:tools/mining_tool` 只含镐） |
   | 武器 | `#minecraft:swords`、`#minecraft:arrows`；`#c:tools/melee_weapon`、`ranged_weapon`、`bow`、`crossbow`、`mace`、`shield` |
   | 盔甲 | `#c:armors` |
   | 矿物 | `#c:ores`（矿石方块）、`#c:raw_materials`、`ingots`、`nuggets`、`gems`、`dusts`、`#minecraft:coals` |
   | 农作物 | `#c:crops`、`#c:seeds`、`#minecraft:saplings` |
   | 木材 | `#minecraft:logs`、`planks`、`#c:stripped_logs`、`stripped_woods`、`rods/wooden`、`#minecraft:bamboo_blocks` |
   | 药水 | `#c:potions`（或有 `potion_contents` 组件） |
   | 红石 | `#c:dusts/redstone`、`#c:storage_blocks/redstone` 加我们自己列的元件（中继器、比较器、活塞、粘性活塞、观察者、拉杆、漏斗、投掷器、发射器、红石灯、红石火把、阳光传感器、目标方块等，清单保持现状） |
   | 唱片 | `#c:music_discs` |

   **物品是否属于某类别只在"放入"时检查**：以后标签变了，已经在行里的物品绝不丢弃，只是不能再放进去。一个物品属于多个类别时，放入时按行的顺序取**第一个有空位的匹配行**。
5. **排布**（036 做界面）：合法尺寸（017）仍按**档位基础容量**算，扩展行接在主网格后面、同一个滚动区里。所以本 feature 里"主区域的格子编号"= 档位容量的格子 + 各**可见**扩展行的格子（按行的顺序）；点击、拖拽、聚拢、转移等现有逻辑只需在"这一格能不能放这个物品"上加规则。
6. **逻辑行模型**：背包里有一个有序的"逻辑行列表"，每行有类别、9 格、是否可见。**放置一个扩展件 = 增加一个逻辑行；拿走一个 = 删掉一个对应行，行里的物品数据不丢、只是看不见（隐藏），后面的行往前提；再放回 = 当作新放置，放到所有可见行的最后面。**
   - 拿走类别 X 的扩展件时：该类别的可见行里**优先删一个空行**（空行直接删除，不产生隐藏行）；没有空行才隐藏最后一行（连同物品）。
   - 放置类别 X 的扩展件时：该类别有隐藏行就把**最早隐藏的一行**恢复成可见，放到所有可见行的最后面；没有才新建空行。
   - **光标上拿着的扩展件仍算"放着的"**（面板光标是背包数据的一部分），只有它真正离开背包才算拿走，这样在功能区之间挪动扩展件不会让行跳到最后。
   - "放着的"数量 = 三个功能区里该类别扩展件的个数 + 面板光标上的；每次保存和每次载入都重新核对（reconcile），数据永远不丢；别的途径让扩展件消失（创造模式、其它模组）也不出错。
7. **行总数上限 35**（可见 + 隐藏，所有档位统一，等于最大工具区格数）：达到后，一个会**新增**一行的扩展件放不进去，并提示（接回隐藏行不受限）。这样总格数最多仍是 108 + 35×9 = 423，不会因隐藏数据无限增长而撑爆网络包。
8. **看不见的物品**：隐藏行里的物品不可操作；背包要能回答"有没有隐藏物品、按类别各有多少件"（给 036 的黄点与悬停提示用）。
9. **转移与聚拢**：快速转移与自动拾取的目标顺序是"该物品匹配的**可见**扩展行（按行的顺序）→ 主区域"，每一段里仍然是"先并进已有的没满的栈，再放空格"。**双击聚拢**（原版 PICKUP_ALL：把面板里所有同种物品收进光标，先没满的、再满的）的范围是所有可操作的格子（主区域 + 可见扩展行），隐藏行不参与；倾倒垃圾、选区、Ctrl 转移对可见扩展行与主区域一视同仁。
10. **工具区放置规则**：扩展件允许放多个相同的（现有的"每区最多一个"限制只针对垃圾桶、标签管理器、自动拾取）；扩展件最大堆叠必须是 1（037 注册物品时保证，本 feature 的规则也要防御性地处理 count>1）。
11. **与标签管理器（018）联动**（用户 2026-11-10 提出，已确认）：类别的判定有**两个来源，满足任一个就算匹配**——(a) 上面的数据标签与 `food`/`potion_contents` 组件；(b) **这只背包的标签册里，这个物品带有该类别对应的标签 id**。这样玩家遇到没有被任何标签收录的模组物品（如"农夫乐事"的食物、作物），可以用标签管理器手动打上 `food`、`crop` 等标签，它们就能放进对应的扩展行。同样**只在放入时检查**：事后删掉标签，行里已有的物品不会被收走。标签册每只背包各一份（018 的既有决策不变）。
    类别与标签 id 的对应（**沿用现有预设 id，不改名**，改名会让旧存档里的标签失效）：

    | 类别 | 标签 id | 预设状态 |
    |---|---|---|
    | 食物 / 工具 / 武器 / 盔甲 / 矿物 / 木材 / 红石 | `food` `tool` `weapon` `armor` `ore` `wood` `redstone` | 已有 |
    | 农作物 | `crop` | **新增预设** |
    | 药水 | `potion` | **新增预设** |
    | 唱片 | `disc` | **新增预设** |

    农作物用新的 `crop`，**不复用**现有的 `plant`（植物范围比农作物大，含花、草、树苗；`plant` 保留，不连任何行）。预设从 10 个变成 13 个，需要新增 3 个预设 id 与中英文语言键各 3 行。

由我按已有惯例设计的部分（可在 plan 阶段微调）：

- **"扩展件解析器"**：一个接口回答"这个物品栈是不是扩展件、属于哪个类别"。035 里**没有任何扩展件物品**（037 才注册），默认解析器认不出任何物品，所以 035 完成后玩家可见行为与现在基本一致（唯一的可见变化：标签管理器的预设下拉里多了 `crop`、`potion`、`disc` 三项）；单元测试用假解析器。
- 行的内部顺序就是"创建/接回的先后"，同一类别的行不要求挨着。
- 空行（可见、没有任何物品）可以存在（放置扩展件时新建的就是空行）；隐藏行一定非空（空行隐藏时直接删除）。
- 请求指向隐藏行或不存在的格子 = 越界，按现状拒绝、零变化。
- 同步前先量编码后的大小，超过阈值（沿用快照预览的 900,000 字节）就拒发并记日志，不能让一个超大背包把客户端断线。

## Out of Scope（本阶段不做）

- 界面：排布、底色、分隔线、锁定/隐藏的提示、标题栏黄点 → 036。
- 10 个扩展件物品、贴图、配方、语言键、物品的堆叠上限 → 037。
- 背包搜索与整理（含 `hidden` 搜索条件）→ 之后单独做。
- 配置项、命令、新网络包（只改现有包的上限与新增字段）。

## 已查证的事实（读本仓库源码与本机游戏数据；规格要尊重）

- 主列表长度就是档位容量：`BackpackInventory.capacityOf(stack)` 取档位的容量，`BackpackContents.fit(...)` 把主列表补齐/裁到容量；档位容量在升级配方、快照恢复（按容量判断档位）、`BackpackGate` 里都被用到。
- 工具区容量由档位基础容量决定：左右 = 默认行数、下 = 默认列数 + 2；工具区三个列表各自最多 64 格。每个扩展件占一个工具格，所以扩展件数 ≤ 工具区总格数（皮革 19 … 下界合金 35）。
- `BACKPACK_CONTENTS` 是 `networkSynchronized` 的数据组件：每次原版同步一只背包栈都会带上全部内容。`BackpackContents.STREAM_CODEC` 已经是 6 个字段的 `StreamCodec.composite`（它的上限）。
- 主列表上限 108 硬编码在多处：`BackpackInventory.MAX_SIZE`、`BackpackContents` 的两个编码、`BackpackSessionPayload` 与 `BackpackFullSyncPayload` 的列表编码、`QuickTransferRequest.MAX_BACKPACK_SLOTS`（快速转移、垃圾桶发送、光标手势的校验）、`BackpackClickPayload` 的格子范围。
- 标签（018/025）存在 `BackpackContents.tags`（`ItemTags`），**每只背包各一份、按物品注册 id 存**，每个物品最多 10 个、1～16 位小写 ASCII；服务端 `BackpackInventory.tags()` 与客户端 `ClientBackpackView.tags()` 都持有它。预设标签 `PresetTags` 现有 10 个（`stone wood food ore trash tool weapon armor plant redstone`），**预设只影响下拉列表**：手输 `food` 与选预设 `food` 存下来的内容完全一样。自动拾取黑名单（024）按同一批标签名判断，所以 `food` 既是类别标签也是黑名单可填的标签（既有行为，不是新问题）。
- 面板的合法尺寸（017）要求列数整除"主格子数"；它由客户端的 `PanelShape.Counts` 算出，必须仍按基础容量算。
- 双击聚拢（013）是原版的 `PICKUP_ALL`：收集面板里所有同种栈到光标，先没满的、再满的，凑满一组为止。
- 现有的功能件限制在 `ToolAreaRules`：右区最多 1 个垃圾桶、下区最多 1 个标签管理器、左区最多 1 个自动拾取；别的物品随便放。
- 本机 1.21.1 / NeoForge 21.1.251 里不存在 `#minecraft:food`、`is_meat`、`is_tool`、`ingots`、`is_armor` 等标签，上面的并入关系已经用实际存在的标签替换。

## 尚未验证（plan 阶段先查证；验证前不得声称已满足）

- "主区域大小 = 档位容量"的所有假设：`BackpackInventory.size()`/`handler(MAIN)`、`BackpackContents.fit/normalize`、`ToolAreaCapacity`、客户端 `ClientBackpackView.slotCount()` 与布局的 `PanelShape.Counts`、`PanelSelection`、拖拽/聚拢/转移的目标范围；哪些调用点要改、哪些不用改。
- `BackpackContents` 的编码：磁盘编码加字段的兼容写法；网络编码怎样手写或折叠字段；最坏情况的大小估算（423 格 + 工具区 + 光标）与保护阈值。
- 统一上限常量需要改的全部位置（`MAX_SIZE`、`MAX_BACKPACK_SLOTS`、`MAX_TOOL_SLOTS` 与所有 `list(`）。
- reconcile 的触发点（`BackpackRef.saveInventory`、`BackpackInventory.fromContents`/`fromItem`）；光标上的扩展件怎样被识别；升级配方、快照恢复、创造模式 `/give` 的背包经过 reconcile 是否安全。
- 一个物品栏可能属于多个类别：放入时"第一个有空位的匹配行"与"先并进已有的栈"怎样组合；`QuickTransferLogic.moveInto` 能否复用。
- 标签册作为判定的第二个来源：判定接口怎样同时拿到「物品栈」与「这只背包的标签册」；`ItemTags` 按物品注册 id 查询的接口；服务端放入规则、快速转移、自动拾取各调用点能否拿到同一只背包的标签册；新增预设对 018/025 现有测试（预设数量、语言键检查）的影响。
- 物品标签在服务端与客户端的可用时机；`required: false` 引用的标签不存在时是否安全；数据文件的测试怎么写（只有 JUnit，没有 JSON 库，沿用文本检查）。

## User Scenarios & Testing *(mandatory)*

035 没有界面也没有扩展件物品，所以下面的场景是**规则层面**的：用假的扩展件解析器做单元测试来验证，游戏内验证的是"现有功能不回归"（见 User Story 5）。

### User Story 1 - 逻辑行随扩展件增减 (Priority: P1)

**Independent Test**: 用假解析器给一只背包"放入/拿走"若干类别的扩展件，每次核对后检查行列表与物品。

**Acceptance Scenarios**:

1. **Given** 没有任何行，**When** 放着 1 个食物扩展，**Then** 有 1 个可见的、空的食物行。
2. **Given** 有食物行，**When** 再放着 1 个工具扩展，**Then** 工具行排在食物行后面。
3. **Given** 食物行里有物品，**When** 拿走食物扩展且该类别没有空行，**Then** 该行变成隐藏行，物品还在；可见行里不再有它。
4. **Given** 两个食物行，第 1 行有物品、第 2 行是空的，**When** 拿走一个食物扩展，**Then** 删掉**空行**（第 2 行），第 1 行仍可见，没有产生隐藏行。
5. **Given** 有一个隐藏的食物行，**When** 再放着 1 个食物扩展，**Then** 把它恢复成可见，放到所有可见行的最后面，里面的物品回来；没有新建行。
6. **Given** 有两个隐藏的食物行，**When** 放着 1 个食物扩展，**Then** 恢复**最早隐藏**的那一行。
7. **Given** 面板光标上拿着一个食物扩展（工具区里没有），**Then** 仍算放着，行不变；光标上的扩展件被放进另一个工具格，行不变；光标上的扩展件离开背包后才算拿走。
8. **Given** 行总数（可见 + 隐藏）已经是 35，**When** 放着的扩展件会**新增**一行，**Then** 这个扩展件放不进去并给出提示；会接回隐藏行的放置不受限。
9. **Given** 别的途径让扩展件突然少了几个（创造模式、其它模组），**Then** reconcile 之后行列表仍符合规则，**没有任何物品丢失**。

### User Story 2 - 扩展行只收匹配的物品 (Priority: P1)

**Independent Test**: 往扩展行的格子放各种物品，核对哪些被接受。

**Acceptance Scenarios**:

1. **Given** 食物行，**When** 往里放面包，**Then** 放得进去；放圆石被拒绝，零变化。
2. **Given** 往主区域放任何物品，**Then** 照旧放得进去。
3. **Given** 行里已有的物品，之后标签变了不再匹配，**Then** 物品仍在、能被取出，只是不能再放进去。
4. **Given** 一个物品同时匹配两个类别（三叉戟：工具/武器；金苹果：食物），**When** 放入，**Then** 进第一个**有空位**的匹配行（按行的顺序）。
5. **Given** 隐藏行里的格子，**Then** 一切操作都被当作越界拒绝，零变化。
6. **Given** 请求里的格子编号超出"档位容量 + 可见行格子数"，**Then** 拒绝，零变化。
7. **Given** 一个没有被任何数据标签收录的模组食物，这只背包的标签册里它带有 `food` 标签，**When** 往食物行放它，**Then** 放得进去；没有 `food` 标签则被拒绝。
8. **Given** 一个物品的标签是 `crop`，**Then** 它能进农作物行，但进不了食物行（除非数据标签或另有 `food` 标签使它匹配）。
9. **Given** 行里有靠手动标签放入的物品，**When** 之后在标签管理器里删掉这个标签，**Then** 物品仍在、能被取出，只是同类物品不再能放进去。
10. **Given** 两只背包，其中一只给某物品打了 `food` 标签，**Then** 另一只背包的食物行仍不接受它（标签册每只背包各一份）。
11. **Given** 一个物品同时被数据标签和手动标签命中同一类别，**Then** 与只被一个命中没有区别（"或"关系，不重复）。

---

### User Story 3 - 转移、聚拢、自动拾取的目标顺序 (Priority: P1)

**Independent Test**: 用假背包验证快速转移、自动拾取、双击聚拢选的格子。

**Acceptance Scenarios**:

1. **Given** 有食物行和主区域，**When** 快速转移一组面包，**Then** 先并进食物行里已有的没满的面包栈，再放食物行的空格，放不下的才进主区域。
2. **Given** 没有匹配的行，**Then** 与现状完全一样（只进主区域）。
3. **Given** 自动拾取，**Then** 与快速转移同样的目标顺序。
4. **Given** 双击聚拢某种物品，**Then** 收集范围是主区域和所有可见扩展行里的同种物品；隐藏行里的不参与。
5. **Given** 倾倒垃圾、选区、Ctrl 转移，**Then** 对可见扩展行与主区域一视同仁；隐藏行里的物品不会被动。
6. **Given** 匹配的可见行都满了，**Then** 物品进主区域；主区域也满了则按现状放不下。

### User Story 4 - 数据永远不丢，限制可控 (Priority: P1)

**Independent Test**: 旧背包载入、往返编码、超大背包的同步保护。

**Acceptance Scenarios**:

1. **Given** 一只旧版本保存的背包（没有行列表），**When** 载入，**Then** 一切照常，物品一个不少。
2. **Given** 一只带行列表的背包，**When** 保存再载入、网络往返，**Then** 行列表与物品完全一致。
3. **Given** 背包最大配置（下界合金、35 个扩展件、每格都是带数据的物品），**Then** 总格数不超过 108 + 35×9 = 423；同步前先量编码后的大小，超过阈值就拒发并记日志，不让客户端断线。
4. **Given** 升级背包（皮革 → 铁等），**Then** 全部内容（含行列表与隐藏行）保留。
5. **Given** 快照（030）的恢复，**Then** 仍按档位容量判断档位，行列表随内容一起恢复。
6. **Given** 看不见的物品，**Then** 背包能回答"有没有、按类别各有多少件"。

### User Story 5 - 现有功能不回归 (Priority: P1)

**Independent Test**: 游戏里照常使用背包。

**Acceptance Scenarios**:

1. **Given** 035 完成后（没有扩展件物品），**Then** 面板的所有功能（放入、拿出、拖拽、聚拢、Ctrl 快速转移、选区、标签管理器、垃圾桶、自动拾取、升级、编号、快照与 031 界面）与 035 之前行为一致。
2. **Given** 旧世界里的背包，**Then** 照常载入。
3. **Given** 协议版本升级，**Then** 新客户端与新服务器正常连接。

### Edge Cases

- 工具区里的扩展件数比 35 还多（旧数据或创造模式）：行总数仍受 35 限制，多出的扩展件当作"没有产生行"，不丢物品。
- 一个扩展件的 count 大于 1：按 count 个计数还是按 1 个计数——防御性地按**1 个**计，并记日志。
- 面板光标上的扩展件随面板关闭回到物品栏：reconcile 之后算拿走。
- 同一次保存里既拿走又放入不同类别：先按"放着的数量"整体核对，结果与逐个操作一致。
- 手动标签与自动拾取黑名单共用名字（`food` 同时是类别标签和黑名单标签）：既有行为，035 不改；文档里说明。
- 玩家手输的自定义标签恰好与类别 id 同名（如 `ore`）：与预设 `ore` 完全等价，当作该类别的手动标签。
- 类别标签被整合包清空：该类别的扩展行仍存在，只是什么都放不进；里面已有的物品保留。
- 隐藏行里的物品被其它途径引用（比如快照预览、选区）：一律不可操作。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 提供 10 个类别（食物、工具、武器、盔甲、矿物、农作物、木材、药水、红石、唱片），每个类别对应一份物品标签 `mcfloatingbackpack:extension/<类别>`（数据文件，`replace: false`，引用 `#c:` 与 `#minecraft:` 标签时用 `required: false`）；食物另加"物品有 `food` 组件"，药水另加"有 `potion_contents` 组件"。
- **FR-002**: 提供判定：一个物品栏是否属于某类别；一个物品在给定的行列表里该进哪一行（第一个有空位的匹配可见行）。物品是否属于类别**只在放入时检查**，已在行里的物品绝不因标签变化被丢弃。
- **FR-003**: 背包保存一个**有序的逻辑行列表**：每行有类别、9 格、是否可见；隐藏行一定非空，空行在隐藏时直接删除。
- **FR-004**: reconcile 规则：每个类别的可见行数 = 放着的该类别扩展件数（三个功能区 + 面板光标）；放置按"恢复最早隐藏的行，放到可见行最后；没有才新建空行"；拿走按"优先删一个空行；没有空行才隐藏最后一行"；行总数（可见 + 隐藏）不超过 35；**数据永远不丢**。
- **FR-005**: reconcile 在每次保存与每次载入时执行；结果与操作的先后无关。
- **FR-006**: "主区域的格子编号" = 档位容量的格子 + 各可见扩展行的格子（按行的顺序）；隐藏行不在编号范围内。
- **FR-007**: 往扩展行的格子放物品时检查"属于该行的类别"，不合格拒绝、零变化；往主区域放任何物品照旧；指向隐藏行或超出范围的请求按越界拒绝、零变化。
- **FR-008**: 快速转移、自动拾取的目标顺序：匹配的可见扩展行（按行的顺序）→ 主区域；每一段里"先并进已有的没满的栈，再放空格"；没有匹配行时与现状一致。
- **FR-009**: 双击聚拢的范围是所有可操作的格子（主区域 + 可见扩展行）；倾倒垃圾、选区、Ctrl 转移、光标放入/拿起/拖拽对可见扩展行与主区域一视同仁；隐藏行里的物品不可操作。
- **FR-010**: 工具区允许放多个相同的扩展件；扩展件最大堆叠 1（037 保证），规则对 count>1 防御性地按 1 个计并记日志。
- **FR-011**: 一个会**新增**行的扩展件在行总数已达 35 时放不进去并给出提示；接回隐藏行不受限。
- **FR-012**: `BackpackContents` 的磁盘编码增加行列表（`optionalFieldOf`），旧背包照常载入；网络编码包含行列表（手写编码或折叠子记录）；背包能回答"有没有隐藏物品、按类别各有多少件"。
- **FR-013**: "主区域最多格子数"统一成一个常量 423（= 108 + 35×9），档位容量最多仍是 108；所有写死 108 的编码与校验（主列表编码、会话/整份同步包、快速转移/垃圾桶/光标手势的校验、点击的格子范围）改用它；协议版本升级。
- **FR-014**: 同步前量编码后的大小，超过阈值（900,000 字节）就拒发并记日志，客户端不断线。
- **FR-015**: 档位容量（`capacityOf`）、升级、快照恢复判断档位、编号、标签数据等现有功能**不受影响**；升级保留包括行列表与隐藏行在内的全部内容。
- **FR-016**: 提供"扩展件解析器"接口：判断一个物品栈是不是扩展件、属于哪个类别；默认解析器认不出任何物品；035 不注册任何扩展件物品，不新增贴图、配方、设置项、命令、新网络包；唯一新增的语言键是 FR-019 的 3 个预设标签名。
- **FR-017**: 行列表、reconcile、目标顺序、上限、判定是**不依赖 Minecraft 类的纯逻辑**，有单元测试（沿用 032 的泛型 + 假类型做法）。
- **FR-018**: 类别判定有两个来源，满足**任一个**即匹配：(a) 数据标签与 `food`/`potion_contents` 组件（FR-001）；(b) 这只背包的标签册里，该物品带有类别对应的标签 id（食物 `food`、工具 `tool`、武器 `weapon`、盔甲 `armor`、矿物 `ore`、农作物 `crop`、木材 `wood`、药水 `potion`、红石 `redstone`、唱片 `disc`）。判定仍是纯逻辑，标签册以"某物品带有哪些标签"的函数传入；只在放入时检查。
- **FR-019**: 预设标签新增 `crop`、`potion`、`disc`（现有 10 个预设的 id 与顺序不变，新增的排在后面），并补中英文语言键；其余标签规则（每物品最多 10 个、小写、1～16 位）不变；`plant` 保留且不对应任何类别。

### Key Entities

- **类别（Category）**：10 个之一；对应一份物品标签。
- **逻辑行（Row）**：类别 + 9 个物品栈 + 是否可见。
- **行列表（RowList）**：有序的逻辑行；背包数据的一部分。
- **标签册（ItemTags，018）**：每只背包一份，按物品注册 id 存标签；类别判定的第二个来源。
- **扩展件解析器（PackResolver）**：物品栈 → 类别（或不是扩展件）。
- **放着的数量（Placed）**：各类别在三个功能区加面板光标上的扩展件数。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 035 完成后，除标签预设下拉多出 3 项外，玩家可见行为与 035 之前**完全一致**：现有所有功能的验证场景结果相同。
- **SC-002**: 行列表的所有规则（放置、拿走、接回、空行删除、光标上的算放着、行总数 35、数据不丢）由单元测试覆盖，全部通过。
- **SC-003**: 任意顺序的放置/拿走序列，reconcile 之后**物品总数不变**（单元测试里用随机序列验证）。
- **SC-004**: 旧背包 100% 照常载入；带行列表的背包往返（磁盘、网络）后完全一致。
- **SC-005**: 最大配置（423 格 + 工具区 + 光标）的编码大小有明确的上界估算，超过阈值时被拒发而不是断线。
- **SC-006**: 协议版本已升级；图集仍是 2048×1024；自动化测试全部通过。

## Assumptions

- 037 会注册 10 个扩展件物品并提供真正的解析器；035 的规则通过假解析器验证。
- 036 会按"主区域的格子编号"画出扩展行（接在主网格后面），并读取"隐藏物品"信息画黄点；035 提供所需的数据。
- 面板光标上的物品是背包数据的一部分（现状如此）。
- 物品标签会随数据包同步到客户端，036 的界面可以用同一判定做提示。
