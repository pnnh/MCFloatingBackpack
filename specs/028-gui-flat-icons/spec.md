# Feature Specification: 背包在 GUI 里用平面图标——解决快捷栏里的背包拖垮帧率

**Feature Branch**: `028-gui-flat-icons`

**Created**: 2026-11-09

**Status**: Draft

**Input**: User description: "快捷栏里放 8 只背包时帧率约 22 fps，移走后约 101 fps（同位置同视角）。原因是五档背包都是 1.6 万～2 万个面的 OBJ 模型，快捷栏每帧都要把它们全画一遍。让背包在 GUI 里用平面图标，手持、第三人称、背在背上仍用现在的 3D 模型。"

## 背景与已确认的决策

2026-11-08 的对照实验（记在 `docs/plan/perf-gui-model-cost.md`）：同一位置、同一视角，F3 开着，macOS / Apple M1 Pro / 2236×1458 / 渲染距离 12 / 开发环境无光影——快捷栏里有 8 只背包时约 **22～23 fps**，把背包全部移走后约 **101 fps**；集成服务端耗时两种情况都是 4～5 ms，所以瓶颈在客户端渲染。009 的性能粗测也记过同一个症状（打开物品栏稳定约 15 fps）。

原因（推断，未用性能分析器验证）：五档背包都是 OBJ 雕刻网格，每档 16,178～20,280 个面；原版物品渲染按面逐个提交，快捷栏的 9 格每帧都重画，8 只就是约 15 万个面/帧，全部由 CPU 提交。

已确认的决策（来自用户，不重新讨论）：

1. **修复方向**：让背包在 **GUI** 里使用平面图标，不再每帧画上万个面的网格（用户 2026-11-09 同意"可以先记录、之后处理"，并要求"依据任务复杂度决定是否开新 feature"）。
2. **原版第一优先**（宪法 2.2.0 原则 VII）：这是性能修复，不是对功能的限制；背包在所有游戏模式、所有界面里的表现一致。

由我按已有惯例设计的部分（不再逐条询问用户，可在 plan 阶段微调）：

- **哪些显示场景换成平面图标**：只换 **GUI**（快捷栏、物品栏、箱子、JEI、面板标题栏图标）。**GROUND（掉在地上的物品）不换**：用户 2026-11-09 验证帧率已达标后要求掉落物仍用 3D 模型（同时掉落很多时帧率会降，但正常游玩不太可能）。**FIXED 不换**：背在背上的渲染（`BackpackBackLayer`）用的就是 `ItemDisplayContext.FIXED`，展示框也用 FIXED；这两处一个只画一只、一个数量很少，保持 3D。手持（第一人称、第三人称）也保持 3D。
- **图标从现有的 3D 模型渲染出来**，保证与手持、背在背上的外形一致：用开发期脚本（`design/demo/tools/`，不随模组发布，与垃圾桶、标签管理器的做法一致）按原来 GUI 的视角把五档模型渲成透明背景的 32×32 图片。
- **图标大小 32×32**：在 16 个单位的格子里按 16 像素显示，细节比 16×16 多；图集增量约 5×32×32 像素，远小于预算（宪法 VI：共用方块图集不得超过 2048 像素宽或高，当前 2048×1024）。
- **模型文件的重组**：现有的每档物品模型（OBJ 加载器 + 各视角变换）原样改名为"3D 模型"，另有一个平面图标模型，两者由 NeoForge 自带的 `neoforge:separate_transforms` 加载器按显示场景选择。**3D 模型本身（OBJ、贴图、手持与背在背上的变换）一个字都不改。**

## Out of Scope（本阶段不做）

- 减面、重做或替换 3D 模型（手持、第三人称、背在背上仍用现在的网格）；每档面数上限（009 的 F002）。
- ESC 菜单掉帧（约 100 → 60 fps，原因不明）：单独排查，本 feature 只在修复后复测它是否还在。
- 改配方、改贴图的外观（五档背包的 512×512 皮肤贴图不变）、改其它物品的模型。
- 光影包下的表现；第三方模组界面（它们同样调用物品渲染，自然受益）。
- 展示框里的背包（FIXED，保持 3D）。

## 已查证的事实（读 NeoForge 21.1.251 与本仓库源码；规格要尊重，不要重新猜）

- 五档物品模型是 `neoforge:obj` 加载的 OBJ 网格：皮革 16,178、铁 20,280、金 19,401、钻石 20,227、下界合金 20,271 个面。
- `neoforge:separate_transforms`（`SeparateTransformsModel`）存在：`base` 是默认模型，`perspectives` 里按显示场景名（`gui`、`fixed`、`firstperson_righthand` 等）给出子模型；`applyTransform` 对命中的场景返回那个子模型，**渲染用的是子模型的面**，没有命中的场景用 `base`。顶层 `getTransforms()` 返回空，所以每个场景的变换要写在各自的子模型里。
- 背在背上的渲染 `BackpackBackLayer` 调 `renderStatic(..., ItemDisplayContext.FIXED, ...)`，依赖 3D 模型的 `fixed` 变换（缩放 1.1、旋转 180°）。所以 FIXED 必须留给 3D 模型。
- 垃圾桶、标签管理器、自动拾取的物品是 `item/generated` 平面模型，图标由 `design/demo/tools/make_*_icon.py` 生成；本仓库没有 numpy，只有 PIL。
- 图集度量脚本是 `design/demo/tools/check_atlas_budget.sh`（会启动客户端，先 `pgrep`）；当前结果 2048×1024。
- 面板标题栏的等级图标（008）是用物品渲染画的，GUI 场景，所以会自动用平面图标。

## 尚未验证（plan 阶段先查证；验证前不得声称已满足）

- 主因是否确实是 GUI 里的网格提交：同样的对照实验，换成平面图标后帧率应回升（验收标准见 SC-001）；如果回升很少，说明还有别的主因。
- `separate_transforms` 的 `base` 能否通过 `parent` 引用一个带 `neoforge:obj` 加载器的模型文件（读源码倾向可以，**没有在游戏里验证**）。
- 平面图标在快捷栏里的观感是否可接受（与原来 3D 立体感的差别）；JEI 里的显示。
- 背在背上、手持（第一、第三人称）的外观与变换是否**完全不变**。
- 图集增量与结果（预算 2048×1024）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 快捷栏里放很多只背包不再拖垮帧率 (Priority: P1)

玩家把多只背包放在快捷栏或物品栏里，帧率与没有背包时相近。

**Why this priority**: 这是本 feature 存在的原因。

**Independent Test**: 同一位置、同一视角、F3 打开：快捷栏里放 8 只背包，记录帧率；全部移走，再记录。两者差别应在几 fps 以内（SC-001）。

**Acceptance Scenarios**:

1. **Given** 快捷栏里 8 只背包，**When** 记录帧率，**Then** 与空快捷栏时相比下降不超过约 10%。
2. **Given** 物品栏里有很多只背包并打开物品栏界面，**Then** 帧率没有像 009 记录的那样掉到约 15 fps。
3. **Given** 面板标题栏的等级图标，**Then** 同样是平面图标，悬停仍显示等级名称。
4. **Given** 打开箱子或 JEI，**Then** 里面的背包也是平面图标。

---

### User Story 2 - 图标一眼能认出这是哪一档背包，外形与 3D 模型一致 (Priority: P1)

五档背包的平面图标各自可区分，外形、配色与对应的 3D 模型一致。

**Independent Test**: 五档背包并排放在快捷栏里，能一眼分出皮革、铁、金、钻石、下界合金；与手持时的模型对照，外形与配色一致。

**Acceptance Scenarios**:

1. **Given** 五档背包各一只，**Then** 图标互相可区分，边缘干净（透明背景、不糊、不带白边）。
2. **Given** 手持同一只背包（第一、第三人称），**Then** 3D 模型与图标的外形、配色一致。
3. **Given** 暗色背景和亮色背景（物品栏界面与世界），**Then** 图标都清晰可辨。

---

### User Story 3 - 手持、背在背上、展示框仍是现在的 3D 模型，一点不变 (Priority: P1)

只有 GUI 换了表现，其它场景（含掉落物）完全不变。

**Independent Test**: 手持（第一、第三人称）、背在背上、放进展示框，五档各看一遍，与改动前对照，外观与位置一致。

**Acceptance Scenarios**:

1. **Given** 手持一只背包（第一人称、第三人称，主手与副手），**Then** 与改动前一致。
2. **Given** 背包穿在胸甲位，**Then** 背在背上的外形与位置与改动前一致。
3. **Given** 放进展示框，**Then** 仍是 3D 模型。
4. **Given** 掉在地上的背包，**Then** 仍是 3D 模型，与改动前一致。

---

### User Story 4 - 不影响其它功能与资源预算 (Priority: P2)

**Independent Test**: 重跑 011～027 的验证项（点击、拖动、转移、标签、垃圾桶、自动拾取、编号显示、创造界面）结果与之前一致；图集度量仍是 2048×1024。

**Acceptance Scenarios**:

1. **Given** 改动之后，**When** 跑图集度量，**Then** 宽、高都不超过 2048，并记录改动前后的数值。
2. **Given** 标题栏的编号显示（026）与 3D 手持，**Then** 不受影响。

---

### Edge Cases

- **升级后的背包、带不同数据的背包**：图标只由物品种类（档位）决定，与内容、编号无关。
- **光影包**：本 feature 不保证；平面图标在光影下与其它物品一样处理。
- **资源包覆盖**：玩家用资源包替换背包的物品模型时，按资源包的内容显示（原版行为）。
- **图标的图集接缝**：32×32 的图标不得出现相邻贴图的边缘渗色（图集的 mip 级别与现有一致，图标四周留透明边）。
- **GUI 缩放很大或很小**：图标是 32×32 贴图缩放到格子大小，与其它物品相同。
- **JEI 中的"背包"配方**（026 的自家配方类型）：配方里的结果图标是平面图标。
- **ESC 菜单掉帧**：不属于本 feature，修复后复测并记录。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 五档背包在 **GUI**（快捷栏、物品栏、箱子、JEI、面板标题栏图标）场景里 MUST 使用平面图标，MUST NOT 再渲染 OBJ 网格。
- **FR-002**: 手持（第一、第三人称，主手与副手）、背在背上（`FIXED`）、展示框（`FIXED`）、掉落物（`GROUND`）MUST 继续使用现在的 3D 模型，外观与变换 MUST 与改动前**完全一致**。
- **FR-003**: 平面图标 MUST 由现有的 3D 模型渲染得到，外形、配色与它一致；五档 MUST 互相可区分；32×32，透明背景，边缘干净。
- **FR-004**: 生成图标的脚本 MUST 放在 `design/demo/tools/`（开发期工具，不随模组发布），MUST 可重复运行、输出确定。
- **FR-005**: 本 feature MUST NOT 修改 OBJ 模型、512×512 皮肤贴图、配方、手持与背在背上的变换；MUST NOT 改变背包的任何功能。
- **FR-006**: 本 feature MUST NOT 引入对任何游戏模式、界面或场景的功能限制，MUST NOT 新增设置项（宪法 2.2.0 原则 VII）。
- **FR-007**: 新增贴图 MUST 在改动前后各测一次共用方块图集，宽、高都 MUST NOT 超过 2048（宪法 VI），结果记入 DELIVERY；测不了 MUST 写"未度量"，不得写成通过。
- **FR-008**: 性能改善 MUST 用与 2026-11-08 相同的对照实验验证（同位置、同视角、快捷栏有 8 只背包 vs 空快捷栏），结果记入 DELIVERY；没有测量 MUST 写"未测量"。
- **FR-009**: 模型 JSON 的结构 MUST 有不依赖游戏的自动检查（五档的物品模型使用 `separate_transforms`，`perspectives` 只含 `gui`，不含 `ground`、`fixed` 与任何手持场景；图标文件存在、是 32×32 的 PNG、有透明像素）。

### Key Entities

- **3D 模型**：现有的 OBJ 物品模型，含手持、第三人称、`fixed` 等变换；改名为 `*_3d`，内容不变。
- **平面图标模型**：`item/generated` 的平面模型，贴图是渲染出的 32×32 图标。
- **物品模型（入口）**：每档一个 `separate_transforms` 模型：`base` 指向 3D 模型，`gui` 指向平面图标模型。
- **图标生成脚本**：从 OBJ 与皮肤贴图渲出五张图标的开发期工具。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 与 2026-11-08 相同的对照实验：快捷栏 8 只背包的帧率，与空快捷栏相比**下降不超过约 10%**（改动前是约 22 对 101，下降约 78%）。
- **SC-002**: 物品栏里放很多只背包并打开物品栏界面，帧率**不再掉到约 15 fps**（009 的记录）。
- **SC-003**: 手持（第一、第三人称，两只手）、背在背上、展示框五档各看一遍，与改动前对照**外观与位置一致**。
- **SC-004**: 五档图标并排放在快捷栏里**一眼可区分**，边缘干净，亮暗背景下都清晰。
- **SC-005**: 图集度量：改动前后的宽、高**都不超过 2048**，并记录两个数值。
- **SC-006**: 重跑 011～027 的验证项，结果与之前一致；026 的编号显示、027 的创造界面不受影响。
- **SC-007**: 模型 JSON 结构与图标文件的自动检查（FR-009）通过；全部既有测试通过。
- **SC-008**: 修复后复测 ESC 菜单的帧率并记录（本 feature 不要求它好转，只要求记录）。

## Assumptions

- **只换 GUI**：`FIXED` 留给背在背上与展示框，`GROUND` 留给掉落物（见"已确认的决策"）。
- **图标是 32×32 而不是 16×16**：保留细节；图集增量可以忽略。
- **图标的视角沿用原来的 GUI 视角**（旋转 `[30, 225, 0]`），所以快捷栏里的外观与改动前相近，只是不再是真正的立体渲染。
- **图标的光照**：渲染时用固定的柔和方向光，近似原来 GUI 里的侧光，不做更多。
- **依赖**：008（标题栏图标）、009/010（OBJ 模型与图集预算）、026（编号显示不受影响）、027（创造界面不受影响）；不依赖任何第三方模组。
- 本功能是纯玩家可见的显示变化，按宪法 V 必须在客户端会话里逐场景验证（尤其是帧率对照、五档外观、手持与背在背上不变）；Windows/Linux 本机无法验证。
