# 规划：联合背包（Combined Backpack）——一只"虚拟背包"联通身上所有背包（2026-11-24，第二版）

**状态**: 规划文档，**不是规格**（真正开工以 `specs/065-*`、`066-*` 为准）。第二版相对第一版（"统一背包"）的改动：改名；**分五档并按档位限定可连接的背包**；补"全部"标签里怎么看出是哪只背包、性能分析、唱片机处理、标题栏里的**纯显示**搜索与整理；配方方向；用户对四个待定项的回答已并入。

## 想要什么

- 一个新物品"联合背包"：**自己不存任何东西**，穿在身上（胸甲槽，或 061 的浮动背包专用槽位）时，起"接线盒"的作用，把身上的浮动背包联通成一个整体来存取。
- 按 **U** 打开它的专属界面：顶部标题栏（图标 + 标题），下面一行标签栏：**全部 / 背包 A / 背包 B / ……**；标签是"背包实例"，不是物品分类。
- "全部"标签：把所有成员背包的**主区域**（含分类扩展行）合在一个网格里存取；"背包 A"标签：那只背包的完整面板，**含左右区、底部功能区**。
- 成员 = 在物品栏（含快捷栏）、副手、各穿戴槽位里的浮动背包，**且档位不高于联合背包的档位**。放在箱子里、地上的不算。

## 已确认的决策（用户，2026-11-24）

1. **连接方式**：自动。身上的浮动背包自动成为成员，不逐只绑定；服务端每次现算成员表，联合背包物品上**没有任何数据**。
2. **打开方式**：B 不变（仍是 手 → 穿戴 → 物品栏 的顺序打开单只背包），另设 **U** 键打开联合界面（穿戴了联合背包才有效）。
3. **分期**：先做"单背包标签"（065），再做"全部"标签（066）。
4. **分五档**，与现有背包一致（皮革、铁、金、钻石、下界合金）：皮革联合背包只能连皮革背包；铁的能连铁和皮革；……下界合金的能连所有档位。**不是一档通吃**，否则它成了过晚期的道具。
5. **配方**：至少需要一只**同档位背包**，再加末影珍珠或末影之眼之类（契合"虚空传送/拾取"的意象，但不强制）；总难度至少是同档位背包的 2 倍。**没有背部模型**，只有物品贴图（它不是真实的背包）。
6. **放胸甲槽会顶掉胸甲**，和现有背包的查找逻辑一致，不另做处理。
7. **成员上限 16**，合适。超出的不连接，只取前 16 个。
8. **065 的标签栏先叠在现有标题栏上方**（多约两行高）；**2026-11-24 更新：用户判断联合标题栏作用不大，066 起取消它**（标签栏直接贴在面板上沿；"全部"里直接复用面板自己的标题栏上的搜索与整理）。原先"融合两层标题栏"的待办因此消失；若仍想把面板标题栏移到标签栏上方，另开 feature。

**关于名称**：同意"联合背包"比"统一背包"合适。"统一"听上去像"一只背包取代所有背包"，而现在的设定是：分档、只连不高于自己档位的背包、界面按背包分标签，是"把几只背包联起来用"。英文建议 **Combined Backpack**（备选 Linked Backpack，更强调"连接"）。**注册名一旦发布就不能改**（语言文件里的显示名可以随时改），所以名称要在 065 开工前定死：注册名暂定 `<档位>_combined_backpack`，例如 `leather_combined_backpack`，与 `leather_floating_backpack` 对应。现在还没注册任何东西，改名零成本。

## 可行性结论

**可行，且第一期风险小**。

| 部分 | 结论 | 理由 |
|---|---|---|
| 联合背包物品（五档）、穿戴 | 容易 | 复用 032/061 的 `WornSource` 体系：`BackpackSearch` 是泛型，`Probe.isBackpack` 只有一个，给联合背包另开一个查找实例，穿戴来源对象可以共用 |
| 成员表 | 容易 | 已有 `WornBackpacks.allWornPlayer`（061）；再加副手、物品栏 36 格，加档位过滤 |
| 单背包标签（重定向面板） | 中等偏易 | 服务端 26 个文件、30 处 `BackpackRef.resolve(player)`；面板类请求都靠它找背包，且点击包本来就带着"声称的引用"但服务端不采信。加一个**服务端会话目标**，面板类请求统一换成 `PanelTargets.resolve`，请求的线上格式基本不用动 |
| 标签栏 UI | 中等 | `PanelLayout` 是纯算术、有单元测试，加一个"顶部额外高度"参数即可 |
| "全部"标签 | **难，单独一期** | 要"成员号 + 格号"寻址：点击、拖动分摊、快速转移、滚动、同步都得认 |
| 显示用搜索与整理 | 中等 | 纯客户端，借 042 已有的"布局格 → 槽号"映射机制，见下 |
| 光标 | 要定规矩 | 现在**光标存在背包数据里**（`BackpackInventory.cursor`），见下"光标" |

## 设计

### 1. 物品与穿戴

- 五个物品 `<档位>_combined_backpack`：堆叠 1，**无数据组件**，不是 `FloatingBackpackItem`，不是容器；`Equipable` 胸甲槽（和背包一样，Shift+右键换到胸甲槽）。
- Curios / Accessories：只放进 061 的**浮动背包专用槽位**（物品标签加进那一个槽位，不加进 `back`、`charm`）。**无法阻止它被放在物品栏里**（不用 mixin 做不到"只能放某槽位"），所以语义是"放在别处不起作用"：按 U 时提示"需要穿戴联合背包"。
- **同时穿几个**：取**档位最高的那个**（同档位取查找顺序里靠前的）。这一条与背包的"第一只算数"不同：档位决定能连谁，穿着皮革的、专用槽里是下界合金的，应当按下界合金算。
- **没有背部模型**：`BackpackBackLayer` 只画背包，对联合背包什么都不画；只穿联合背包时背上什么也没有。物品图标用平面贴图（028 的经验：高面数模型会拖垮 GUI 帧率）。
- 064 的嵌套规则要认它：不能放进浮动背包，`canFitInsideContainerItems` 返回 false（它没有数据，不会数据爆炸，但放进去没有意义）。
- **配方（草案，数值开 065 时敲定）**：
  - 合成：同档位背包（**必须是空的**）居中，四角末影珍珠，四边该档位材料（皮革 / 铁锭 / 金锭 / 钻石 / 下界合金锭）。大致是同档位背包的 2 倍难度。
  - **必须拒绝非空背包**：被当作原料消耗的背包里若有东西，会连同物品一起消失。配方类型本来就是自定义的（`backpack_crafting`、`backpack_upgrade` 都是），在 `matches` 里检查背包整体为空即可；这条要有单测。
  - 升档：沿用现有背包升级的锻造台配方（模板 + 材料块），底料换成低一档的联合背包；没有数据，所以升级就是换物品。这样玩家升级背包时可以顺手升级联合背包。
  - 末影之眼是否用在高档位上（比如钻石、下界合金档把末影珍珠换成末影之眼）：留给规格阶段，按"难度至少 2 倍"核对。

### 2. 成员表（纯逻辑，可单测）

`CombinedMembers.of(player, 联合背包档位)`，顺序，每项是 `(BackpackRef, 身份, 档位, 位置说明)`：

1. 穿戴槽位里的所有浮动背包（`WornSource` 的顺序，**不只第一只**）。
2. 副手。
3. 物品栏 0～35 下标升序（快捷栏 0～8 先于主物品栏；主手背包就是被选中的那一格，成员表按物品栏下标列，不单独列主手，客户端服务端都按下标去重）。

排除，各自计数后在界面提示：

- 档位高于联合背包的（"n 只背包档位过高未连接"）；
- **040 保护中的背包**（存档比本版本新，不能重写）（"n 只背包因版本过新未连接"）；
- 满 16 只之后的（取**前 16**，见"性能"）。

**复制出来的背包共享身份**（030）：成员表允许同身份出现两次，寻址靠引用，身份只做"没被换掉"的校验。

### 3. 服务端会话目标（第一期的核心）

- 现有 `BackpackGate` 的 `OpenSessions` 已记着"这个玩家的面板开在哪只背包的身份上"，并有过期保护（`acquireForPanel`）。扩展成：会话里多一个**目标引用**（成员的 `BackpackRef` + 身份）。
- 新增 `PanelTargets.resolve(player)`：有联合会话且目标仍在成员表里、身份仍对得上 → 返回目标；否则退回 `BackpackRef.resolve`。面板请求处理器统一换成它；加一个接线测试，像 064 的 `NestingWiringTest` 那样断言每个面板处理器都经过它，防止以后新增入口漏掉。
- 切标签：新包 C→S `CombinedSelectPayload(成员下标, 身份)`。服务端校验后改会话目标，随后发一次现有的整包同步（客户端不用学新东西）。
- **顺序保证**：同一连接上的包按序处理，切标签之前发的点击在切换前处理，之后发的在切换后处理。唯一的缝是客户端切了标签、还没收到新整包前画面还是旧的。解决：客户端切标签后进入"加载中"，**收到整包前不发任何面板请求**；服务端对带"声称引用"的点击包，引用与目标不一致时拒绝并重同步（不再像现在那样悄悄改用解析结果）。
- **跟随身份**：目标背包被挪了位置，按身份在新表里找回它（唯一匹配就悄悄改目标；找不到或有多个相同身份就回到第一个标签）。
- 成员的身份：从未打开过的背包没有身份，选标签时 `acquire` 会给它一个（会改写物品栏里的那个栈）；成员表本身只读，不改任何背包。

### 4. 光标

现在面板光标是背包数据的一部分，打开容器界面时则改用菜单的携带物（`PanelCursor`）。

- **第一期**（单背包标签）：光标仍是**那只背包自己的光标**，行为不变；**光标非空时不允许切标签**（动作栏提示"先放下手里的物品"）。
- **第二期**（"全部"标签）：光标需要跨背包。做成**服务端会话里的内存光标**，不写进任何物品数据（联合背包保持无数据，不动 `DataRevision`，没有快照/保护问题）；关闭联合界面、切标签、下线时**冲洗**：先按成员顺序塞回成员背包，塞不下进物品栏，再塞不下就像原版那样丢在脚下。代价：服务器在持有光标时崩溃，光标里的东西会丢（和原版菜单携带物一致）。

### 5. 界面

```
┌────────────────────────────────────┐
│ [联合图标] 联合背包（档位）    🔍 ⇅  │  标题栏（新；搜索与整理在 066 加，见 §7）
├────────────────────────────────────┤
│ 全部 │ ■A3F2 │ ■K7Q1 │ ■9ZB0 │ ◂ ▸ │  标签栏（新）：色块 + 编号，悬停显示位置
├────────────────────────────────────┤
│ 现有面板：自己的标题栏（编号、搜索、整理、…）
│ 左区 │ 主区域                  │ 右区 │
│ 底部功能区                          │
└────────────────────────────────────┘
```

- 第一期：联合标题栏 + 标签栏叠在**现有面板上方**，现有面板标题栏保留（它有搜索、整理、标签、快照等按钮），所以高度多约两行；以后再合并。
- 标签文字：背包的**铁砧改名**优先，否则"档位图标 + 4 位编号"（026 已有）；悬停提示位置（"胸甲 / Curios 专用槽 / 副手 / 物品栏第 5 格"）、容量。"背包 A/B/C"这种字母不用做，编号更稳定（位置会变，编号跟着背包）。
- `PanelLayout` 加 `topExtra`：命中检测、滚动、`FloatingPanelRenderer`、JEI/EMI 排除区（`compat/jei`）都按它走；要核对排除区矩形把标签栏算进去，也要核对 `FloatingPanelState` 的位置钳制把它算进去。
- 键位：`FloatingBackpackKeys` 加 U，`HostKeyRouter`（019 宿主界面）要认它。
- 客户端 `ClientBackpackView` 是**单例**（101 处引用，26 个文件）。第一期**不动它**：它始终镜像"当前标签的那一只"，新增的只是一个 `ClientCombinedState`（成员表、当前标签、加载中标志、每个成员的颜色）。

### 6. "全部"标签（第二期，另开规格）

- **虚拟网格**：成员主区域依次排列（成员下标升序），**各背包的格子首尾相连（不再每只从新的一行开始）**（整理排序前的默认视图）；含各自的分类扩展行，格子的限制照旧（`canPlaceMain`，灰格规则 `GreyCellRules` 沿用）。
- **寻址**：全局格号 → (成员下标, 成员内格号)，前缀和表，纯逻辑可测；`PanelLayout.mainMap` 已经是"布局格 → 槽号"的映射机制，聚合版同理。
- **请求**：把 `BackpackClickPayload` 的处理体拆成 `applyClick(player, ref, …)`；"全部"里的点击发新包 `CombinedClickPayload(成员下标, 身份, 格号, …)`，服务端定位成员后调同一个函数；拖动分摊、快速转移同理。**每个成员各自 `saveInventory`**，只保存真正改动的。
- **放入"全部"的目标规则（初版）**：按成员顺序试，每只走自己的 `mainTargetOrder`（分类行优先、再通用格）；"已有同种物品的背包优先"以后再做。
- **同步量**：clientbound 自定义包上限约 1 MiB，不能把所有成员塞进一个包。每个成员一个"只含主区域"的同步包（大小不超过现在的整包），按序发；增量更新包要带成员下标。
- 工具区、功能区、垃圾桶、标签管理在"全部"里**不提供**，要用请点具体背包标签。

#### 怎么知道操作的是哪只背包（回答用户的问题）

可选的做法：格子底色、边框、悬停提示、分区标题行。**推荐组合：格子底色淡染 + 悬停提示 + 标签同色，三项都便宜**：

| 做法 | 实现成本 | 作用 | 取舍 |
|---|---|---|---|
| **格子底色淡染成该背包的颜色，标签栏上该背包的标签用同一个颜色** | 低：每个可见格多一次半透明填充，颜色由成员下标查一张 16 色表（客户端纯显示）；染色画在高亮与灰格之下 | 一眼看出归属；**整理排序后各背包的物品混在一起时，这是唯一能直观区分的办法** | 颜色要选得相互区分、与灰格（分类行限制）和搜索高亮的颜色不冲突；只靠颜色对色盲不友好，所以必须配悬停 |
| **悬停提示里多一行"来自 ■A3F2（物品栏第 5 格）"** | 低：提示里追加一行 | 精确，无歧义，不靠颜色 | 要悬停才能看到 |
| **悬停某格时，对应的标签高亮** | 低：标签栏读"悬停成员" | 不用读文字就能知道是哪只 | 无 |
| 边框 | 中：每格画边框，和已有的物品/选中边框叠在一起容易乱 | 比底色清晰 | 容易与选中框混；**不推荐** |
| 分区标题行 | 中：占整行，虚拟网格要为它留位置，排序后失效 | 默认视图里很清楚 | 排序（见 §7）会打乱分区，**不推荐**；默认视图靠"每只从新的一行开始 + 底色"已经够区分 |

颜色取法：**按成员在标签栏里的位置**查表（第 1 个是色 1……），16 色正好对应 16 个成员；背包增减时颜色会顺延，标签上的色块始终与格子一致，不会错。以后想让颜色跟着背包身份走再改（需要成员间避免撞色，复杂，不做）。

### 7. 联合标题栏里的搜索与整理（"全部"标签；纯显示，不动数据）

理解：联合标题栏（新增的那一栏）里放搜索框和整理按钮，作用于**"全部"标签的显示**；数据始终存在各自背包里。"单个背包标签"里照旧用它自己标题栏里已有的搜索与（真正的）整理，不重复做。

- **搜索**：042 的搜索本来就是**纯显示**（实时过滤主区域并高亮命中），语法 `@模组` `#标签` `/hidden` 照用；联合版只是把过滤对象换成聚合网格。命中的格子按位置压紧显示，点击时仍发真实的 (成员, 格号)。
- **显示整理**：点整理图标时，**客户端**把所有成员的主区域格子按 047 的排序规则（注册名顺序、分类行优先）排出一张**排列表**——一个"显示位置 → (成员, 格号)"的置换，包含全部格子：非空格子按序在前，空格子在后。显示按这张表画，点击按表翻译回真实位置发给服务端。
  - 是"缓存"：排列表只在点整理、成员表变化（增删背包）时重算；平时数据变化（放进、取出）**不**自动重排，否则物品会在光标下乱跳。放进去的物品留在它所在的显示位置，直到下次点整理。
  - **不合并堆叠、不挪动数据**：跨背包合并要真的搬东西，那不是显示效果。想真整理，到具体背包标签里用它自己的整理。
  - 不改服务端：没有新包，不涉及快照、保护、嵌套检查。
  - 因为整理后各背包的物品交错在一起，§6 的底色染色就是必需的，不是可选项。
  - 切走"全部"再回来：排列表保留到关闭联合界面为止；下次打开按默认视图（各背包的格子首尾相连（不再每只从新的一行开始））。
- 单背包标签里也能用联合标题栏的搜索吗：本期不做，那里已有自己的。

## 性能分析（回答用户的问题）

**结论：实时算成员表不会有性能问题**，真正的开销不在这里。下面的量级是估算，没有实测。

| 开销 | 量级 | 说明 |
|---|---|---|
| 扫一遍成员 | 物品栏 36 + 副手 + 若干穿戴槽，约 40～50 个物品栏的 `instanceof` 判断，微秒级 | 即使 36 格全放背包也一样（读的是物品栏里的栈对象，不解码背包内容） |
| 多久算一次 | **只对开着联合界面的玩家**，每秒一次（`tickOpenSession` 已有每秒钩子）；其他玩家、其他 tick 为零 | 没开界面不算，没穿联合背包不算 |
| 面板请求里的校验 | O(1)：只验证目标引用还指着同身份的背包，**不重算整张成员表** | 每次点击不会比现在贵 |
| 成员表变化的通知 | 每秒比较"引用 + 身份"列表，变了才推 `CombinedMembersPayload`（几十字节） | 放进、取走背包时标签栏一秒内更新 |
| "全部"标签的内容刷新 | 服务端记住每个成员**上次发出去的内容对象**，每秒对每个成员比较一次（先比引用，不同再比相等），不同才推更新；自动拾取往 B 的背包里存东西时本来就会推增量，联合界面直接收到 | 16 个成员 × 每秒一次比较，仍是微秒～毫秒级 |

**真正会贵的地方**（也是限制成员数的真正理由）：

1. **每次请求都要解码背包**：`BackpackInventory.fromItem` 把物品上的内容整个解码、再 `saveInventory` 编码，这是现状，不是新增。"全部"里一次点击只动 1～2 只背包，与现在差不多；**快速转移放入"全部"**最坏要依次试 16 只（都满了的话），所以要：按需加载、同一请求内缓存已解码的成员、只保存改过的。
2. **"全部"的同步量**：16 只 × 每只最多 108 + 分类行 × 9 格；一次打开要发 16 个同步包（每个不超过现有整包），不是一个超大包。
3. **客户端**：最多约 16 × 几百格 = 几千格，只画可见的；搜索词缓存（`TermsCache`）已经存在，过滤是纯内存比较。

所以：**16 个上限的理由是界面与同步量，不是成员表计算**；只取前 16 个（按成员表顺序：穿戴、副手、物品栏下标升序）是对的，超出的在标签栏上提示数量。**36 格全放背包**的极端情况：前 16 个连接，其余 20 个提示"未连接"，没有性能问题。

## 唱片机（回答用户的问题）

读了代码：**唱片机的播放已经是"B 键会打开的那只背包"**——`JukeboxPlayback` 用 `BackpackRef.resolve(player)` 读取背包物品栈里的播放列表和身份，**不读面板里显示的背包**。所以切标签**不会影响播放本身**，用户设想的"和自动拾取一样，只对 B 打开的那只生效"其实已经是现状。

只需要处理一个界面细节：在联合界面里查看的标签背包若不是"B 会打开的那只"，它的右区里的唱片机控件按下去操控的是另一只背包的播放，会让人困惑。做法：**那只背包不是 B 激活的背包时，唱片机控件灰掉并提示"唱片机只对按 B 打开的背包生效"**。列入 065 的验证项。

**065 plan 的补充（2026-11-24 读码）**：移动工作台、移动熔炉、自动拾取、灯笼光、管子也都是按"B 会打开的那只"找背包（`OpenToolPayload` → `MobileTools.has` → `BackpackRef.resolve`），所以灰掉的是**三个移动工具控件**，不只唱片机；另外标题栏/标签栏实现为**挂在现有面板上沿之上**（像垃圾桶页挂在右侧），不改 `PanelLayout`。详见 `specs/065-combined-backpack-tabs/research.md`。

## 配置与协议

- 服务端配置 `[combined]`：`enabled`（默认 true，关了联合背包物品仍存在但不起作用）；`maxMembers` 固定 16（用户已定，不开放配置；以后要调再加）。
- 协议号 22 → **23**（新包：`CombinedSelectPayload`、`CombinedMembersPayload`，第二期 `CombinedClickPayload` 等）；`DataRevision` **不变**（联合背包无数据，背包数据结构不动）。
- 不用 mixin、不用反射（宪法 VII）；Curios/Accessories 一侧只改物品标签与槽位验证数据，沿用 061。

## 风险

1. **面板入口漏改**：30 处解析，漏一处就会"点击落在 B 的背包而不是标签里的那只"。对策：单一解析函数 + 接线测试 + 容器里逐项点验。
2. **客户端单例**：第一期靠"单例始终镜像当前标签"绕开；第二期"全部"才需要同时持有多只背包的主区域视图，那时引入 `ClientCombinedView`，不改单例的含义。
3. **跨背包写入的原子性**：从背包 A 拿起放进背包 B 是两次保存，同一服务端 tick 内完成，崩溃窗口很小，与现有"面板光标"相比没有新增风险，但第二期规格里要写明。
4. **身份不唯一**（复制背包）：寻址用引用不用身份。
5. **配方吃掉非空背包**：见 §1，配方必须只接受空背包。
6. **标签栏带来的高度**：小分辨率下面板可能超出屏幕；要核对 `topExtra` 参与位置钳制。
7. **颜色表**：16 色要在深色背景上也看得清，且与灰格、高亮不冲突，需要真机看；这是主观项，我不替你勾。
8. **没验证的事实**（plan 阶段读代码确认，不凭印象）：`OpenSessions.check` 对"没有身份的背包"的判断；`OpenToolPayload` 找背包的方式；JEI 排除区的实现；服务端"上次发出的内容对象"能否直接用物品上的 `BACKPACK_CONTENTS` 记录做引用比较。

## 待你定
