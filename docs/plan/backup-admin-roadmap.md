# 备份与管理员命令：结论（2026-11-09）

**状态**: 已决定并在 `specs/030-backpack-snapshots/` 里实现；本文件只记**为什么**，不再是待办。最初的规划（030 管理员命令、031 登记表备份、管理员面板、玩家命令、垃圾桶放入的二次确认）在下面的发现之后被推翻。

## 发现

1. **原版和 NeoForge 都没有全局物品索引。** 背包在箱子、潜影盒、未加载区块、离线玩家的存档里时，没有办法枚举或直接修改它们。最初设想的"过滤出所有浮动背包，整体备份"做不到。
2. **026 的登记表（世界存档里的索引 + 影子副本）几乎没有独有价值：**
   - 它只知道**被使用过**的背包，不知道箱子里的在哪里；
   - 它在世界目录里，**回档时跟着回去**，对"回档后找回新做的背包"毫无帮助；
   - 它让存档体积约翻倍，并且是物品栈之外的第二份真相，要保持一致；
   - 数量上限取消之后，连它的另一个理由也没了。
3. **"管理员特殊功能"没有立足点**：删除、恢复背包都要先找到它，找得到的范围（在线玩家的物品栏、副手、胸甲位、光标）玩家自己用面板就能处理；管理员能做的和普通玩家没有区别，除了一件事——**从快照生成新背包在生存模式里等于复制物品**，需要权限。
4. **墓碑与待办标记**要靠一份按 UUID 记的世界状态，会让用户困惑（"为什么删了还能用"），也需要同步，决定不做。

## 结论（已做在 030）

- 去掉登记表、影子副本、墓碑；背包身上只留 UUID，编号由它算出。
- 每只被使用的背包在**世界目录之外**存**单个背包的快照文件**（最近 5 份），内容变化后在合适的时机写出；失败只记日志。
- 命令只管快照：玩家可以看自己的；op 可以从快照生成**新背包**（副本，不覆盖）、删除、清理。
- 编号改 4 位（786,432 种），重复时命令列候选，改用 UUID 开头指定。

## 仍然暂缓（需要时再开新 feature）

- 玩家可用的快照面板（目前只有命令）。
- 快照目录的服务端配置、快照总量的上限。
- 垃圾桶放入背包的二次确认、掉落物消失（`ItemExpireEvent`）的处理：数据安全这一面由快照兜住——背包被销毁后，op 能从快照取回它最后一次保存的内容。
