## 1. 已验证的事实（容器 `mcfb-c1`，2026-11-20，AI 自动验证 + 读源码）

012 做的是"任意第三方菜单"的**通用路径**：面板 → 容器时，服务端把物品临时放进玩家物品栏的一个槽，调用当前菜单自己的 `quickMoveStack`（相当于在那个界面里 Shift+点击物品栏）；容器 → 面板时，Ctrl+点击容器**自己的 `Slot`**，服务端把那一格的物品转进背包。两个方向都只对"有真 `Slot`、且 `quickMoveStack` 在服务端完成"的菜单有效。

| 模组 | 面板 → 容器 | 容器 → 面板 | 依据 |
|---|---|---|---|
| **精妙存储**（Sophisticated Storage 1.6.13） | ✓ 通用路径可用 | ✓ 通用路径可用 | 游戏里：铁箱子打开、面板叠在上面，Ctrl+点击面板里的圆石与石头进了箱子；再 Ctrl+点击箱子格子，圆石回到面板。菜单与精妙背包同一个基类（`StorageContainerMenuBase`，真 `Slot`，服务端 `quickMoveStack`）。日志里有"The floating panel is shown on a screen of mod 'sophisticatedstorage'" |
| **应用能源 2**（AE2 19.2.20） | ✓ 通用路径可用 | **未验证，预计不可用** | 游戏里：ME 终端（ME 箱子 + 创造能量元件 + 流体晶体玻璃线缆 + 终端部件）打开，Ctrl+点击面板里的圆石，终端网格里出现"圆石 32"。`MEStorageMenu` 覆盖了 `transferStackToMenu`，服务端把物品插进 ME 网络。反向：网格里的条目由客户端的 `Repo` 绘制，不是菜单的 `Slot`，我们的反向转移找不到可点的格子；在容器里没能验证（面板盖住了网格的左半，只有一个条目可点） |
| **集成终端**（Integrated Terminals 1.11.2） | ✗ 无效（无害：什么也不移，面板里的物品留着） | ✗ 无效 | 读源码：`ContainerTerminalStorageBase.quickMoveStack` 在服务端只有"当前页自己处理"时才移（只有末影箱页实现了 `handleQuickMove`），存储页返回空；真正的移动由**客户端**发 `TerminalStorageIngredientSlotClickPacket`（`PLAYER_QUICK_MOVE`）驱动。网络里的物品也不是 `Slot`。游戏里**没有搭网络验证**（要集成动力学的线缆、接口、终端部件），只有源码证据 |

仓库里**没有** AE2 的任何专门代码或 spec：之前以为的"AE2 兼容"其实是 012 的通用路径。

## 4. 集成终端：面板 → 终端的做法

### 4.1 接入点：给通用路径加一个"按菜单类型分派的处理器"

`OpenContainerDelivery` 现在只会"停放 + `quickMoveStack`"。加一个小的服务端扩展点（纯接口，放在 `compat/`）：

```
interface NetworkStorageBridge {
    String modId();                              // "integratedterminals"
    boolean handles(AbstractContainerMenu menu); // 是不是我的菜单、当前页是不是我支持的页
    ItemStack insert(ServerPlayer player, AbstractContainerMenu menu, ItemStack stack); // 返回没放进去的部分
}
```

服务端递送物品到打开的容器时，先问注册的桥：有桥认得这个菜单就走桥（不停放、不调 `quickMoveStack`），否则走原来的通用路径。**这个接口为"终端 → 面板"预留**：以后加一个 `extract(...)`，AE2 的反向也用它。

### 4.2 集成终端的桥（`compat/integratedterminals/`，第三方类型只出现在这里）

- `handles`：`menu instanceof ContainerTerminalStorageBase`，当前页 `container.getTabServer(container.getSelectedTab())` 是 `TerminalStorageTabIngredientComponentServer` 且成分是**物品**（`IngredientComponent.ITEMSTACK`），并且**不是**合成页（`…ItemStackCraftingServer`）、不是末影箱页。
- `insert`：对当前页的物品网络通道调用插入：`tab.getIngredientNetwork().getChannel(container.getSelectedChannel())` → `insert(stack, false)`，返回剩余。网络离线、没有存储、通道不可用时原样返回。不碰玩家物品栏。网络变化会按集成终端自己的监听同步给客户端终端界面（不用我们发包）。
- 服务端校验沿用 012：菜单是服务端当前打开的菜单、玩家仍在范围内（菜单 `stillValid` 由原版保证）、背包是 `B` 键会打开的那只；守恒（放进网络多少、从背包拿走多少）由桥的返回值保证。
- 客户端：**不用改**（Ctrl+点击面板的手势已经发请求；终端界面是 `AbstractContainerScreen`，面板照常叠在上面——日志里会出现"floating panel is shown on a screen of mod 'integratedterminals'"）。

### 4.3 编译依赖

`compileOnly`（`transitive = false`）：`integrated-terminals`、`integrated-dynamics`、`common-capabilities`、`cyclops-core`（API 类型：`IngredientComponent`、`IPositionedAddonsNetworkIngredients`、终端的 tab 类）。仓库是 Modrinth maven（同开发运行时）。主代码的第三方引用只在 `compat/integratedterminals/`，`neoforge.mods.toml` 加四个可选依赖声明（见第 5 节：范围写宽，不让加载器强制）。`DependencyRulesTest` 的第三方坐标规则要加入这几个组。

### 4.4 测试

- 纯逻辑：桥的分派（哪个菜单、哪个页由哪个桥处理）、守恒（插入量 + 剩余 = 原量）、版本门（见 5.3）。用假菜单、假网络。
- 接线（源码文本）：第三方类型只在 `compat/integratedterminals/`；桥在服务端递送路径里被问到；范围外时不注册桥。
- 游戏里（容器，`-PnoJei`）：搭集成动力学网络（线缆 + 物品接口/箱子 + 终端部件）验证：面板里 Ctrl+点击 → 物品进网络、终端界面的网格里出现、面板里扣掉；网络满/离线 → 物品留在面板；合成页/末影箱页上 Ctrl+点击 → 不处理，沿用通用路径（无效果）。

### 4.5 工作量

中等。桥 + 扩展点约 6～8 个类（含测试），主要风险是第三方 API 的细节（通道的选择、离线网络的行为）要在游戏里试。"终端 → 面板"（以后）需要客户端识别悬停的网络条目（终端屏幕内部的悬停判断）并自己发一个包，工作量更大，对终端版本更敏感。

## 5. 第三方模组的版本管理

### 5.1 一个被源码证实的事实：不能用 `neoforge.mods.toml` 的 `versionRange` 做上限

读 FML 4.0.44 的 `ModSorter.verifyDependencyVersions`：**已安装的可选依赖，版本不在 `versionRange` 里，也会让加载失败**（"Unsupported installed optional dependencies"，进入"我们缺依赖或检测到不兼容就中止"的分支，游戏起不来）。所以：

- 给上限（或任何会把某个已装版本排除在外的范围）= 玩家装了新版第三方模组就**起不来游戏**，与"可选兼容、只警告"相反；
- 现有的下限（`curios [9,)`、`accessories [1,)`、`lambdynlights [4,)`）有同样的性质：装了更旧版本的 Curios 会直接拒绝加载。这是 033/034/052 时有意的（更旧版本不支持），但要知道它是**硬**的；
- 因此新兼容的 `neoforge.mods.toml` 声明一律写 `[0,)`（只用来让别的模组与启动器知道有这个可选依赖），**真正的范围放在我们自己的代码里**。

### 5.2 方案：运行时的"受支持范围表"+ 警告（用户的思路）

一张表（纯 Java，放 `compat/`），每行是一个第三方模组，带**一个或多个"已兼容的版本段"**：

```
ThirdPartyCompat(
    String modId,                    // "integratedterminals"
    String displayName,              // 提示里用
    List<VersionRange> supported,    // 例如 [1.11.0, 1.12.0) 与 [1.13.0, 2.0.0)：我们主动为哪些版本段做了兼容
    List<Requirement> also           // 同时要看的模组（各自也是一个"版本段列表"），如 integrateddynamics、commoncapabilities
)
VersionRange(Version minInclusive, Version maxExclusive)
```

- **版本段可以有多段，段与段之间可以有空隙**（例如 `>=1.1.0 且 <2.0.0` 与 `>=3.2.0 且 <4.0.0`）：我们没有义务为第三方模组的所有版本做兼容，只对其中一部分做了主动兼容，范围表就是"我们声明做过兼容的版本"的清单。段由我们做过的验证决定，不由第三方模组的版本号规律决定。
- 唯一的硬依赖是 Minecraft 1.21.1 与 NeoForge 21.1.251 及以上（`neoforge.mods.toml` 里的 `neoforge`、`minecraft` 两条，已有）；满足硬依赖的前提下，第三方模组可能有很多版本，不在任何一段里的就要**提醒用户**（5.3）。
- 以后同一个模组的不同版本段可能需要不同的适配代码（API 变了）：表的行预留一个可选的"变体"标签（`variant`），本 feature 只有一个变体，不实现分派；多段时每段落在同一个适配器上。
- 版本比较：按数字从左到右比，**宽松解析**（`1.11.2`、`9.5.1+1.21.1`、`1.1.0-beta.54+1.21.1`、`21.1.22` 都能取到前面的数字；预发布后缀与构建元数据忽略；没有数字的版本当"无法判断"，视为范围外并说明）。不使用 Maven 的 `ArtifactVersion` 的整体比较（它对 `+1.21.1` 这类后缀的处理不适合语义比较），只取 `ModInfo.getVersion()` 的字符串自己解析。
- 每一段的约定（语义化版本策略）：`minInclusive` = 开发时验证过的最低主.次版本（`.0` 补零）；`maxExclusive` = 该段的上限，**可以收紧到下一个次版本**（用户同意：Cyclops 家族次版本常带 API 变更时，用 `[1.11.0, 1.12.0)` 这样的窄段），也可以是下一个主版本。段之内的次版本升高**假定不破坏 API**（语义化版本策略），**所以要有 5.4 的兜底**。
- 判断一个已装版本：落在某一段 → 受支持；否则分三种说明：**比所有段都低**、**比所有段都高**、**落在两段之间的空隙里**（提示文字要区分，并列出所有受支持的段）。
- 单一事实来源：这张表。`neoforge.mods.toml`、README 的兼容表、开发依赖的版本（`build.gradle`）都由测试对着它核对（见 5.5）。

### 5.3 范围外时做什么（用户已确认）

- **主动兼容关闭**：已装版本不在任何一段里时，该模组的主动兼容**不启用**（桥不注册），只留 012 的通用路径；同时警告。
- **服务端配置项** `[compat].allowUntestedVersions`（布尔，默认 `false`）：管理员明知风险时设为 `true`，范围外也照常启用主动兼容（警告照旧）。**配置注释必须写明风险**：第三方模组的 API 变了，我们的代码可能出错，严重时让服务器崩溃（`NoSuchMethodError` 之类不是普通异常）；启用前先备份存档；出了问题请先把它设回 `false`。启动时读取，改动需重开世界（同 057 的配置）。
- **日志**：服务器启动（`ServerStartingEvent`，与快照服务同一处）对表里每个**已安装**的模组检查，范围外的写一条 WARN：模组名、已装版本、受支持的所有版本段、属于"过低/过高/空隙"哪一种、主动兼容是"未启用"还是"被配置强制启用"。
- **聊天**：管理员登录（`PlayerLoggedInEvent`）时，每个范围外的模组一条提示，内容同上的人话版，并说明"面板仍可在它的界面上使用，只是主动兼容（例如存入集成终端）没有启用"（强制启用时改成风险提示）。每次登录一次，不记名单（持续存在的状态，不像 057 的一次性升级提示）。
- **管理员** = 拥有 op 权限的玩家（`player.hasPermissions(2)`，与 031/057 一致）：专用服务器上是 `/op` 过的玩家，单人游戏里是开了作弊的玩家。没开作弊的单人玩家和专用服务器的控制台只有日志。
- 没装的模组：不检查、不提示。
- 客户端才有的兼容（如 LambDynamicLights）：只写客户端日志；单人游戏里开了作弊的玩家同样收到聊天。

### 5.4 兜底：`LinkageError` 防护（不依赖版本号）

语义化版本不保证次版本不破坏 API（用户也认同"无法预测"）。所以每个第三方适配器的入口都包一层：

- 捕获 `LinkageError`（`NoSuchMethodError`、`NoClassDefFoundError`、`IncompatibleClassChangeError`）与适配器自己的 `RuntimeException`；
- **第一次出错就在本次运行里关闭该兼容**，写一条 ERROR 日志（含异常），并给在线管理员发一条聊天；物品不丢（桥在出错前没有改动任何一方，或在改动后补回）；
- 不用反射：只是 `try/catch` 加上"关闭"的标志。

### 5.5 测试与防漂移

- 纯逻辑：版本解析（用上面列的真实版本串）、多段范围判断（含边界、预发布、无数字；段内、过低、过高、两段之间的空隙四种结果）、表的完整性（每段 `min < max`、同一模组的段互不重叠且按升序）。
- 资源/接线：`neoforge.mods.toml` 里表里的模组都声明为 `optional` 且 `versionRange="[0,)"`（防止有人写了上限）；README 的兼容表与表一致；`build.gradle` 里的开发依赖版本落在对应范围内（测试读 `build.gradle` 的 `localRuntime` 行，与表比较）。
- 配置：`allowUntestedVersions` 的注释里含"备份"与风险说明（资源测试）；默认 `false`；为 `true` 时范围外仍启用且仍警告。
- 游戏里：用调试开关把"已装版本"伪造成范围外（沿用 `VersionDebug` 的写法，如 `-Pmcfb.fakeModVersion=integratedterminals=2.0.0`），验证管理员登录的聊天与服务器日志，以及兼容被关闭；非管理员看不到。

### 5.6 有没有更合适的办法（对比）

| 办法 | 做什么 | 优点 | 问题 | 结论 |
|---|---|---|---|---|
| `neoforge.mods.toml` 的 `versionRange` | 加载器强制 | 零代码 | **范围外会让游戏起不来**（5.1，已读源码）；上限尤其不行 | 只用于"必须拒绝加载"的下限；新兼容不用 |
| `type="discouraged"` 声明"已知不好的范围" | 加载器记 ERROR 日志，客户端启动时显示警告，不中止 | 非阻断、零代码 | 只能写"已知坏"的范围，未来版本写不出；弹给每个玩家而不是管理员；没有聊天提示 | 可选的补充，不能替代 |
| **运行时范围表 + 管理员警告**（用户的方案） | 自己比较版本，范围外警告 | 非阻断；警告对象是管理员；一处事实来源 | 只能靠版本号，防不了范围内的破坏 | **采用，作为核心** |
| `LinkageError` 防护 + 失败即关闭 | 出错时关兼容并警告 | 不依赖版本号，覆盖"次版本破坏 API"这种无法预测的情况 | 要在每个适配器入口写；第一次出错之前的那一次操作可能失败 | **采用，作为兜底** |
| 特性探测（启动时用反射检查用到的类和方法在不在） | 启动时就知道行不行 | 比版本号准 | 要反射；每个适配器要维护一份"用到的 API 清单" | 暂不做；以后真的遇到"范围内也坏"再加 |
| 精确的已验证版本白名单 | 只有列出的版本才启用 | 最稳 | 第三方模组每周更新，几乎总在名单外，天天警告 | 否 |

## 6. 已确认的决定（用户 2026-11-20）

1. **范围外时主动关闭兼容并警告**（聊天与日志），**再加服务端配置项** `[compat].allowUntestedVersions`（默认 `false`）让管理员强制启用；配置注释写明风险并提醒先备份数据。
2. **版本范围接受建议，可以收紧**：集成终端用窄段，初版 `[1.11.0, 1.12.0)`（开发验证过 1.11.2）；同时要求集成动力学与公共能力各自的版本段（初版取开发验证过的主.次，如 `[1.39.0, 1.40.0)`、`[2.11.0, 2.12.0)`，实现时按验证过的版本定）。以后验证了新版本就**加一段**，不一定改旧段。

## 8. 设计原则：档位管"适配代码"，"向第三方注册内容"走启动配置（061，2026-11-23）

058～060 的 FULL / GENERIC / OFF 档位管的是**本模组的代码**对第三方模组做什么（桥、背着来源、通用路径是否生效）。061 要给 Curios、Accessories 各加一个专用槽位，这是另一类事：**向第三方模组的数据里添加内容**。它在数据包加载时就决定了，而服务端配置（SERVER 类型）晚于数据包才读入、客户端配置在专用服务器上根本不加载，所以**档位管不了它**；槽位消失的后果（槽里的物品去向）又取决于对方模组。

决定（用户已确认）：这类添加由 **FML 的 `STARTUP` 配置**里的**按模组布尔开关**控制（`config/mcfloatingbackpack-startup.toml`，注册的瞬间读入，默认开，改动需重启），数据文件带一个自定义的 NeoForge 条件 `mcfloatingbackpack:slot_enabled` 去读它；与档位互不相干。宪法 VII 因此加了一个子节（2.3.0）。以后别的模组要"注册内容"，照这个做法给它单开一项，不复用档位。

061 在游戏里查到的事实：关掉开关、重启后，**Curios 把专用槽里的物品还给玩家**；**Accessories 不还，物品消失**（背包内容只能靠 030 的快照恢复）。所以两处文档（README、配置注释）都写了"先取下背包再关开关"。客户端的开关值在联机时不起作用（槽位由服务端同步）。
