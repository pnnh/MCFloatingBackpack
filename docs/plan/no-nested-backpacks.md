# 禁止浮动背包嵌套（064）：分析与取舍

> 完整规格见 `specs/064-no-nested-backpacks/`；本页只记"为什么这样限制、为什么不限制别的"。

## 为什么要禁浮动背包套浮动背包

背包的内容是物品上的数据组件，放进另一个容器时整份按值复制。嵌套让数据量按扇出连乘：皮革背包 36 格，三层各塞满是 36³ ≈ 4.7 万只背包（按每只空背包几百字节估算，未实测）。这会撞上自定义载荷约 1 MiB 的上限、玩家数据的登录同步，以及 057 快照（把嵌套内容再存一遍）。皮革背包很便宜，所以这也是服务器可被刻意搞坏的入口。原版禁止潜影盒套潜影盒、收纳袋有大小上限，是同一个原因。

## 做了什么

- 面板的所有区域（主区域、工具区、垃圾桶）和所有入口（点击、拖动、Ctrl/Shift+点击、自动拾取、容器 → 面板、终端 → 面板、Delete/倾倒）都不收浮动背包，也不收"里面装着浮动背包"的物品（深度扫描：原版容器、收纳袋结构化读取，别的模组的数据编码后查物品 id）。
- `FloatingBackpackItem` 重写无参 `canFitInsideContainerItems()` 返回 false：原版潜影盒、收纳袋、旅行者背包（反编译确认它的格子会问）和 NeoForge 的 `ComponentItemHandler` 拒收。
- 旧数据不动：已经嵌套的可以取出；面板记着"刚从哪只背包拿起了什么"，同一个物品放回同一只背包放行一次（不增加嵌套）；其它一律拒绝。

## 为什么没有限制别的

- **其它容器放进浮动背包（潜影盒等）**：潜影盒不能套潜影盒，扇出有界；"潜影盒放进背包"是最主流的用法（051 的"容器收纳"分类里就有潜影盒）。
- **AE2、集成终端、精妙存储的网络与箱子**：没有可用的钩子。AE2 19.2.20 只有一个无关的 `ae2:blacklisted/annihilation_plane` 标签；这三者不看 `canFitInsideContainerItems`；我们的代码也不在它们的存入路径上。要拦只能用 mixin，违反宪法 VII。存进网络的浮动背包和潜影盒一样，是一件带数据的物品。
- **精妙背包**：默认 `containerItemsDisallowed=false`，不认 `canFit`；我们不替别的模组改配置，只在 README 写明管理员的两种做法。

## 来源记录为什么是"记录"而不是"看光标"

最初的设想是"面板光标上的物品就是从本背包拿起的"。读代码后发现不成立：开着容器界面（含按 E 的物品栏）时，从面板拿起的物品直接进菜单携带物（`BackpackClickLogic.click` 的结果交给 `menu.setCarried`），创造模式则镜像到 `inventoryMenu` 的携带物。所以改成每个玩家一条临时记录。退路：若记录不可靠，放行条件恒为假，规则变成"一律只能取出"，旧数据照样不丢。

## 没做、留给以后

- 把几十只满背包放进 ME 网络，对比同样数量的潜影盒，量终端同步与元件体积（决定要不要在文档里再提醒）。
- 客户端先行拒绝（现在由服务端回发槽位，被拒的一瞬间可能有一帧闪现，见 DELIVERY 的验证记录）。
