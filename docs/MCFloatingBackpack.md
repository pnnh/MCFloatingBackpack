# MCFloatingBackpack — 项目目标与可行性分析（初版）

## 1. 项目概述

### 背景
原版 Minecraft 在同一时间通常只允许一个激活的 `Screen`（例如按 E 打开的玩家物品栏，或打开的箱子 / 旅行者背包 / 精妙背包界面）。打开新容器界面时，前一个界面会被关闭。这使得「像魔兽世界那样同时打开多个可拖动背包窗口，并在窗口之间拖动物品」在默认机制下不可用。

### 目标
开发一个面向 **Minecraft 1.21.1 + NeoForge** 的**浮动背包模组**：

- 通过**可自定义快捷键 / 组合键**开关浮动背包面板。
- 面板类似 MMO 背包：可拖动、始终浮在游戏画面之上。
- 即使同时打开原版物品栏、旅行者背包、精妙背包或箱子等容器 GUI，浮动背包仍保持可见并可交互（类似可拖动 HUD / 叠加层）。
- 支持在浮动背包与玩家物品栏、第三方背包 GUI、原版容器之间**互相拖放物品**。

### 核心原则
- **不要用「替换当前 Screen」作为主路径**：否则无法与其它容器界面共存。
- **显示层与存储层分离**：客户端负责面板渲染、拖动与输入抢占；服务端负责真实物品存储与校验。
- **优先 Overlay / Panel，而非多 Screen 栈**：参考 JEI/EMI 叠加在容器 GUI 上的做法。
- **双端模组**：只要背包有独立格子且可联机同步，就需要服务端逻辑；不能做成纯客户端伪造物品。
- **分阶段交付**：先打通「可开关、可拖动、可与原版物品栏互拖」，再做第三方背包专项兼容。

## 2. 核心功能需求（初版范围）

### 2.1 浮动面板 UX
- 快捷键切换显示 / 隐藏（默认建议 `B`，可在控制设置中改键与修饰键）。
- 面板可拖动到屏幕任意位置，位置可持久化（本地配置）。
- 打开其它容器 GUI 时不自动关闭；关闭其它 GUI 时也不强制关闭浮动背包。
- 渲染层级高于当前容器界面内容（至少在物品栏 / 容器内容之上可点中）。

### 2.2 物品交互
- 面板内格子支持点击、拖拽堆叠等接近原版槽位的操作；Shift 单击/拖动用来选择格子（014），原来的主手交换改为 Alt+点击。
- 当原版物品栏或其它 `AbstractContainerScreen` 打开时，可在浮动背包槽位与当前打开容器槽位之间移动物品。
- 无打开容器时，仍可独立管理浮动背包内物品（打开面板本身即足够）。

### 2.3 存储与联机
- 背包内容绑定玩家（或绑定可配置的背包物品 / 附件），由服务端权威保存。
- 客户端预测点击反馈，服务端通过网络包确认，避免「看起来移动了但实际没同步」。

### 2.4 兼容目标（优先级）
1. 原版玩家物品栏（E）
2. 原版箱子 / 潜影盒等标准容器
3. 精妙背包（Sophisticated Backpacks）类界面
4. 旅行者背包（Traveler's Backpack）类界面
5. JEI/EMI 叠加层共存（避免抢鼠标冲突）

## 3. 原版限制：为什么「同时只能开一个背包」

| 机制 | 表现 | 对本需求的影响 |
|------|------|----------------|
| `Minecraft.screen` 单例 | 客户端同一时刻只有一个活动 Screen | 用 `setScreen(new InventoryScreen)` 会关掉上一个界面 |
| `AbstractContainerMenu` | 服务端玩家通常对应一个打开的容器菜单 | 多容器同时打开需要额外菜单会话或自定义交互协议 |
| 槽位点击 | `ServerboundContainerClickPacket` 针对当前 `containerId` | 跨界面拖放不能只靠「两个 Screen 同时存在」 |
| 鼠标捕获 | Screen 打开时游戏进入 GUI 输入模式 | Overlay 必须在 Screen 事件链中抢先处理点击 |

结论：**需求无法通过「再做一个普通 Screen」直接满足**；必须绕开单 Screen 假设，或改造容器窗口系统。

## 4. 可行性结论

**总体判断：可行，但工程重点在「叠加层输入 + 跨菜单物品同步」，不是简单 UI 贴图。**

| 能力 | 可行性 | 说明 |
|------|--------|------|
| 快捷键开关浮动面板 | 高 | NeoForge `RegisterKeyMappingsEvent` + 客户端 tick / 输入事件即可 |
| 面板拖动与常驻显示 | 高 | HUD / `ScreenEvent.Render` 叠加绘制已有大量先例 |
| 浮在原版物品栏之上并可点击 | 高 | JEI/EMI、Inventory HUD+、Panels Not Screens 等证明 Overlay 可拦截鼠标 |
| 与箱子等标准容器互拖物品 | 中高 | 需把 Overlay 点击翻译成对「当前打开 Menu」或「自有 Menu」的服务端操作 |
| 与精妙 / 旅行者背包互拖 | 中 | 对方若走标准 `AbstractContainerScreen`/`Menu`，路径类似；若自定义渲染/输入则需专项适配 |
| 完全像 WoW 多窗口自由共存且无兼容问题 | 中低（长期） | 第三方 GUI 差异大，需黑名单 / 适配层与持续回归 |

### 4.1 推荐技术方案（主路径）

采用 **「自有背包库存 + 客户端浮动 Overlay」**：

1. **服务端**：为玩家注册背包库存（Attachment / Capability / 保存到玩家 NBT），提供点击与移动的网络协议。（**现状**：库存保存在背包物品实例的数据组件上，不再是玩家 Attachment，见 `specs/005-item-backpack`。）
2. **客户端**：不调用 `setScreen` 打开背包；用 Overlay / Panel 绘制格子。
3. **输入**：在 `ScreenEvent.MouseButtonPressed.Pre`（及拖拽相关事件）中，若指针落在浮动面板上则消费事件，避免穿透到下层容器。
4. **跨 GUI 拖放**：
   - 浮动背包 ↔ 当前打开的 `AbstractContainerMenu`：通过自定义包或模拟槽位点击，在服务端两个库存之间转移。
   - 浮动背包自身：始终有明确的服务端库存句柄，不依赖「当前是否打开了 Screen」。
5. **可选增强**：当需要原版手持光标物品（carried stack）体验时，复用 / 同步玩家当前 Menu 的 carried 槽，或自建 carried 状态并在打开原版 GUI 时合并。

这条路径与「再做一个 InventoryScreen」相比，能直接满足「按 E 后背包仍浮在上面」。

### 4.2 备选 / 参考路径

| 路径 | 优点 | 缺点 | 适用 |
|------|------|------|------|
| Overlay + 自有库存（推荐） | 不抢占 `Minecraft.screen`；可控性强 | 要自研槽位交互与同步 | 本模组主目标 |
| 改造多窗口容器（如 Windowed GUIs 思路） | 可同时开多个原版容器 | 侵入大、兼容面极广 | 可作为远期研究方向，非 MVP |
| 仅 HUD 展示玩家背包（InvHUD 类） | 实现简单 | 通常只是「看」或弱交互，不是独立背包 | 不满足独立存储目标 |
| 第三方面板库（如 Panels Not Screens） | 拖动 / 停靠 / z-order 现成 | 引入依赖；库存逻辑仍要自写 | 可评估是否降低 UI 成本 |

### 4.3 关键先例（说明并非空中楼阁）

- **JEI / EMI**：在容器 Screen 之上绘制可交互区域并处理鼠标，证明 Overlay 可行。
- **Inventory HUD+ / InvHUD**：背包格子 HUD 化、可拖动定位。
- **Windowed GUIs**：把容器改成可同时存在的窗口（目标更激进，兼容成本更高）。
- **Panels Not Screens**：NeoForge 1.21.1 上的可拖动面板框架思路，可参考输入路由与 z-order。
- **HoloGUI**：浮动菜单同时保留世界交互的另一类尝试。

本模组与「纯 HUD 显示」的差异在于：**独立（或半独立）库存 + 与其它打开容器双向拖放**；与 Windowed GUIs 的差异在于：**不试图重做全游戏多窗口系统，只做一个常驻浮动背包**。

## 5. 主要风险与缓解

| 风险 | 影响 | 缓解 |
|------|------|------|
| 鼠标事件与 JEI/EMI/其它 Overlay 抢占顺序 | 点击失灵或点穿 | 明确事件优先级；提供「面板锁定 / 穿透」配置；联调 JEI |
| 第三方背包非标准 Screen | 无法互拖 | 检测模组后走适配器；做不到则降级为「仅与原版容器互拖」并文档说明 |
| carried 物品（鼠标上挂着的物品）状态分裂 | 拖到一半错乱 | 尽量接入当前打开 Menu 的 carried；无 Menu 时用自有 carried 并在打开 GUI 时同步 |
| 仅客户端改画面、不同步服务端 | 联机刷物 / 回滚 | 服务端权威；所有移动走网络校验 |
| 打开 Screen 时快捷键被吞 | 无法开关面板 | 使用 `KeyConflictContext.UNIVERSAL` 或额外在 Screen 输入钩子中处理 |
| GUI 缩放 / 宽屏坐标 | 拖动与点击偏移 | 统一用 GUI 坐标换算（`guiLeft`/`guiTop` 同思路） |

## 6. 建议里程碑

1. **M0 — 工程骨架（本仓库当前状态）**  
   NeoForge 1.21.1 工程、模组入口、快捷键注册、文档。
2. **M1 — 可见可拖动空面板**  
   Overlay 渲染、拖动、位置持久化；尚无真实物品。
3. **M2 — 服务端库存 + 面板内取放**  
   玩家绑定背包、网络同步、面板内点击。
4. **M3 — 与原版物品栏 / 箱子互拖**  
   有打开容器时的跨库存转移与 carried 行为。
5. **M4 — 精妙 / 旅行者等热门背包兼容**  
   二者主界面均继承 `AbstractContainerScreen`，走 M3 菜单 carried 通路；软检测 + 可选 `./gradlew runClientCompat` / `runServerCompat`（等价于 `-PcompatRuntime`）联调。流体罐/假槽/升级页不保证。详见 `specs/004-backpack-compat/`。
6. **M5 — 打磨**  
   配置项、键位冲突、JEI 共存、多语言、性能与联机测试。面板可拖拽缩放行列（独立调整，3 格下限，列数变化时按虚拟总行数重新排布，仅纵向滚动条）、标题栏关闭按钮、标题栏按背包等级动态命名，详见 `specs/007-floating-window-chrome/`。**Ctrl+点击 / Ctrl+拖动在玩家物品栏与浮动背包之间快速转移物品**（macOS 为 Command 键，Shift 手势保持原样，详见 `specs/011-ctrl-quick-transfer/`）。从面板转出时，打开着容器（箱子、精妙背包、旅行者背包、熔炉等）就按该容器自己的 Shift+点击规则存入容器，否则进玩家物品栏；反过来，在打开着的容器里 Ctrl+点击/拖动容器自己的槽位，物品存入浮动背包（输出类槽位除外，按着 Shift 时让路）（详见 `specs/012-ctrl-transfer-to-open-container/`）。面板内部还支持原版风格的拖动：拿着物品按住左键（或右键）滑过多个格子，松开时均分（或每格放一个），拖动中有预览；单击拿起一组后不松手滑过同种物品的格子可把它们收进光标；双击同一格可把面板里所有同种物品收集到光标。按着 Ctrl/Command 或 Shift 时让路，拿着物品单击放下改为松开时生效（详见 `specs/013-panel-drag-split-gather/`）。面板里还有**选区**：按住 Shift 单击切换或拖动加入格子（已选格子金色内边框），之后按住 Ctrl/Command 点击任一已选格子，松开鼠标时把所有已选格子里的物品批量转出（目标同 011/012，放不下的留在原格，选区不变）；不按 Shift 点击面板格子清空选区；原来 HUD 下 Shift+点击的主手交换改为 Alt（macOS Option）+点击（详见 `specs/014-panel-selection/`）。**019 起面板不再有"没有任何界面的 HUD 模式"**：没有容器界面时，面板挂在模组自己的透明宿主界面上（只是兜底：打开原版物品栏、精妙背包、工作台、聊天等任何其它界面时宿主自动让位，关闭后自动恢复；宿主在场期间玩家不能移动和转向），详见 `specs/019-fallback-host-screen/`。主区域外侧还有三个**工具区**：左区（输入工具区）、右区（输出工具区）各一列，下区（功能工具区）一行并横跨整个面板宽度，格子底色各不相同（浅蓝/浅绿/浅琥珀），始终贴在主区域外侧；面板不再有滚动条，四块区域各自用滚轮滚动（下区左右滚动），有隐藏内容的一侧显示小扁箭头；缩放只改变主区域行列，面板最小 5×4；三个工具区容量由等级的默认尺寸决定（左右 = 默认行数，下 = 默认列数 + 2），能存放任意物品但只做单击/右键（不参与 Shift 选区、Ctrl 转移与拖动手势），为将来的扩展工具（类似升级组件）预留，详见 `specs/016-panel-tool-areas/`。拖动缩放只停在**不会出现实心空格的合法尺寸**上（列数整除主格子数、行数不超过左右区格子数，不合法的目标直接忽略；例如铁背包只能是 3/6/9 列、3～6 行），滚动箭头缩小并贴边，详见 `specs/017-panel-valid-sizes/`。功能区里的第一个**扩展工具"标签管理器"**（018）：它是一个普通物品，可以放进任何区域，只有放进功能区才有功能——左键点击展开一个覆盖主区域的标签面板，为 Shift 选中物品的**物品分类**（如 `minecraft:oak_log`，不是某个具体堆叠）增加和删除标签（预设 10 个，自定义标签仅限 1～16 个小写可见 ASCII 字符，每个分类最多 10 个标签，满了加号变灰）；标签存放在该背包自己的数据里，物品被取走、关闭面板、退出重进后仍在，升级保留；增删由服务端校验，协议升到 8；有合成配方（线/纸/皮革/书/墨）与一张平面图标，详见 `specs/018-tag-manager/`。**第三方模组兼容开关**（020）：浮动背包只依赖 Minecraft 1.21.1 与 通用互动）、`GENERIC`（没有专用适配：关闭我们为该模组写的专有代码，没写过的模组与 FULL 一样；不决定面板能否显示、能否交换物品，那取决于该模组自己的实现；目前唯一的专用适配是 `jei`——让 JEI 避开面板）、`OFF`（面板不显示，与该模组的界面二选一；对只叠加在别的界面上的 `jei` 等同 GENERIC）；配置写错会在聊天里提示；没列出的模组按 `specs/020-compat-switches/`。第二个**扩展工具"垃圾桶"**（021）：普通物品，可放进任何区域，只有放进**右侧区**才有功能——左键点击在面板右边缘之外向右展开一个小面板（标题栏 + 3×3 格）；光标上的物品点击面板或拖到面板上松开即整组丢进去，光标为空时点击有物品的格子把那一组拿回光标，Ctrl+点击/拖动把组恢复到主区域（放不下的留在原位）；只保留最近丢掉的 `mcfloatingbackpack:never_trash`（本模组物品、潜影盒、收纳袋、龙蛋、下界之星、鞘翅、不死图腾、信标、海洋之心、附魔金苹果），标签面板拒绝给它们加"垃圾"标签（只拦这一个标签）；一次操作会让超过 9 组被永久销毁时先弹确认框（半透明蒙版盖住整个浮动面板，ESC 只取消确认），服务端要求带"已确认"标志；协议升到 10，详见 `specs/022-trash-delete-tools/`。**背包配方难度调整**（023）：升级改为四档统一用材料"块"（铁块 / 金块 / 钻石块 / 下界合金块），并且锻造台的模板格要放入各档指定的原版锻造模板——皮革→铁用哨兵、铁→金用沙丘、金→钻石用眼、钻石→下界合金用下界合金升级模板，模板与材料各消耗 1 个，背包内容照旧保留；皮革背包的工作台配方改为 5 皮革 + 2 铁锭 + 线 + 箱子；升级配方的 JSON 增加可选的 `template` 字段（缺省仍是"模板格必须为空"，旧数据包不受影响）；JEI 里能看到这些配方；已有背包不受影响；不新增任何贴图，协议升到 11，详见 `specs/023-recipe-difficulty/`。第三个**扩展工具"自动拾取"**（024）：普通物品，可放进任何区域，只有放进**左侧区**才有功能——只对"按 B 会打开的那只"背包生效（与面板开关无关）：玩家拾取地上物品时先存入该背包主区域（先叠后填），放不下的部分按原版进物品栏；左键点击展开覆盖主区域的**标签黑名单页面**（最多 64 个标签，复用 018 的标签规则与输入组件，与标签面板互斥），分类标签（用标签管理器给物品分类打的标签）命中黑名单的物品**留在地上**，既不进背包也不进物品栏；黑名单存放在该背包自己的数据里（第六个字段，旧背包读成空，升级保留）；服务端规定左侧区最多 1 个自动拾取（已有的不删）；与精妙背包/旅行者背包同时拾取时**不检测、不依赖它们的内部类**，只用低优先级并在事件已被处理时跳过（各背包拿多少不保证，只保证不崩溃、不复制、不丢失）；协议升到 12；配方为中期（4 铁锭、末影珍珠、2 红石粉、漏斗、钻石）与一张平面图标，详见 `specs/024-auto-pickup/`。**标签总览**（025）：标签面板顶部状态行右端有一个菜单图标，点它在"选区视图"（018 原有）与"总览视图"间切换；总览列出这只背包给哪些物品分类设置过标签（**不要求物品现在在背包里**，已移除模组的物品显示原始注册 id），每行显示图标、名称、标签数量，悬停列出全部标签，按显示名排序、可滚动；列表顶部可按一个标签筛选（文本框 + 下拉，候选是预设标签与本背包已用过的标签），直接找出"哪些被标成了垃圾"；点击某行进入明细页，增删该分类的标签（每个分类最多 10 个、"垃圾"标签的物品保护沿用 022；已不在游戏里的物品只能删除不能添加）；列表每行的"清空"需要行内二次确认；总览的修改走一个按物品注册 id 寻址的新请求（服务端核对功能区有标签管理器、规则；添加只允许对已有标签的分类），协议升到 13，不新增贴图、数据格式不变，详见 `specs/025-tag-overview/`。**背包编号与登记表**（026，2026-11-09 精简）：每只浮动背包有一个玩家可见的四位编号（如 `K7M2`，首位是字母，后三位是字母或数字，去掉易混淆的 I、O、0、1，共 786,432 种；026 起初是三位、24,576 种，030 改成四位以减少重复），显示在面板标题栏等级图标右侧（窄面板下按像素截断、悬停显示完整编号）和物品提示里，没有编号的背包提示"还没有编号（首次使用时分配）"。**编号由背包的内部标识（UUID）算出**，不查表、可能偶然重复，只是用来区分自己的背包；复制出来的栈共用同一个标识与编号。皮革背包的合成配方换成 `mcfloatingbackpack:backpack_crafting`（图案与材料不变），在合成结果上盖标识，所以合成出来立刻有编号；创造栏、`/give`、旧存档里的背包第一次被使用时才有标识；升级不改编号。世界存档里**没有登记表**（026 最初做过，030 去掉了：它回档时跟着回去、不知道箱子里的背包、还让存档翻倍）；服务端所有读写背包的入口先过同一道检查，它只给没有标识的背包分配标识，**不拒绝任何请求**。**不限制背包数量**（没有每人上限、没有服务端配置）：极端数量的风险（模型面数拖低帧率）不做预防，背包的备份见 030 的快照；不新增贴图，详见 `specs/026-backpack-id/`。**创造物品栏界面兼容**（027）：创造界面里玩家手上的物品只存在于客户端，原先点面板放不进去；现在创造界面（物品栏标签页与物品标签页）打开且面板可见时，客户端把创造光标报告给服务端，服务端的菜单光标镜像它，面板的放入、拿起、拖动、聚拢、垃圾桶都与生存界面一致，服务端处理完把结果光标发回客户端；只有创造模式玩家的报告被接受，物品栈要合法；关闭创造界面时光标上的物品由原版逻辑放回物品栏（面板可见时从创造物品列表里取的虚拟物品也会放回，与原版创造模式的"直接丢弃"不同，是为了让面板里取出的物品守恒）；Ctrl 快速转移在创造界面里仍未支持；这是对原版的修复，不是限制，宪法 2.2.0 原则 VII 的"Support priority"规定原版问题必须修复；协议升到 15，不新增贴图与设置，详见 `specs/027-creative-inventory-compat/`。**背包在 GUI 里用平面图标**（028）：五档背包都是 1.6 万～2 万个面的 OBJ 网格，快捷栏里放 8 只时每帧要画约 15 万个面，帧率从约 101 掉到约 22 fps（同位置同视角对照）；现在每档物品模型是 `neoforge:separate_transforms`：**GUI**（快捷栏、物品栏、箱子、JEI、面板标题栏）用 32×32 的平面图标，手持（第一、第三人称）、**背在背上**、展示框与**地面掉落物**仍用原来的 3D 模型（`BackpackBackLayer` 用 `FIXED` 场景，所以 `FIXED` 不换）；图标由开发期脚本 `design/demo/tools/render_backpack_icons.py` 从 OBJ 与皮肤贴图按原来的 GUI 视角渲出（纯 Python + PIL，输出确定）；3D 模型、皮肤贴图、配方、功能都不变；图集仍是 2048×1024；用户验证：同位置同视角、物品栏放 8 只背包，帧率稳定在 90 fps 以上（改动前约 22），详见 `specs/028-gui-flat-icons/`。**创造物品栏界面里的 Ctrl 快速转移**（029）：011/012/014 的 Ctrl+点击、Ctrl+拖动、选区 + Ctrl 现在在创造界面（物品栏标签页与物品标签页）里也可用：客户端把物品栏标签页里按菜单序号编号的格子换算成真实的物品栏下标（快捷栏在菜单里是 36～44、在物品栏里是 0～8），服务端转移后给创造玩家同步一次整份物品栏（物品标签页会忽略单格更新）；创造物品列表（虚拟物品）不是转移来源、Delete 键删除到垃圾桶在创造界面里仍未支持；协议不变，不新增贴图与设置，详见 `specs/029-creative-quick-transfer/`。**背包快照**（030，取代最初的"登记表管理员命令"）：服务端给每只用过的背包在**世界目录之外**存快照，位置是 `<服务器实例目录>/mcfloatingbackpack/snapshots/<世界文件夹名>/<背包UUID>-<编号>/<毫秒>.dat`（回档不会带走它）；内容停止变化 10 秒后、最长 5 分钟、玩家退出、服务器停止、以及任何快照命令执行前写出；每只背包只留最近 5 份，内容没变不写，旧背包本次运行里第一次使用时补一份基线；编码在主线程、写文件在一个后台线程，失败只记日志。命令 `/mcfloatingbackpack snapshot …`（别名 `/mcfb`）：所有玩家可以 `list [页]`、`info <背包>` 看**自己**的快照（背包用 4 位编号、UUID 或 UUID 开头指定，编号对应多只时列出候选）；**op（权限 2，控制台可用）**还有 `list all|owner <玩家>|inactive <天数>`、`restore <背包> [版本] [玩家]`（从快照给玩家一只**新背包**——副本、不带标识、不覆盖原背包；在生存模式里等于复制物品，所以需要权限）、`delete <背包> [版本]` / `delete <背包> confirm`、`trim <天数> [confirm]`（默认只预览，0 表示全部）。**不做**管理员特殊功能：原版和 NeoForge 都没有全局物品索引，找不到箱子、未加载区块、离线玩家里的背包，所以没有墓碑、没有遍历、没有直接改背包内容的命令；所有消息带英文兜底文字；不新增网络包与设置，详见 `specs/030-backpack-snapshots/` 与 `docs/plan/backup-admin-roadmap.md`。标题栏改为背包等级图标（悬停显示名称提示，窄面板下不再溢出）；可选的 JEI 兼容：通过 `IGlobalGuiHandler` 让 JEI 避让浮动面板区域，并修正与 JEI 自身提示框的渲染顺序冲突，仅在玩家安装 JEI 时生效，详见 `specs/008-panel-title-icon-and-jei-safe-zone/`。五档背包（皮革/铁/金/钻石/下界合金；其中下界合金贴身的一面在 015 里重画成了平整背板，以便区分前后，详见 `specs/015-netherite-back-distinct/`）的外观是由 AI 生成工具产出的雕刻网格模型，通过 NeoForge 自带的 OBJ 加载器接入：五个等级各自一个独立模型、**无肩带**，贴图每档 512×512（010 起；009 时为 1024×1024）外加供光影包使用的 `_n` 法线贴图，法线贴图用图集 `filter` 排出共用方块图集，图集实测 2048×1024（原 4096×4096）；背部渲染直接渲染物品自己的烘焙模型，所以图标、手持、背上是同一套外形，详见 `specs/009-sculpted-mesh-backpack-models/`，素材与处理记录见 `design/demo/`。已知缺口：这些大贴图会把共用方块图集撑到 4096×4096、网格有少量开放边、没有性能预算，都记录在 009 的"已知限制"里，尚未解决。可拆卸小包（左/右/后）与升级组件玩法已延后，当前所有档位都是完整模型；更早的立方体程序模型（`design/backpack-redesign/`）已被取代，仅保留作设计历史。

## 9. 初版 conclusión

- **需求在 NeoForge 1.21.1 上可行**，关键不是「再做一个背包 Screen」，而是 **Overlay 常驻 UI + 服务端库存 + 跨当前容器的物品操作协议**。
- 原版「同时只能有一个激活面板」的限制真实存在，但可被 Overlay 方案绕过；JEI 类模组已验证这条技术路线。
- 与旅行者 / 精妙背包的无缝互拖属于**兼容性工作**，应在原版通路打通后再做，不宜作为 MVP 阻塞项。
